## 这个实验要验证什么

一句话：**验证"插件之间靠'服务'协作，消费方不导入提供方"——即依赖注入的解耦。**

02 讲我们看的是**单个插件**的挂载与清理（时间可组合性）；03 讲往前一步：**多个插件之间**怎么协作。

官方原话：

> **出处**：`docs/cordis-tutorial/03-services.zh.md`——*"服务是一个插件提供、其他插件通过 `ctx` 消费的具名能力……消费方只指定 `'tools'` 之类的能力，而不导入其提供方，因此配置可以选择提供方，无需修改消费方。"*

用你的 Go 经验类比：这就像**面向接口编程 + DI 容器**——消费方 `import` 的是一个 interface（这里叫"服务名"），具体实现由容器在运行时注入。换成 dsh 的话：`ctx` 就是那个 DI 容器，`greeter` 就是接口名，`GreeterService` 是某个实现。

## 先讲理论（动手前必读）

这一讲讲透 **5 个概念**，你先理解"是什么、为什么"，再动手。

### 概念① `Service` 基类 = 注册进容器的"具名能力"

```ts
export class GreeterService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'greeter')   // ← 关键：以名字 'greeter' 注册本实例
  }
  greet(who: string) { return `Hello, ${who}!` }
}
```

`super(ctx, 'greeter')` 做的事：**把当前实例注册到 ctx 这个容器里，名字叫 `greeter`**。此后任何插件都能用 `ctx.greeter` 访问它。

源码为证——`Service` 构造函数末尾调用了 `ctx.reflect.provide(...)`：

> **出处**：`vendor/cordis/src/service.ts:57`——`self.ctx.reflect.provide(name, self, this[symbols.check])`
> **出处**：`vendor/cordis/src/service.ts:8-9`（注释）——*"The service is registered immediately and is automatically removed with the owning fiber."*（注册是即时的，且随所属 fiber 自动移除）

**注意最后半句**：注册本身就是一个 **effect**（02 讲学的那个）。卸载提供方插件时，这个服务会被**自动移除**。这是"注册可逆"在服务上的体现。

### 概念② 两条线：运行时 vs 编译时

官方特意强调 `Service` 代码里有**两条独立的线**在协同：

```ts
declare module '@deepseek-ai/cordis' {   // ← 编译时：类型声明合并
  interface Context { greeter: GreeterService }
}
```

| 线 | 谁负责 | 作用 | 删掉的后果 |
|---|---|---|---|
| **运行时** | `super(ctx, 'greeter')` | 真注册，`ctx.greeter` 真的能取到 | 服务没了 |
| **编译时** | `declare module` 块 | 让 TS 知道 `ctx.greeter` 有类型 | 运行照常，只是 `ctx.greeter` 报类型错 |

> **出处**：`docs/cordis-tutorial/03-services.zh.md`——*"它不会生成代码；没有该声明时，服务在运行时仍能工作，但消费方会失去类型安全。"*

Go 类比：`declare module` 就像**在 Go 里给一个已有的 struct 补一个 interface 断言/方法签名**——纯编译期，不产生运行代码；运行时的真实行为由 `super(...)` 决定。这就是 TS 的"声明合并"（declaration merging），后面《TS 随用随讲》会专门拆。

### 概念③ `inject` = 硬依赖声明 + 调度器

```ts
export const inject = ['greeter']   // ← 声明：我需要 greeter 服务
export function apply(ctx: Context) {
  console.log(ctx.greeter.greet('world'))   // ← 这里 ctx.greeter 一定就绪
}
```

`inject` 有一个**远超"声明"的作用**——它是**调度器**。官方说：

> **出处**：`docs/cordis-tutorial/03-services.zh.md`——*"Cordis 会让插件保持 PENDING，直到列出的每项服务都存在，因此在 `apply` 内可以保证 `ctx.greeter` 已经就绪。`cordis.yml` 中的加载顺序无关紧要：决定插件何时启动的是依赖关系，而不是文件顺序。"*

源码为证——`fiber` 构造时会逐个检查 `inject` 列的服务，就绪后 `_refresh()` 才让 fiber 从 PENDING 变 ACTIVE：

> **出处**：`vendor/cordis/src/fiber.ts:313-317`——`for (const name of Object.keys(this.inject)) { this._checkImpl(name) } this._refresh()`

Go 类比：`inject` 就像 **wire/fx 里的构造器依赖声明**——容器会做**拓扑排序**，等依赖（Provider）全部就绪，才调用你的构造函数（这里叫 `apply`）。你不需要关心启动顺序，就像 fx 不需要你在 `main` 里手动排 `fx.Provide` 的顺序。

### 概念④ 依赖是"持续跟踪"的，不是一次性启动检查

官方原话：

> **出处**：`docs/cordis-tutorial/03-services.zh.md`——*"`inject` 并非一次性的启动检查。如果应用运行期间所需服务消失……每个依赖插件也会随之卸载，并在服务恢复后再次加载。……依赖消失时，它自己的注册也会撤销。"*

这直接接上 02 讲的 effect：**消费方的注册也是 effect，依赖消失 → 逆序撤销；依赖恢复 → 重新执行 `apply`**。这也是配置能**替换服务实现**的原理：卸载旧 provider、挂新 provider，所有 `inject` 它的插件自动在新实现上重启。

### 概念⑤ 可选依赖 `ctx.get()`（这里有个坑，见第 6 步）

如果某能力**缺失时插件也能跑**，那就不写 `inject`，直接在**用到的时候**探测：

```ts
const greeter = ctx.get('greeter')
console.log(greeter?.greet('maybe') ?? 'no greeter available')
```

> **出处**：`docs/cordis-tutorial/03-services.zh.md`「可选依赖」节——*"`inject` 用于硬性依赖。如果某项功能缺失时插件仍可运行，请跳过 `inject`，并在使用处探测。"*

**注意官方措辞是"在使用处探测"**——这个细节第 6 步会变成一个大坑。

## 第 3 步：写代码（两个文件）

### 文件一：`greeter.ts`（提供方）

**请自己敲这个文件**（逻辑与官方 03 讲一致，注释我做了中英对照）：

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    greeter: GreeterService
  }
}

export class GreeterService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'greeter')   // 以名字 'greeter' 注册本实例
  }

  greet(who: string) {
    return `Hello, ${who}!`
  }
}

export const name = 'greeter'

export function apply(ctx: Context) {
  // Service 子类本身就是插件，用 ctx.plugin 像挂载普通插件一样挂载它
  ctx.plugin(GreeterService)
}
```

> **出处**：`docs/cordis-tutorial/03-services.zh.md`「提供服务」节（代码逐字一致，仅注释为本人添加）

### 文件二：`consumer.ts`（消费方）

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'consumer'
export const inject = ['greeter']   // 声明硬依赖

export function apply(ctx: Context) {
  console.log(ctx.greeter.greet('world'))
}
```

> **出处**：`docs/cordis-tutorial/03-services.zh.md`「使用 inject 消费服务」节（代码逐字一致，仅注释为本人添加）

## 第 5 步：验证三个论断（本实验的硬核部分）

官方文档给了几个"反直觉"的论断，**别只信，跑出来才算数**。请你自己做这两个实验：

### 实验 A：交换顺序，输出不变（验证"顺序无关"）

把 `cordis.yml` 两行对调：

```yaml
- name: './consumer.ts'
- name: './greeter.ts'
```

重新 `npm start`——**输出仍是 `Hello, world!`**。因为决定插件何时启动的是**依赖关系**（`inject`），不是文件顺序。

### 实验 B：删掉提供方，静默退出（验证 PENDING）

把 `cordis.yml` 改成只有消费方：

```yaml
- name: './consumer.ts'
```

重新 `npm start`——**什么输出都没有，且退出码是 0**（用 `echo $?` 看）。不是报错、不是卡死，是**静默退出**。

原因：`consumer` 一直 PENDING，而且——

> **出处**：`docs/cordis-tutorial/03-services.zh.md`——*"处于 PENDING 的 fiber 也不会让 Node 的事件循环保持活跃，因此如果组合中没有其他运行项，进程会静默地以状态码 0 退出。"*

> [!tip] 为什么这个"静默退出"很重要
> 这是个**极易踩的坑**：你写了个消费方插件，忘了挂提供方，程序不报错、不崩溃、直接 `exit 0`，你会以为"跑成功了"。官方在[第 6 章]专门讲怎么诊断这种 PENDING 状态。

**本实验三个论断的实测结果**（2026-09-16 亲测）：

| 场景 | 实测输出 | 退出码 | 与文档一致 |
|---|---|---|---|
| 正常（greeter 在前） | `Hello, world!` | 0 | ✅ |
| 交换顺序（consumer 在前） | `Hello, world!` | 0 | ✅ 顺序无关 |
| 删掉 greeter.ts | （无输出） | 0 | ✅ PENDING 静默退出 |

> **出处**：上述三行均为本人在 `test_workspace/cordis-tutorial/lesson-03-services/` 实测（`@deepseek-ai/cordis@4.0.2`）

## 第 6 步：⚠️ 原创陷阱——`apply` 里同步 `ctx.get()` 会拿到 `undefined`

官方"可选依赖"示例看起来很简单，但**直接照搬会在一个地方翻车**。这是本笔记**实测挖出的坑**，官方文档没展开讲。

### 现象

把 `consumer.ts` 换成**不写 `inject`、直接同步 `ctx.get()`** 的版本：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'optional-consumer'
export function apply(ctx: Context) {
  const greeter = ctx.get('greeter')       // ← 这里同步拿
  console.log(greeter?.greet('maybe') ?? 'no greeter available')
}
```

`cordis.yml` 里**明明挂了 greeter**：

```yaml
- name: './greeter.ts'
- name: './optional-consumer.ts'
```

但跑出来是：

```
no greeter available          ← 不是预期的 Hello, maybe!
```

### 根因（源码级）

`ctx.get()` 默认 `strict=true`，**只返回"提供方 fiber 当前已 ACTIVE"的服务**：

> **出处**：`vendor/cordis/src/reflect.ts:12-18`（注释）——*"`strict` — when `true` (default), only return implementations whose providing fiber is currently active. Returns the service value, or `undefined` when not (yet) provided."*

而 greeter 是**异步挂载**的：`optional-consumer` 的 `apply` 同步执行的那一刻，greeter 的 fiber 可能**还没 ACTIVE**，于是 `ctx.get('greeter')` 返回 `undefined`。

### 验证：延后一个事件循环，服务就出现了

把探测从"同步"挪到 `setTimeout`：

```ts
export function apply(ctx: Context) {
  console.log('[sync] ', ctx.get('greeter'))          // undefined
  setTimeout(() => {
    console.log('[async]', ctx.get('greeter'))        // GreeterService { ... }
  }, 50)
}
```

实测输出（2026-09-16）：

```
[sync]  ctx.get(greeter) = undefined
[async] ctx.get(greeter) = GreeterService { ctx: Context <GreeterService>, name: 'greeter' }
[async] -> Hello, async!
```

> **出处**：本人实测（`test_workspace/cordis-tutorial/lesson-03-services/`，`@deepseek-ai/cordis@4.0.2`，2026-09-16）

### 结论：这正是"官方为什么要你用 inject"

- **硬依赖** → 用 `inject`：Cordis 会**等你**（PENDING），`apply` 里服务一定就绪。
- **可选依赖** → 用 `ctx.get()`：但官方说的是**在"使用处"探测**（真的要用它那一刻），**不是**在 `apply` 初始化时同步探测。

Go 类比：`apply` 里同步 `ctx.get()` 拿未就绪的服务，就像**在构造函数里直接去读一个还没被依赖注入进来的全局变量**——拿到 nil。而 `inject` 就像 fx 保证了"依赖先构造完，才构造你"。**能用 `inject` 就用 `inject`；用 `get()` 时，要确认调用时机在服务就绪之后。**

> **出处**：推论综合自 `vendor/cordis/src/reflect.ts:12-18`（strict 语义）+ `vendor/cordis/src/fiber.ts:313-317`（inject 的 PENDING 调度）+ 本人实测

## 第 7 步：命名空间提醒（一个设计约定）

官方最后提醒了一句，值得记：

> **出处**：`docs/cordis-tutorial/03-services.zh.md`「命名」节——*"每个应用中的服务名称共用一个扁平命名空间。请为自有服务添加有辨识度的前缀或命名空间（harness 已占用 `tools` 和 `llm` 等普通名称）"*

用 Go 类比：像**全局包名/注册表**——别用 `log`、`http` 这种无前缀的名字去抢，容易和别人的撞。你自研的服务建议起个有辨识度的前缀（如 `myapp-foo`）。

## 一页纸总结

| 概念 | 一句话 | Go 类比 | 出处 |
|---|---|---|---|
| `Service` + `ctx.plugin()` | 以名字注册能力进 ctx，注册即 effect | 向 DI 容器暴露一个 interface | `service.ts:57` |
| `declare module` | 编译期类型声明合并，不生成代码 | 给 struct 补 interface 签名 | 官方 03 讲 |
| `inject` | 硬依赖声明 + PENDING 调度器 | fx/wire 构造器依赖 + 拓扑排序 | `fiber.ts:313-317` |
| 依赖动态跟踪 | 依赖消失→卸载，恢复→重载 | 依赖变化触发的生命周期重入 | 官方 03 讲 |
| `ctx.get()` 可选依赖 | 缺了也能跑，但**要在使用处**探测 | 可选注入 / 场景探测 | `reflect.ts:12-18` |
| 命名空间 | 服务名扁平共享，加前缀 | 全局包名避冲突 | 官方 03 讲 |

## 踩坑记录

- **独立课时目录必须自己 `npm install`**：`tsx` 从当前目录向上找 `node_modules`，直接复用 02 讲的 `node_modules` 路径不会生效。（出处：AGENTS.md）
- **⚠️ `apply` 里同步 `ctx.get()` 返回 `undefined`**：`ctx.get()` 默认 `strict=true`，只返回提供方 fiber 已 ACTIVE 的服务；异步挂载的提供方在消费方 `apply` 同步执行时可能未就绪。解决：硬依赖用 `inject`；可选依赖在**使用处**探测。（出处：`reflect.ts:12-18` + 实测）
- **PENDING 静默 `exit 0`**：忘了挂提供方时，消费方 PENDING、无输出、退出码 0，极易误判为成功。（出处：官方 03 讲）
