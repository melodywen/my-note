# 实验04 亲手跑通《事件》——看见"五种分发模式"的差异

> [!info] 版本锚点
> - 对应官方：`docs/cordis-tutorial/04-events.zh.md`
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；`@deepseek-ai/cordis@4.0.2`
> - 前置：读完《01》《附》《附2》《实验02》《实验03》
> - **本文是动手文档**：你照着**贴代码、跑命令**，我负责讲清楚每个现象为什么发生

## 这个实验要验证什么

一句话：**验证"插件不用知道谁在监听，就能广播通知"——事件是比服务更松的耦合。**

03 讲的服务是**一对一直接调用**（`ctx.greeter.greet()`，你明确知道调用谁）；04 讲的事件是**一对多广播**（`ctx.emit('xxx')`，发出方**不知道也不关心**谁在听）。

官方原话：

> **出处**：`docs/cordis-tutorial/04-events.zh.md`——*"服务支持直接调用；**事件**让插件无需知道有哪些插件正在监听，就能发出通知。"*

用你的 Go 经验类比：服务 ≈ 直接调用一个 interface 方法；事件 ≈ **发布订阅 / 事件总线**。但 Cordis 的事件比普通 pub/sub 更讲究——它有**五种分发模式**（emit/parallel/serial/bail/waterfall），每种决定"监听器能不能返回值、能否并发、能否短路"。

**本实验的最大价值**：把这五种模式的**差异亲手跑出来**（官方只给了表格，我们自己造例子验证）。

## 先讲理论（动手前必读）

### 概念① 事件也要"声明合并"，且有专门的 `interface Events`

03 讲的 `interface Context` 合并（让 `ctx.greeter` 有类型）你还记得吧？事件有**对应的另一套**：

```ts
declare module '@deepseek-ai/cordis' {
  interface Context { stats: StatsService }          // ← 服务声明（03 讲）
  interface Events {
    'stats/report'(name: string, count: number): void // ← 事件声明（04 讲）
  }
}
```

> **出处**：`docs/cordis-tutorial/04-events.zh.md`——*"`interface Events` 合并与第 3 章的 `interface Context` 合并在事件系统中相互对应：它声明事件名称及其监听器签名，因此 `ctx.emit` 和 `ctx.on` 都具有完整类型。"*

Go 类比：`interface Events` 就像给事件总线定义一套"事件签名表"——有了它，`emit`/`on` 才有编译期类型检查（事件名拼错、参数个数不对，编译就报错）。**删掉它照样跑**（03 讲同理），只是失去类型安全。

### 概念② 命名约定 `namespace/action`

事件名官方推荐 `命名空间/动作` 的写法（如 `stats/report`、`agent/request`）：

> **出处**：`docs/cordis-tutorial/04-events.zh.md`——*"`namespace/action` 命名约定让扁平的事件命名空间保持易读。"*

用 Go 类比：像**日志的 `module.action`** 约定，扁平命名空间里靠前缀区分归属，避免 `report`、`request` 这种名字互相打架。

### 概念③ 五种分发模式（本实验主角）

官方表格：

> **出处**：`docs/cordis-tutorial/04-events.zh.md`「分发模式」节——原文表格如下

| 模式            | 调用                                   | 语义                                                                 |
| ------------- | ------------------------------------ | ------------------------------------------------------------------ |
| **emit**      | `ctx.emit(name, ...args)`            | 同步广播；**不会等待或收集**返回的 promise 与值                                     |
| **parallel**  | `await ctx.parallel(name, ...args)`  | 所有监听器**并发**运行，并一同等待                                                |
| **serial**    | `await ctx.serial(name, ...args)`    | 监听器**按顺序**运行并等待；**第一个非 `null`/`false`/`undefined` 返回值胜出，并停止**后续监听器 |
| **bail**      | `ctx.bail(name, ...args)`            | serial 的**同步版本**                                                   |
| **waterfall** | `ctx.waterfall(name, ...args, next)` | 环绕中间件（见概念④）                                                        |

用 Go 类比，记住这条**心智模型**：

| 模式            | Go 里的对应物                                           |
| ------------- | -------------------------------------------------- |
| emit          | 异步发一个消息就返回（fire-and-forget）                        |
| parallel      | `errgroup.Wait()` / `sync.WaitGroup` 并发跑所有 handler |
| serial / bail | 中间件链，**命中就短路**（如 Gin 的 `c.Abort()`）                |
| waterfall     | **洋葱模型中间件**（Gin/Koa 的 `next()`），可改写返回值             |
|               |                                                    |

### 概念④ waterfall = 洋葱模型中间件（转换或短路）

waterfall 是**实现拦截**的模式。每个监听器收到参数 + 一个 `next()`：

> **出处**：`docs/cordis-tutorial/04-events.zh.md`「waterfall：转换或短路」节——*"每个监听器都会收到参数和一个 `next()` continuation；它可以转换 `next()` 的返回值，也可以不调用 `next()` 就直接返回，从而短路链条的其余部分。Cordis 文档把后一种行为称为否决。"*

官方给的纪律（**非常重要**）：

> **出处**：`docs/cordis-tutorial/04-events.zh.md`——*"**只负责观察或标注的 waterfall 监听器必须调用 `next()`**；不调用就直接返回代表有意短路。如果日志监听器忘记调用 `next()`，会悄无声息地吞掉所有下游的默认行为。"*

Go 类比：就是 Koa/Gin 的洋葱中间件——你**必须** `return next()` 才能把请求传下去；忘了调，后面的中间件和 handler 全部不执行（而且**静默**，不报错）。

## 第 2 步：示例① 声明、发出与监听

### `stats.ts`（既是服务，又发事件）

**请自己敲**（逻辑与官方一致，注释为本人添加）：

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    stats: StatsService
  }
  interface Events {
    'stats/report'(name: string, count: number): void
  }
}

export class StatsService extends Service {
  private counts = new Map<string, number>()

  constructor(ctx: Context) {
    super(ctx, 'stats')
  }

  bump(name: string) {
    const next = (this.counts.get(name) ?? 0) + 1
    this.counts.set(name, next)
    this.ctx.emit('stats/report', name, next)   // ← 发出事件（emit 模式）
  }
}

export const name = 'stats'

export function apply(ctx: Context) {
  ctx.plugin(StatsService)
}
```

> **出处**：`docs/cordis-tutorial/04-events.zh.md`（代码逐字一致，注释为本人添加）

### `reporter.ts`（监听方）

```ts
import type { Context } from '@deepseek-ai/cordis'
import type {} from './stats.ts'

export const name = 'reporter'
export const inject = ['stats']

export function apply(ctx: Context) {
  ctx.on('stats/report', (name, count) => {
    console.log(`[stats] ${name} -> ${count}`)
  })
  ctx.stats.bump('tool_call')
  ctx.stats.bump('tool_call')
  ctx.stats.bump('prompt')
}
```

> **出处**：`docs/cordis-tutorial/04-events.zh.md`（代码逐字一致）

**注意那行 `import type {} from './stats.ts'`**——它**运行时啥都不导入**，只为让 TS 看到上面 `interface Events` 的声明合并。

> **出处**：`docs/cordis-tutorial/04-events.zh.md`——*"`import type {} from './stats.ts'` 行不会在运行时导入任何内容；它的作用是让 TypeScript 看到声明合并。"*

### 配置并运行

```yaml
- name: './stats.ts'
- name: './reporter.ts'
```

```sh
npm start
```

预期输出：

```
[stats] tool_call -> 1
[stats] tool_call -> 2
[stats] prompt -> 1
```

> **出处**：实测（2026-09-16，`@deepseek-ai/cordis@4.0.2`）——输出与官方完全一致

**关键点**：`ctx.on()` 也是 **effect**，监听器随插件一同消失，**永远不需要手动 `removeListener`**。

> **出处**：`docs/cordis-tutorial/04-events.zh.md`——*"因为 `ctx.on()` 属于 effect，监听器会随插件一同消失，绝不需要手动维护 `removeListener`。"*

这正是 02 讲"时间可组合性"在事件上的体现——**注册即 effect，卸载即撤销**。

## 第 3 步：示例② 亲手验证五种分发模式的差异

官方只给了表格。我们**自己造例子**，把差异跑出来。

### 实验 design

写一个 `modes2.ts`，对 serial / bail 各挂 3 个**同步**监听器（L1 返回 undefined、L2 返回非空、L3 本应跑但不该跑），对 emit 挂一个**异步**监听器：

```ts
import type { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Events {
    'demo/serial2'(x: number): number
    'demo/bail2'(x: number): number
    'demo/emit2'(x: number): void
  }
}

export const name = 'modes2'

export function apply(ctx: Context) {
  ctx.on('demo/serial2', (x: number) => { console.log('  serial L1'); return undefined })
  ctx.on('demo/serial2', (x: number) => { console.log('  serial L2 (胜出)'); return x * 10 })
  ctx.on('demo/serial2', (x: number) => { console.log('  serial L3 (应被跳过)'); return 999 })

  ctx.on('demo/bail2', (x: number) => { console.log('  bail L1'); return undefined })
  ctx.on('demo/bail2', (x: number) => { console.log('  bail L2 (胜出)'); return x + 7 })
  ctx.on('demo/bail2', (x: number) => { console.log('  bail L3 (应被跳过)'); return 999 })

  ctx.on('demo/emit2', async () => {
    await new Promise(r => setTimeout(r, 100))
    console.log('  emit 异步监听器（100ms 后才打印）')
  })

  void (async () => {
    console.log('--- serial2 ---')
    console.log('  => ', await ctx.serial('demo/serial2', 3))
    console.log('--- bail2 ---')
    console.log('  => ', ctx.bail('demo/bail2', 3))
    console.log('--- emit2（不 await，立即打印下一行）---')
    ctx.emit('demo/emit2', 0)
    console.log('  emit 之后立刻打印（应早于异步监听器）')
    await new Promise(r => setTimeout(r, 150))
  })()
}
```

`cordis.yml` 只指向它，跑：

```sh
npm start
```

### 实测输出（2026-09-16）

```
--- serial2 ---
  serial L1
  serial L2 (胜出)
  =>  30
--- bail2 ---
  bail L1
  bail L2 (胜出)
  =>  10
--- emit2（不 await，立即打印下一行）---
  emit 之后立刻打印（应早于异步监听器）
  emit 异步监听器（100ms 后才打印）
```

> **出处**：本人实测（`test_workspace/cordis-tutorial/lesson-04-events/`，`@deepseek-ai/cordis@4.0.2`，2026-09-16）

### 逐条解读（这就是表格背后的真相）

| 现象                             | 证明了什么                                    |
| ------------------------------ | ---------------------------------------- |
| serial：L1→L2 后 **L3 没打印**      | serial **首个非空返回即胜出并停止**（L2 返回 30 后短路）    |
| serial 返回值 `=> 30`             | 胜出监听器的返回值被 `serial` 返回                   |
| bail：同 serial 的短路行为            | bail 是 **serial 的同步版**，语义一致              |
| emit："立刻打印" **早于** "100ms 后打印" | emit **不等待**异步监听器，发完就返回（fire-and-forget） |

> [!tip] 为什么 emit 的顺序看着"反直觉"
> `ctx.emit('demo/emit2')` 下面那行 `console.log('emit 之后立刻打印')` **先**输出，异步监听器**后**输出。因为 emit **不同步等待**监听器里的 `await`——这正是官方说的*"不会等待或收集返回的 promise"*。Go 类比：`go func(){...}()` 之后立即执行下一行，不等 goroutine。

## 第 4 步：示例③ waterfall——亲手看"转换"与"短路"

这是本讲最精妙的部分。官方示例（代码逐字）：

```ts
import type { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Events {
    'demo/transform'(input: string, next: () => Promise<string>): Promise<string>
  }
}

export const name = 'waterfall-demo'

export function apply(ctx: Context) {
  // Listener 1: wrap the downstream result.
  ctx.on('demo/transform', async (input, next) => {
    const downstream = await next()
    return downstream.toUpperCase()
  })

  // Listener 2: short-circuit when it owns the decision.
  ctx.on('demo/transform', async (input, next) => {
    if (input.includes('blocked')) return '** blocked **'
    return next()
  })

  void (async () => {
    console.log(await ctx.waterfall('demo/transform', 'hello', async () => 'hello'))
    console.log(await ctx.waterfall('demo/transform', 'blocked words', async () => 'blocked words'))
  })()
}
```

> **出处**：`docs/cordis-tutorial/04-events.zh.md`（代码逐字一致）

`cordis.yml` 只指向该文件，跑：

```sh
npm start
```

预期输出：

```
HELLO
** BLOCKED **
```

> **出处**：实测（2026-09-16，`@deepseek-ai/cordis@4.0.2`）——与官方一致

### 官方解读（照抄，这是理解 waterfall 的关键）

> **出处**：`docs/cordis-tutorial/04-events.zh.md`——*"按顺序看第二行如何产生：监听器 1 先运行并调用 `next()`，从而调用监听器 2；监听器 2 看到 `blocked` 后直接返回而不调用 `next()`，因此最内层默认逻辑（传给 `ctx.waterfall` 的函数）从未运行；返回途中，监听器 1 再把替换消息转换为大写。"*

**画成时序**（第二行 `** BLOCKED **` 的来历）：

```
ctx.waterfall('demo/transform', 'blocked words', 默认fn)
  │
  ├─ 监听器1 执行：await next()
  │     │
  │     └─ 监听器2 执行：input 含 'blocked' → return '** blocked **'（不调 next！）
  │            │
  │            └─ （默认 fn『blocked words』从未执行 —— 被短路）
  │     ← next() 返回 '** blocked **'
  │  监听器1 把它 .toUpperCase() → '** BLOCKED **'
  │
  └─ 返回 '** BLOCKED **'
```

对比第一行 `hello`：监听器2 没命中 blocked → 调 `next()` → 执行默认 fn 返回 `'hello'` → 监听器1 转大写 `'HELLO'`。

用你的 Go 经验：这就是 **Koa/Gin 的洋葱中间件**——`next()` 往下钻、返回值往上冒，每一层都能改写。区别是 Cordis 这里**不调 `next()` = 短路否决**。

### ⚠️ 纪律（一个极易踩的 silent bug）

> **出处**：`docs/cordis-tutorial/04-events.zh.md`——*"**只负责观察或标注的 waterfall 监听器必须调用 `next()`**；不调用就直接返回代表有意短路。如果日志监听器忘记调用 `next()`，会悄无声息地吞掉所有下游的默认行为。"*

**踩坑场景**：你写了个"日志监听器"只想记录一下，忘了 `return next()` → 所有下游逻辑**全被吞掉，且不报错**。Go 类比：Gin 中间件忘了 `c.Next()`，后面的 handler 全不跑——而且是**静默**的，极难排查。

## 第 5 步：harness 里的真实用例（知道事件用在哪儿）

官方列了两个真实示例，说明 waterfall 在 dsh 里怎么用：

> **出处**：`docs/cordis-tutorial/04-events.zh.md`——*"harness 使用 waterfall 处理协作插件可以包装或回答的决策：`agent/request` 允许插件替换模型调用配置，`approval/request` 允许策略代替用户作答。"*

## 一页纸总结

| 概念                  | 一句话                   | Go 类比               | 出处           |
| ------------------- | --------------------- | ------------------- | ------------ |
| `interface Events`  | 事件的声明合并，让 emit/on 有类型 | 给事件总线定签名表           | 官方 04 讲      |
| `namespace/action`  | 扁平命名空间靠前缀区分           | 日志的 `module.action` | 官方 04 讲      |
| **emit**            | 同步广播，不等不收集返回          | fire-and-forget     | 官方 04 讲 + 实测 |
| **parallel**        | 并发跑所有监听器并等待           | `errgroup.Wait()`   | 官方 04 讲      |
| **serial**          | 顺序跑，首个非空返回胜出并停止       | 中间件链命中短路            | 官方 04 讲 + 实测 |
| **bail**            | serial 的同步版           | 同上                  | 官方 04 讲 + 实测 |
| **waterfall**       | 洋葱中间件，可转换/短路否决        | Koa/Gin 的 `next()`  | 官方 04 讲 + 实测 |
| `ctx.on()` 是 effect | 监听器随插件卸载自动消失          | `defer` 自动清理        | 官方 04 讲      |

## 踩坑记录

- **waterfall 忘记 `next()` = 静默吞掉下游**：只想观察的监听器必须 `return next()`；不调即"有意短路否决"。忘调不报错，极难排查。（出处：官方 04 讲）
- **emit 不等待异步监听器**：`ctx.emit()` 后立刻往下走，异步监听器的 `await` 在其后完成——别指望 emit 后的代码能拿到监听器结果。（出处：实测 + 官方 04 讲）
- **serial/bail 的"胜出"判定**：首个返回**非 `null`/`false`/`undefined`** 的监听器胜出并**停止**后续；返回 `undefined` 会被跳过继续找。（出处：官方 04 讲 + 实测）
- **bail 是同步版**：若监听器是 `async`，`ctx.bail()` 拿到的是 Promise（不是解析值）——要同步短路就用同步监听器。（出处：实测 modes.ts 的 `Promise { <pending> }`）
- **`import type {} from './x.ts'` 不导入运行时代码**：只为让 TS 看到 `interface Events` 声明合并。（出处：官方 04 讲）
