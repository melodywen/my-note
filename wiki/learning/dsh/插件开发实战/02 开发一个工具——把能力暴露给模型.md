## 这个实验要验证什么

一句话：**验证"给 dsh 注册一个模型可调用的工具"——模型能通过工具拿到结果。**

01 篇的插件只是打印一行日志（**它不做任何事**）。02 篇的插件**注册一个真正能用的工具** `greet`，模型在对话里可以调用它。

官方原话：

> **出处**：`docs/user/develop/basic/tool.zh.md`——*"本教程会在 Web UI 中添加一个 `greet` 工具。"*

用你的 Go 经验类比：01 篇像**写了个空 main**；02 篇像**注册一个 HTTP handler / RPC 方法**——而且这个 handler 的签名会自动暴露给"调用方"（这里是**模型**）。

## 先讲理论（动手前必读）

### 概念① 工具 = 注册到 `tools` 服务的具名能力

```ts
export const inject = ['tools']              // ← 等工具注册表就绪
export function apply(ctx: Context) {
  ctx.tools.register(defineTool({ ... }))    // ← 注册（注册即 effect）
}
```

> **出处**：`docs/user/develop/basic/tool.zh.md`——*"`inject` 让 Cordis 等待工具注册表就绪。"*

**这与实验07 完全同源**——07 讲你就在最小工程里注册过 `greet` 工具。区别只是**换成真实 dsh 环境**。

### 概念② `defineTool` 的三块：`parameters` / `output` / `execute`

```ts
defineTool({
  name: 'greet',
  description: 'Greet someone by name.',
  parameters: {
    name: { type: 'string', required: true, description: 'The name to greet' },
  },
  output: {
    schema: { type: 'string' },
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute(args) {
    return `Hello, ${args.name}!`
  },
})
```

> **出处**：`docs/user/develop/basic/tool.zh.md`——*"`defineTool` 根据 `parameters` 推导并校验 `args`；`execute` 返回 `output.schema` 声明的规范值，`output.render` 再将该值转换为面向模型的内容。"*

拆开看（**这是 02 篇的理论核心**）：

| 部分 | 作用 | 类比 |
|---|---|---|
| `name` / `description` | 工具名 + 给模型看的描述 | RPC 方法名 + 注释 |
| `parameters` | **参数规约** → 转成**给模型的 JSON Schema** | 函数签名（要暴露给调用方） |
| `output.schema` | 返回值的**规范结构** | 返回类型 |
| `output.render` | 把规范值**转成面向模型的内容**（Native renderer） | 序列化/渲染层 |
| `execute(args)` | 真正干活 | handler 函数体 |

**三个关键洞察**：
1. `parameters` 不只是校验——它**生成给模型看的 JSON Schema**（模型靠它知道怎么调）。
2. `execute` 返回的是 `output.schema` 声明的**规范值**（这里就是字符串 `'Hello, Ada!'`）。
3. `output.render` 把规范值转成**模型/UI 能消费的内容块**（这里是 `[{type:'text', text: value}]`）。

### 概念③ `inject: ['tools']` 的连接作用

> **出处**：官方 `develop/basic/index.zh.md`——*"如果你的插件需要使用其他服务（如 `tools`、`llm`），需要声明 `inject`……框架会确保依赖的服务就绪后才加载你的插件。"*

`tools` 是 dsh 的**工具注册表服务**（03 讲的服务 + 06 讲的 PENDING 机制都在这生效）。

### 概念④ ⚠️ 真实 dsh 插件 vs 最小工程：**依赖解析是最大区别**

这是 02 篇**最该记住的坑**（实测踩到）：

插件被 `--patch` **按绝对路径**加载时，Node 从**插件所在目录**向上找 `node_modules`。而 `dsh-learn/example/plugins/greet-tool/` 默认**没有 `node_modules`**，于是：

```
Error: Cannot find package '@deepseek-ai/dsh-tools'
  imported from .../example/plugins/greet-tool/greet-tool.ts
```

**根因**（本仓库 `codebuddy-llm` 的注释早已点破）：

> **出处**：`example/plugins/codebuddy-llm/codebuddy-llm.ts` 头注释——*"零运行时依赖：`--patch` 按绝对路径加载本文件，插件目录解析不到 `@deepseek-ai/*` 包，因此 dsh-llm 的类型词汇表……在本文件内以结构等价的方式本地实现。"*

**两种解法**：
- **A. 零依赖**：像 `codebuddy-llm` 那样，**不 import** dsh 包，在文件内用结构等价方式自实现（编译器类型擦除后不需要真包）。
- **B. 符号链接**（本文采用）：在插件目录建 `node_modules/@deepseek-ai/*` 符号链接，指向**全局 dsh 安装里的包**。

> **出处**：本人实测（2026-09-16）——解法 B 见下文第 4 步；解法 A 见 `example/plugins/codebuddy-llm/codebuddy-llm.ts`

## 动手：注册 `greet` 工具

> **规则（AGENTS.md）**：动手环节"你动手"。本文代码已写出并可加载；**功能验证（Web UI 调用）由你在浏览器完成**。

### 第 1 步：建插件目录

```sh
cd ~/ai-work/dsh/dsh-learn
mkdir -p example/plugins/greet-tool
```

### 第 2 步：写插件本体 `greet-tool.ts`

创建 `example/plugins/greet-tool/greet-tool.ts`：

```ts
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'greet-tool'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'greet',
    description: 'Greet someone by name.',
    parameters: {
      name: { type: 'string', required: true, description: 'The name to greet' },
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args) {
      return `Hello, ${args.name}!`
    },
  }))
}
```

> **出处**：`docs/user/develop/basic/tool.zh.md`（代码逐字一致）

### 第 3 步：写挂载层 `cordis.patch.yml`

创建 `example/plugins/greet-tool/cordis.patch.yml`：

```yaml
# greet-tool 插件挂载层
- insert:
    - id: greet-tool
      name: '/Users/melodycchen/ai-work/dsh/dsh-learn/example/plugins/greet-tool/greet-tool.ts'
```

> **出处**：结构同 01 篇 + `example/plugins/codebuddy-llm/cordis.patch.yml`

### 第 4 步：⚠️ 解依赖（本文的核心坑）——建符号链接

因为插件 `import { defineTool } from '@deepseek-ai/dsh-tools'`，而插件目录解析不到该包，**必须先接上依赖**。

先找到全局 dsh 的包目录：

```sh
ls ~/.nvm/versions/node/v24.14.0/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/ | grep dsh-tools
```

给插件目录建符号链接（指向全局包）：

```sh
GLOBAL_DSH=~/.nvm/versions/node/v24.14.0/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai
cd ~/ai-work/dsh/dsh-learn/example/plugins/greet-tool
mkdir -p node_modules/@deepseek-ai
for p in dsh-tools dsh-llm dsh-brand cordis schemastery cosmokit dsh-agent \
         dsh-scope dsh-session dsh-invariants dsh-code-runtime \
         dsh-system-prompt dsh-user-approval dsh-timeout; do
  [ -e "$GLOBAL_DSH/$p" ] && ln -sfn "$GLOBAL_DSH/$p" "node_modules/@deepseek-ai/$p"
done
```

> **出处**：本人实测（2026-09-16）——不加链接时 `dsh` 启动报 `Cannot find package '@deepseek-ai/dsh-tools'`；加链接后启动无报错

> [!warning] 符号链接是权宜方案，不是最佳实践
> 它把插件**耦合到全局 dsh 的绝对安装路径**（换机器/换 Node 版本就失效）。更"正统"的做法是给插件一个 `package.json` 并把依赖**本地安装**（或用 pnpm 的 workspace）。本文用符号链接是因为：**全局 dsh 里已有全部包**，链接最省事且能立刻跑通。生产插件应走本地安装。

### 第 5 步：启动并验证加载

```sh
cd ~/ai-work/dsh/dsh-learn
./start.sh --patch /Users/melodycchen/ai-work/dsh/dsh-learn/example/plugins/greet-tool/cordis.patch.yml
```

**实测**（2026-09-16）：dsh 启动**无报错**，Web UI 在 `http://127.0.0.1:3080` 起来。

> **出处**：本人实测（2026-09-16）——启动日志无 `Cannot find package`，dsh web 正常服务

### 第 6 步：在 Web UI 里让模型调用工具 ✅ 已实测

打开 `http://127.0.0.1:3080`，输入：

```
Use the greet tool to greet Ada.
```

**实测结果**（2026-09-16）：

| 界面显示 | 内容 |
|---|---|
| 用户输入 | `Use the greet tool to greet Ada.` |
| 工具调用 | **1 次工具调用** → `工具调用 · greet · Ada` |
| 工具输入 | `{ "name": "Ada" }` |
| **工具输出** | **`Hello, Ada!`** |
| 模型回复 | `Done! 👋 Greeted Ada: "Hello, Ada!"` |

> **出处**：官方 `docs/user/develop/basic/tool.zh.md`——*"打开 `http://127.0.0.1:3080`，然后输入：`Use the greet tool to greet Ada.` 模型可以调用 `greet`，并收到 `Hello, Ada!` 这一工具结果。"*
> **出处**：本人实测（2026-09-16，Web UI）——模型成功调用 `greet`，工具输出 `Hello, Ada!`，与官方预期一致

**这一步证明了完整链路**：模型 → 读懂 `parameters` 生成的 JSON Schema → 生成 `{name:"Ada"}` → 调用 `execute` → 返回 `'Hello, Ada!'` → `output.render` 渲染成 `[{type:'text', text:'Hello, Ada!'}]` → 模型读到结果并回复。

## 一页纸总结

| 概念 | 一句话 | 出处 |
|---|---|---|
| 工具注册 | `ctx.tools.register(defineTool({...}))` | 官方 tool.zh.md |
| `inject: ['tools']` | 等工具注册表就绪 | 官方 tool.zh.md |
| `parameters` | 参数规约 → 给模型的 JSON Schema | 官方 tool.zh.md |
| `output.schema` / `render` | 返回值规范结构 / 面向模型的渲染 | 官方 tool.zh.md |
| `execute(args)` | 真正干活，返回规范值 | 官方 tool.zh.md |
| ⚠️ 依赖解析 | 插件按绝对路径加载，解析不到 dsh 包 | 实测 + codebuddy-llm 注释 |
| 解法 | 零依赖自实现 / 符号链接 / 本地安装 | 实测 |

## 踩坑记录

- **⚠️ `Cannot find package '@deepseek-ai/dsh-tools'`**：插件被 `--patch` 按绝对路径加载，插件目录无 `node_modules`，解析不到 dsh 包。解法：建符号链接指向全局 dsh 包，或零依赖自实现。（出处：实测 + `codebuddy-llm.ts` 注释）
- **端口 `EADDRINUSE: 3080`**：上次 dsh 进程未完全退出。`pkill -f "@deepseek-ai/dsh"` 后再启动。（出处：实测）
- **符号链接不是生产做法**：耦合全局 dsh 绝对路径，换环境即失效；生产中应给插件 `package.json` + 本地安装依赖。（出处：实测）
