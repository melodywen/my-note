# 07.1 agent 的 prompt 写哪——系统提示词 vs user 侧

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）
> - 外部：`code.claude.com/docs/en/{agent-teams,sub-agents}`（Claude Code 官方，2026-09 核实）
> - 前置：**07 篇（agent-team）**、**04.1 篇（系统提示词组装）**
> - 写法说明：本系列采用**完整重讲式**；本篇**专门讲"prompt 写哪"这个问题**

> [!abstract] 本章是什么 / 该记住什么
> **问题**：**一个 agent 的"人设/prompt"，写到【系统提示词】和写到【user 侧（首条消息）】——有什么不同？会有什么问题？**
> **读完该记住 3 点**：
> 1. **系统提示词**（system message）与 **user 消息**——**在模型眼里是"不同优先级/不同位置"的**
> 2. **写 user 侧**：能"扮演"，但**每个 turn 都在"角色扮演的语境"里**——**易被后续指令稀释**
> 3. **写系统提示词**：**更强、更稳定**——但**要能拿到"系统提示词的定义权"**（dsh 的 agent-team 给不了，CC 给得了）

## 这一篇在讲什么

前面的案例暴露了一个真问题：**dsh 的 `spawn_teammate` 只能给 teammate 一个 `prompt`（= 首条 user 消息）**——**给不了"系统提示词"**。于是**"人设"只能写在 user 侧**。

**这引出一个通用问题**：**"人设/prompt 写系统提示词" vs "写 user 侧"——差在哪？**

> **一句话**：**系统提示词（system）= "铁律/身份"**；**user 消息 = "任务/请求"**——**把"人设"写在 user 侧，模型"知道"但那不是它的"身份"，容易被当成"一个用户请求"处理。**

---

## 一、先分清：prompt 的"位置"

一次模型调用的消息，有**两种角色位置**：

| 位置 | 角色 | 在 dsh/CC 里 |
|---|---|---|
| **系统提示词** | `system` message | **人格/铁律/工具用法**（dsh：`persona` section + 各工具 section，见 04.1 篇） |
| **user 侧** | `user` message | **用户请求 / 任务 / 首条 prompt** |

**关键**：**同一个"人设文字"写在不同位置，模型对待它的方式不同**。

---

## 二、写 **user 侧**（如 dsh `spawn_teammate` 的 prompt）——会有什么问题？

dsh 的 teammate 人设**只能写 user 侧**（案例实测：人设在 `spawn_teammate` 的 `prompt`）。

**问题**：

| 问题 | 说明 |
|---|---|
| **① "扮演"而非"是"** | 模型**把"你是资深 PM…"当成"用户让我扮演 PM"**——**是"一个请求"，不是"我的身份"** |
| **② 易被稀释** | 后续对话一多，**这条"人设消息"离得远**——**影响力衰减**（尤其长会话） |
| **③ 不是"铁律"** | **用户在后一条消息说"别管 PM 了，你现在是开发"**——**模型容易"改角色"** |
| **④ 每轮都占 token** | user 消息**留在对话历史里**——**每轮都发**（占上下文） |

**dsh 的实测印证**：**teammate"按人设发言"是"扮演"**——**它能演，但那不是"系统级身份"**。

---

## 三、写 **系统提示词**——更"强"

**写系统提示词**：

| 优点 | 说明 |
|---|---|
| **① 是"身份"** | 系统提示词是模型的"最底层设定"——**"我是 PM"是身份，不是请求** |
| **② 稳定** | **不随对话漂移**（在 user 消息之前，优先级最高） |
| **③ 不易被覆盖** | user 说"别当 PM 了"——**系统提示词的约束更硬**（模型更倾向守系统提示词） |
| **④ 不占每轮 user 历史** | 系统提示词**在固定位置**（不是"历史里的一条"） |

**所以**：**同样的"人设"，写系统提示词 > 写 user 侧**。

---

## 四、⭐ dsh vs Claude Code：谁能给 teammate"写系统提示词"？

**这才是本篇的焦点**——**两边给了不同能力**：

| | **dsh agent-team** | **Claude Code Team** |
|---|---|---|
| **teammate 的 prompt** | `spawn_teammate` 的 `prompt`（**user 侧**） | 可**引用 subagent 定义** |
| **能写系统提示词吗** | ❌ **不能**（继承 Lead 的 preset，见 07 篇） | ✅ **能**——`.claude/agents/*.md` 的正文**追加到 teammate 的系统提示词** |

> **出处**：`code.claude.com/docs/en/agent-teams`（逐字）——*"the definition's body is **appended to the teammate's system prompt** as additional instructions rather than replacing it."*

**即**：
- **dsh**：teammate 人设**只能写 user 侧**（"扮演"）
- **CC**：teammate 人设**能写系统提示词**（"身份"）

**所以 CC 的 teammate 人设"更硬"**——**这正是 CC Team 比 dsh agent-team 成熟的地方**。

---

## 五、⚠️ 两种写法的"正确用法"

| 你想表达 | 该写哪 |
|---|---|
| **"你是谁"（身份/铁律/工具用法）** | **系统提示词** |
| **"这次做什么"（任务/请求/本次上下文）** | **user 侧** |

**⚠️ 反例（常见错误）**：
- ❌ **把"人格/铁律"写在 user prompt 里**（"你是资深 PM，只谈价值…"）——**能演，但不稳**
- ❌ **把"本次任务"写进系统提示词**——**系统提示词应是"长期设定"，不是"单次任务"**

**dsh 的 teammate 现状**：**人设被迫写 user 侧**（因为给不了系统提示词）——**这是"将就"，不是"最佳"**。

---

## 一页纸总结

| 概念 | 一句话 | 出处 |
|---|---|---|
| **系统提示词** | 身份/铁律（`system` message） | 04.1 篇 |
| **user 侧** | 任务/请求（`user` message） | — |
| **写 user 侧的问题** | "扮演"非"身份"；易稀释；可被改；占每轮 token | 本篇分析 |
| **写系统提示词** | 更硬/更稳/是身份 | 本篇分析 |
| **dsh teammate** | 人设**只能写 user 侧**（spawn prompt） | 07 篇 |
| **CC teammate** | 人设**能写系统提示词**（引用 subagent 定义，**追加**） | CC 官方文档 |
| **CC 的限制** | `skills`/`mcpServers` 不应用；`permissionMode` 不能 spawn 设 | CC 官方文档 |

## 踩坑预防

- **⚠️ 别把"人设/铁律"写 user 侧**（若平台支持系统提示词）——**会被当"请求"，不稳**。
- **⚠️ 别把"单次任务"写系统提示词**——**系统提示词是长期设定**。
- **⚠️ dsh 的 teammate 人设只能写 user 侧**（`spawn_teammate` 的 prompt）——**是"将就"**。
- **⚠️ "实验性"**：dsh agent-team 没做"subagent 定义引用"——**这是它相对 CC 的短板**。
