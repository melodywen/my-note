# 07.2 dsh agent-team vs Claude Code Team——逐项对比

> [!info] 版本锚点
> - dsh 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）
> - CC 文档：`code.claude.com/docs/en/{agent-teams,sub-agents}`（2026-09 核实）
> - 前置：**07 篇（agent-team）**、**07.1 篇（prompt 写哪）**
> - 写法说明：本系列采用**完整重讲式**；本篇是**对比篇**

> [!abstract] 本章是什么 / 该记住什么
> **问题**：**dsh 的 agent-team 相比 Claude Code 的 Team，是强还是弱？弱在哪？**
> **一句话答案**：**核心协作机制【对等】；per-teammate 定制【dsh 弱】**。
> **读完该记住 3 点**：
> 1. **对等的**：共享任务板 / 邮箱互发 / 独立 context / 只由 Lead 管理（无嵌套团队）
> 2. **dsh 缺的**：**per-teammate 系统提示词**（CC 引用 subagent 定义）、**per-teammate model**
> 3. **定位**：**dsh agent-team = "CC Team 的对等骨架 + 缺失的 per-teammate 定制"**

## 这一篇在讲什么

前两篇暴露了：**dsh 的 teammate 人设只能写 user 侧**（07/07.1）。这自然引出对比：**CC 的 Team 呢？dsh 到底差多少？**

> **一句话**：**不是"整体弱很多"——是"框架对等、定制能力弱"。**

---

## 一、⭐ 对等的部分（框架级——两边都有）

> **出处**：dsh `agent-team.zh.md`；CC `code.claude.com/docs/en/agent-teams`

| 能力 | dsh | CC | 说明 |
|---|---|---|---|
| **Lead + teammates 结构** | ✅ | ✅ | 一个 Lead 统筹、多个 teammate |
| **每个 teammate 独立 context window** | ✅ | ✅ | 各自上下文，不共享 |
| **共享任务板（task list）** | ✅ | ✅ | teammates 认领任务 |
| **邮箱 / 互发消息** | ✅ | ✅ | teammate 之间**直接**通信（不走 Lead） |
| **只由 Lead 管理（无嵌套团队）** | ✅ | ✅ | teammate 不能再起 team |
| **Leader 固定（不能转让）** | ✅ | ✅ | — |

**即**：**"多 agent 互相通信 + 共享任务板"这个核心——两边【对等】。**

> **⚠️ 关键洞察**：**agent-team 相对 subagent 的本质 = "通信"**（subagent 只能回报父，teammate 能互发）——**这一点两边都做到了**。

## 二、⭐ dsh **缺的**部分（per-teammate 定制）

> **出处**：dsh `tool-agent-team/src/index.ts`（`spawn_teammate` 参数：`name`/`description`/`prompt`/`context`——**无 `model`**）；CC 官方文档

| 能力 | dsh | CC | 说明 |
|---|---|---|---|
| **per-teammate 系统提示词** | ❌ **无** | ✅ **有**（引用 `.claude/agents/*.md`，**追加**到系统提示词） | **最重要的一条** |
| **per-teammate model** | ❌ **无**（spawn 无 `model` 参数） | ✅ **有**（spawn 指定 / `/config`） | — |
| **per-teammate 工具限制** | ⚠️ 有限 | ✅（`tools` 继承） | — |
| **per-teammate 权限** | ⚠️ spawn 后改 | ⚠️ spawn 后改 | 两边都不支持 spawn 时设 |
| **per-teammate skills / mcpServers** | ❌ | ❌（CC 也**不应用**） | 两边都缺 |

**dsh 最明显的短板**：**teammate 的系统提示词 / model 不能按角色定制**——**人设只能写 user 侧（07.1）**。

> **CC 的做法**（逐字）：*"the definition's body is **appended to the teammate's system prompt**"*——**即：CC 的 teammate 能"带着自己的系统提示词"上工**。

## 三、dsh agent-team **对等或偏强**的地方（公平说）

| 能力 | dsh | 说明 |
|---|---|---|
| **复用 subagent seam** | ✅ | dsh teammate 走 **`ctx.subagents.startContinuable`**（`roster.ts:282`）——**和 subagent 共享基础设施** |
| **持久 mailbox** | ✅ | **append-only + `foldTeam` 回放**（崩溃可恢复，`agent-team.zh.md:26/78`） |
| **显式启用 + profile 层** | ✅ | 部署方**显式控制**（不会误触发）——CC 也是 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` |

## 四、结论："弱"要限定范围

> **dsh agent-team = "CC Team 的【对等骨架】+ 缺失的【per-teammate 定制】"**。

| 维度 | 判定 |
|---|---|
| **核心协作机制**（任务板/邮箱/互发/独立 context） | ✅ **对等** |
| **per-teammate 定制**（系统提示词/model/工具） | ❌ **dsh 弱** |
| **整体** | ⚠️ **"框架对等、定制弱"**——不是"整体弱很多" |

**⚠️ 且 dsh 的是 `experimental`**——**它可能"以后补上"**（CC 的"引用 subagent 定义"也是**后来才加**的，issue #24316 记录了演进）。

## 踩坑预防

- **⚠️ 别以为 dsh agent-team"整体弱"**——**核心机制对等**，弱在"per-teammate 定制"。（出处：逐项对比）
- **⚠️ dsh teammate 人设只能写 user 侧**（spawn prompt）——CC 能写系统提示词。（出处：07.1）
- **⚠️ 两边都不支持有的**：spawn 时设 per-teammate 权限、skills/mcpServers 不应用。（出处：双方文档）
- **⚠️ 都是 experimental**——**API/能力可能变**。（出处：双方文档）
