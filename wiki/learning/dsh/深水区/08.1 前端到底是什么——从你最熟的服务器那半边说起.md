# 08.1 前端到底是什么——从你最熟的"服务器"那半边说起

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**08.0（本章地图）**
> - 本篇对象：**没写过前端的后端**。全程 Go 类比。

> [!abstract] 读完该记住 5 点
> 1. **"前端"= 跑在浏览器里的那部分程序**；"后端"= 跑在服务器里的那部分。**dsh 两边都有**。
> 2. **浏览器里就三样东西**：**HTML**（结构）、**CSS**（样式）、**JavaScript/TypeScript**（行为）。
> 3. **它们怎么通信**——这才是后端最该先懂的：**不是函数调用，是"网络请求"**（HTTP / WebSocket）。
> 4. **dsh 的边界**：浏览器这半边叫 `client/`，服务器那半边叫 `host/`；中间隔着一层 **RPC**。
> 5. **dsh 的浏览器插件，代码就是 `.tsx` / `.css` 文件**——跟你写后端插件一样是"项目里的文件"，只是跑在浏览器。

## 这一篇在讲什么

你是后端。你脑子里的"程序"是：**一个进程，监听端口，收请求，返回响应**。

那"前端"呢？——**它是另一个程序，跑在用户的浏览器里**。

**一句话**：**前端 = 跑在浏览器里的程序；它通过"网络请求"和后端说话。**

> **Go 类比（先立住）**：
> - 你的 Go HTTP 服务 = **后端**（跑在服务器）
> - 浏览器 = **另一种"客户端进程"**（跑在用户机器），它自己也能跑代码（JS/TS）
> - 前端代码 = **装进浏览器里运行的那个程序**
> - 浏览器和你的服务之间，**靠 HTTP/WebSocket 通信**（跟你写过的任何 web 服务一样）

## 一、最基础的分工：谁跑在哪

```
┌────────────────────┐                    ┌────────────────────┐
│   用户的机器        │                    │    服务器           │
│                    │   ← 网络请求 →      │                    │
│  ┌──────────────┐  │   HTTP / WebSocket │  ┌──────────────┐  │
│  │   浏览器      │  │                    │  │  你的服务     │  │
│  │  (前端程序)   │  │                    │  │  (后端程序)   │  │
│  └──────────────┘  │                    │  └──────────────┘  │
│         ↑          │                    │         ↑          │
│    用户直接操作      │                    │    处理数据/逻辑    │
└────────────────────┘                    └────────────────────┘
```

**关键认知（后端最容易忽略的）**：**浏览器是一个"独立的执行环境"**——它**能跑代码**，而且**跑的是用户机器上的代码**。

> **Go 类比**：把"浏览器"想成**一个你不知道对方是谁的客户端**。你不知道它是什么机器、什么系统、甚至（理论上）是不是真浏览器。**所以你不能信任它**——这就是为什么**鉴权、校验必须在后端做**（dsh 就是这么做的，见第四节）。

**在 dsh 里**：

| 半边 | dsh 叫它 | 跑在哪 | 干什么 |
| --- | --- | --- | --- |
| 前端 | `packages/client/` | **浏览器** | 显示界面、响应用户点击 |
| 后端 | `packages/host/` | **服务器**（Node.js 进程） | 跑 Agent、读写文件、调模型 |

> **出处**：`packages/client/README.zh.md` 开篇——*"`client/` 组提供 dsh web GUI 的**浏览器体验**"*；`packages/host/README.zh.md` 对应"服务端页面交付与宿主集成"。

> **注意**：dsh 的后端是 **Node.js**（JS 写的服务器），不是 Go。但**架构上和你写的 Go 服务是一回事**——一个监听端口、处理请求、返回响应的进程。

## 二、浏览器里的"三件套"：HTML / CSS / JS

浏览器里的程序，**不是一坨代码**，而是**三样东西分工协作**：

| 三件套 | 管什么 | 后端类比 | 文件后缀 |
| --- | --- | --- | --- |
| **HTML** | **结构**——页面上有什么（标题、按钮、输入框） | 一个**树形结构**（≈ XML/JSON 描述的对象树） | `.html` |
| **CSS** | **样式**——这些东西长什么样（颜色、大小、位置） | **主题/模板配置**（决定"渲染成什么样"） | `.css` |
| **JavaScript**（写 TS 编译成它） | **行为**——点了按钮干什么 | **运行时代码**（真正干活的逻辑） | `.js` / `.ts` / `.tsx` |

### ① HTML：不是"编程"，是"描述结构"

HTML 长这样：

```html
<div class="sidebar">
  <button>新建会话</button>
  <span>Hello</span>
</div>
```

**读法**：`<div>` 是一个"盒子"，里面装了个 `<button>`（按钮）和一个 `<span>`（一段文字）。

> **Go 类比**：像**结构体/JSON**——
> ```go
> type Div struct {
>     Class    string
>     Children []Node  // 一个 button + 一个 span
> }
> ```
> HTML **描述"页面树长什么样"**，不描述"怎么动"。

### ② CSS：给结构"上样式"

```css
.sidebar {
  background: var(--dsw-alias-bg-base);   /* 背景色 */
  padding: 8px;                            /* 内边距 */
  font-weight: 500;
}
```

**读法**：凡是 `class="sidebar"` 的盒子，背景色是某个变量、内边距 8 像素。

> **Go 类比**：像**配置文件**（决定"输出格式"）。dsh 的 CSS 里到处是 `--dsw-alias-*` 这种**变量**——它是主题系统，见 [08.4]。**改样式 = 改 CSS/变量**，不用碰逻辑。

### ③ JavaScript / TypeScript：让页面"动起来"

```ts
button.addEventListener('click', () => {
  // 点按钮时执行
})
```

**读法**：给按钮挂个"点击回调"。

> **Go 类比**：**这就是普通的程序代码**，只不过跑在浏览器里。**TypeScript = JavaScript + 类型**（下一篇 08.2 详解）。

## 三、最关键的一节：浏览器和你的服务，怎么"说话"

**这是后端最该先建立的直觉**：前端和后端**不共享内存、不互相调用函数**——**它们隔着网络**。

### 通信方式 1：HTTP 请求（请求-响应，一问一答）

这是**你最熟的模式**：

```
浏览器 —— "GET /api/settings" ——►  你的服务
浏览器 ◄—— 200 {"preference":"dark"} —— 你的服务
```

**这就是你天天写的 REST 接口**。浏览器 `fetch(...)` 发请求 → 你的服务返回 JSON。

> **Go 类比**：**一模一样**。你写 `http.HandleFunc("/api/settings", ...)`，浏览器那边就是发个 `GET /api/settings`。

### 通信方式 2：WebSocket（长连接，服务端主动推）

HTTP 是一问一答；但有时**服务器要主动推消息给浏览器**（比如实时日志、进度更新）。这时用 **WebSocket**——**一条保持不断的双向通道**。

```
浏览器 ◄══════ 长连接一直开着 ══════► 你的服务
        服务端随时可以 push 数据下来
```

> **Go 类比**：像你写的 **gRPC streaming** 或者长轮询——**只是浏览器原生支持 WebSocket**。

### dsh 用的是哪种？——两个都用

> **出处**：`packages/client/connection/README.zh.md`（逐字）——*"浏览器通过 **HTTP POST** 执行 Remote 一元调用；**API Gateway 自己拥有 `/api/remote.mux` WebSocket 及其逻辑流**。"*

**翻译**：

| dsh 的通信 | 用途 | 对应你的经验 |
| --- | --- | --- |
| **HTTP POST** | 一次性调用（"改个设置"、"发条消息"） | REST |
| **WebSocket**（`/api/remote.mux`） | 持续的事件流（Agent 边跑边推、日志） | gRPC streaming |

**这条边界的两侧，就是 dsh 的 `client`（前端）和 `host`（后端）**。理解了这一点，你就理解了 dsh Web 架构的**骨架**。

## 四、后端最该警惕的：浏览器"不可信"

因为浏览器跑在**别人机器上**，所以：

- **鉴权必须在后端做**——不能指望"前端藏起来就安全"。
- **每个请求都要验证**。

**dsh 怎么做的**（值得后端读，因为思路和你熟的一模一样）：

> **出处**：`packages/client/connection/README.zh.md`「浏览器认证与请求信任」（逐字要点）：
> - *"**每个进程生成一个随机启动令牌**。`dsh-web-app` 打印并打开带 `?token=...` 的普通根 URL；`frontend-static` ……只在 `GET /` 接受该令牌，**写入绑定 authority 的签名 cookie**，再重定向到干净的 `/`。**缺失、过期、畸形或 authority 不匹配的 cookie 会在 RPC 分发前得到 401**。"*
> - *"**静态资源保持公开**。"*
> - *"cookie ……它是 **host-only、`Path=/`、`HttpOnly`、`SameSite=Strict`**"*
> - *"认证之前，每个请求仍经过 `src/api-request-trust.ts`。其 `Host` 必须是 loopback，或与 `trustedHosts` 条目匹配……这些检查防御 **DNS rebinding** 与跨站浏览器请求"*

**这套东西，你（后端）应该一点都不陌生**：

| dsh 的做法 | 你的经验 |
| --- | --- |
| 启动打印一个随机 token（`?token=...`） | 一次性登录链接 / 一次性 token |
| 交换成签名 cookie | session cookie / JWT |
| 静态资源公开，API 要鉴权 | 静态文件 + 受保护 API |
| 鉴权前先做 Host/Origin 校验 | CSRF / DNS-rebinding 防护 |
| 401（没认证）/ 403（Host 不可信） | 标准 HTTP 语义 |

> **这就是你之前启动 dsh 时为什么必须带 `?token=...`**——不带就 **HTTP 401**。现在你知道**为什么**了：这是 dsh 的浏览器鉴权机制，**跟你后端的鉴权是同一类东西**。

## 五、dsh 的"前端代码"长什么样（先看一眼，不深究）

你不需要现在就懂，但**先知道"它长在哪、什么形态"**：

```
deepseek-harness/packages/client/ui-sidebar/src/
├── index.ts                       ← 插件入口（后端也写这种）
└── client/                        ← 浏览器半边
    ├── SidebarRoot.tsx            ← 一个"组件"（.tsx = TS + 界面）
    ├── SidebarRoot.module.css     ← 这个组件的样式
    └── contract/slots.ts          ← 声明"这里有哪些扩展点"
```

**看到没**：**跟你写后端插件一样，就是一堆文件**。只是：

- `.tsx` = **TypeScript + 界面描述**（里面能写 `<div>` 这种东西）
- `.module.css` = 样式
- 跑在**浏览器**，不是服务器

> **Go 类比**：这一堆 `.tsx`，就像你的 `myplugin/*.go`。**都是"插件项目里的源文件"**，区别只是**运行环境**和**语言**。
