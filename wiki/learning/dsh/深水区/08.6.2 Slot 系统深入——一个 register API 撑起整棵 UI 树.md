# 08.6.2 Slot 系统深入——一个 register API 撑起整棵 UI 树

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**08.6.1（三层模型）**——本篇深入中间那层（② 组合层）
> - 权威文档：`.agents/notes/implemented/architecture/2026-07-22-slot-type-chain-implementation.zh.md`（标题：*"slot 体系标准——单一 register、props 四份额与框架 store 席位"*）
> - 写法说明：以**读源码 + 讲机制**为主；引号内中文为文档**逐字**引用

> [!abstract] 本章是什么 / 该记住什么
> **回答的问题**："**dsh 的 UI 是怎么拼出来的？**"
> **答案**：**只有一个 API——`ctx.slots.register(...)`**。整个页面（从 root 到任意深度）都是插件**递归 register** 出来的。
> **读完该记住 6 点**：
> 1. **`'root'` 是唯一的先验 slot**——渲染器只渲染它一次，其余全靠插件声明
> 2. **没有"slot 定义 API"**——`children` 对象**同时**做"声明子 slot"+"授权渲染"（**"声明即认领"**）
> 3. **四种 kind**：`single` / `list` / `keyed` / `chain`——覆盖"单个/有序列表/按键分派/自荐路由"
> 4. **组件 props 分"四份额"**：运行时 / 子 slot 渲染 / store / 业务（inject）——**各有唯一真源**
> 5. **`store` 必须是工厂函数**——杜绝模块级单例（会跨插件重载"复活"）
> 6. **装载即炸**：重复声明、注册未声明 slot、chain 缺 `select` → **加载时抛错**（不留到渲染热路径）

## 这一篇在讲什么

08.1 讲了"三层"，其中**② 组合层（`ui-slots`）是纯核心**。本篇把它彻底拆开：**一个 `register` 调用是怎么变成一个页面的**。

**一句话**：**slot 系统 = "一棵由插件自己长出来的渲染树"**。没有中央"布局配置"，每个插件**声明自己要渲染哪些洞（slot）+ 自己往哪些洞里放东西**。

> **Go 类比**：像 **`database/sql` 的 `Register` 驱动**——只有一个注册入口，但注册的东西自己声明"我能处理什么"。又像 **`http.ServeMux` + `HandleFunc`**——`register` 近似 `Handle(pattern, handler)`，但**更强**：它还能声明"我这个 handler 内部还有哪些子路由"。

## 一、'root'：唯一的先验 slot

整个 slot 树**不是无中生有的**——它有**唯一一个"上帝给定"的根**：`'root'`。

> **出处**：slot 标准文档 `:21`（逐字）——*"`SlotRegistry`（client 运行时）在构造时声明 `'root'`——**single/root**、`owner: {}`……ui-renderer 的全部装配就是 `ctx.slots.renderSlot('root', {})`：**唯一的 ctx 级渲染入口**；传任何其他键、渲染器未安装、root 无人注册，**一律大声失败（无 fallback）**。"*

> **出处**：源码 `packages/client/ui-slots/src/index.ts:740` —— `root.spec = { kind: 'single', scope: 'root' }`（**逐字源码**，印证'root' 是 single + root scope）

**关键三点**：

1. **`'root'` 是 `single` kind + `root` scope**——一个占位者（谁注册谁独占）。
2. **渲染器只调用一次** `renderSlot('root', {})`——这是**全程序唯一的 ctx 级渲染入口**。
3. **无 fallback**——root 没人注册 / 传了别的键 / 渲染器没装 → **直接 throw**。这是**故意的**："大声失败"优于"白屏"。

> **出处**：`packages/client/ui-renderer/README.zh.md:32`（逐字）——*"渲染器执行**全程序唯一一次**上下文级 `renderSlot('root')` 调用；注册的根占用方**拥有产品布局与文档元数据**。"*

```
renderSlot('root')  ← 唯一入口，只有这一条
   └─ 由某个插件 register 的根组件渲染
        └─ 它的 children 里声明的 slot（如 'sidebar' / 'main'）
             └─ 又被别的插件 register 填充……递归下去
```

## 二、"声明即认领"：没有 slot 定义 API

这是整个系统**最反直觉、也最精巧**的设计。

### 没有独立的"声明一个 slot"的 API

大多数"插槽系统"是两段式：

```ts
// ❌ 这不是 dsh 的做法
defineSlot('sidebar')                      // 先定义
register('sidebar', MyComponent)           // 再填充
```

dsh **只有一段**——`register` 的 `children` 对象**同时**做两件事：

> **出处**：slot 标准文档 `:27`（逐字）——*"**不存在独立的 slot 定义 API**。`children` 对象**同时做两件事：声明子 slot，并授权本组件渲染它们**——slot 是渲染树上的一个洞，**因为有人要渲染它才存在**，所以 slot 的生命周期就是声明它的 entry 的生命周期（entry 一经 dispose，slot 随之消亡、slot 内既有贡献清空）。"*

```ts
// ✅ dsh 的做法（出处：slot 标准文档 :27 的代码块）
ctx.slots.register({
  name: 'root',
  children: {
    'sidebar': { kind: 'single', scope: 'root' },
    'main':    { kind: 'keyed',  scope: 'root' },
  },
  store: createLayoutStore,      // store 席位（见第五节）
  inject: injectFrame,           // 业务面（见第六节）
}, AppFrame)
```

**读法**：
- `name: 'root'` → 我**占用** root slot
- `children: {...}` → 我**声明** root 下面有两个洞 `sidebar`/`main`，**并授权**我自己渲染它们
- `AppFrame` → 我的组件（它是 `SlotComponent`）

> **出处**：源码 `packages/client/ui-slots/src/index.ts:152`（逐字注释）——*"**Declaring is claiming**: the registering entry becomes the only entry…"*（声明即认领：注册的条目成为唯一被允许渲染该键的条目）

### "声明即认领"带来的三条铁律

**铁律 1：slot 的生命周期 = 声明它的 entry 的生命周期**

> **出处**：slot 标准文档 `:27`（逐字）——*"条目的 disposer 会**递归移除其声明的子 slot**——账本行、贡献与 store 挂载**都随同一生命周期结束而移除**。"*

**铁律 2：对等独占**——子 slot 的渲染权**独占**给声明它的 entry：

> **出处**：slot 标准文档 `:33`（逐字）——*"**声明子 slot 的 entry 独占渲染这些子 slot 的权力**，全部在 register 时确定（**配置错误会在装载时明确失败；渲染热路径不再校验**）。"*

**铁律 3：装载即炸**（fail-fast）——下列情况**加载时就抛**：

> **出处**：slot 标准文档 `:33`（逐字）——*"**装载即炸**的情形：第二个 entry 声明已被声明的 slot；向未声明的 slot register；同一个 store 句柄挂到两个 scope 之下；chain 注册缺 `select`。"*

| 错误 | 何时发现 |
| --- | --- |
| 两个 entry 声明同一个 slot | **装载时** ✅ |
| 向未声明的 slot register | **装载时** ✅ |
| 一个 store 句柄挂两个 scope | **装载时** ✅ |
| chain 注册缺 `select` | **装载时** ✅ |
| （反例）运行时才发现冲突 | —— dsh **不做**这个 |

> **Go 类比**：像**编译期就能抓到的重复 `Handle` 注册**——而不是运行到请求进来才 panic。

## 三、四种 kind：一个"洞"的四种形态

> **出处**：源码 `packages/client/ui-slots/src/index.ts:98`（逐字）——`export type SlotKind = 'single' | 'list' | 'keyed' | 'chain'`

| kind | 含义（出处：slot 标准文档 `:12` 的相关段落 + `ui-slots/README.zh.md:12`） | 谁决定渲染什么 |
| --- | --- | --- |
| `single` | **单个占位者**——只有一个 entry 能占用 | entry 自己（唯一） |
| `list` | **有序条目**——多个 entry 按 `order` 排列 | 声明方按序全部渲染 |
| `keyed` | **按键分派**——分发现场用 `entryKey` 点选 | **owner** 用 key 点选 |
| `chain` | **条目自荐**——entry 带 `select` 纯选择器，首个匹配者接管 | **entry** 自荐（owner 不知道谁来） |

### `keyed` vs `chain`：路由权归属相反（最值得理解的一对）

这是文档专门用一节讲的**关键对照**：

> **出处**：slot 标准文档 `:56`（逐字）——*"第四种 `SlotKind`——`'chain'`——**把路由权相对 `keyed` 反转**：keyed 的分派现场以 `entryKey` **点选**占用 slot 的 entry，chain 则由 entry **自荐**——**owner 只分派一套格式统一的 owner props，永远不知道谁来接管**，新的接管包注册进来 **owner 零改动**。"*

```
keyed（owner 知道有谁）：
  owner ──"给我 toolName='Bash' 那个"──► 找到注册 key='Bash' 的 entry

chain（owner 不知道有谁）：
  owner ──"这是 owner props，你们谁要？"──► entry1.select(props)→null
                                          ► entry2.select(props)→{matched} ← 我接了！
```

**`chain` 的完整机制**（出处：slot 标准文档 `:56`，逐字要点）：

- 每个 chain 注册带一个 **`select` 纯选择器**（`ChainSelect<O, M>`：`(owner) => matched | null`）
- 可选 **`priority`**（**升序**；同值保持**注册序** = 装配序）
- **渲染时**：outlet 按链序依次执行各 `select` → **首个非 null 返回值当选**，该值以 `matched` 并入组件 props（**组件绝不自行重新推导匹配**）
- **全 null** → 渲染 owner 的 fallback（`ChainRenderOpts`）

### 为什么 `select` 必须是"纯函数"（一条纪律）

> **出处**：slot 标准文档 `:56`（逐字）——*"「不接」的判定**住在 `select` 里，绝不在挂载后的组件里自探 props**：组件为了渲染 null 也得先挂载，其**钩子与 effect 全部白跑**，随之而来的**挂载/卸载抖动还会破坏 memo 化与 React key 语义**；而选择器是**纯函数**——可单测、零挂载副作用……**选择器只做路由，绝不创建新对象**——按分派逐次构造对象会让引用每次渲染都换新。"*

> **Go 类比**：`select` 就像 **`http.Handler` 的中间件"要不要处理这个请求"的判断**——判断应当是**纯函数**（只看请求、不产生副作用），而不是"先执行一半再决定". 又像 **gRPC 的 `UnaryServerInterceptor`**——决定"拦不拦"的逻辑应独立于"实际处理"的逻辑。

## 四、组件 props 的"四份额"：各有唯一真源

注册的组件**不会凭空拿到数据**——它收到的 props 由**四份**自动推导拼成，**每一份都有一个唯一的真源**：

> **出处**：slot 标准文档 `:45`（表格，逐字）：

| 份额 | 类型 | 真源 | 内容 |
| --- | --- | --- | --- |
| **运行时** | `PropsRuntime<K>` | K 对应的 `SlotMap` entry | `OwnerOf<K>`（渲染现场传参）+ session scope 标配 `useSession`/`sessionId` + 全局 `useSessions`/`useWorkspaces` |
| **子 slot 渲染** | `PropsRenderSlots<S>` | register 的 `children` 键集 | `renderSlot(key, owner)`，键参静态收窄到 S；chain 键另有 `renderSlotChain` |
| **store** | `PropsStore<H>` | store 工厂的返回类型 | `useStore` selector 钩子 + `actions.*`（剥去 draft 形参） |
| **业务** | `I` | **inject 的返回类型** | 普通数据+回调；`hooks` 区域内裸 observable 经绑定后以 `use<Name>` 选择器钩子形式到达 |

### "四份额"的设计动机：**编译期收口**

> **出处**：slot 标准文档 `:45`（逐字）——*"register 调用点是**双重类型约束的收口**：组件的 renderSlot 键集超出 `children` 声明、漏接某个已声明的面、store/inject 形状漂移，**任何一条都在那一行上报编译错误**。"*

**翻译成人话**：你在 `register(...)` 那一行写错任何一个"接头"，**TypeScript 当场红**——不用等运行时。

```
register({ children: {...}, store, inject }, Component)
                │              │       │         │
                │              │       │         └─ 组件实际消费的 I 必须匹配 inject 返回值
                │              │       └─ 组件收到的 store 份额由工厂返回类型推导
                │              └─ 组件能 renderSlot 的键 ⊆ children 声明的键
                └─ children 的值必须与 SlotMap 静态对齐
```

### 转授 = 普通 props 传递（没有"面对象"）

> **出处**：slot 标准文档 `:45`（逐字）——*"**转授就是普通的 props 传递**（把 `renderSlot` 函数递下去，可按需包一层更窄的签名）——**不存在白名单面对象，也不存在铸面 API**。"*

**含义**：父组件想把"渲染某个洞"的能力交给子组件，就**把这个函数当普通 props 传下去**——不需要任何"权限系统/面对象"。

### 两条"类型链硬化裁定"（将来别随手改）

文档明确说这两条是**为什么存在**、**将来编辑者不应重新争论**：

> **出处**：slot 标准文档 `:99`（逐字）

1. **注册位用 `SlotComponent<P>`（裸调用签名）而非 `FC<P>`**。因为 React 的 `FC` 带静态字段（`propTypes`/`defaultProps`），其可赋性检查会**拒绝设计本想接受的组件**；裸调用签名只走干净的形参逆变检查。
   > **出处**：源码 `packages/client/ui-slots/src/index.ts:376` —— `export type SlotComponent<P> = (props: P) => ReactNode`（**逐字源码**）
2. **`NoInfer<I>` 把业务份额推断钉在 inject 工厂上**。否则 TS 会从组件形参位收集推断候选，**漂移的组件会静默把 `I` 加宽到让调用通过**——恰好吸收掉类型链要抓的漂移。

> **⚠️ 提醒**：文档说负样本 spec 钉住了第 2 条——**若日后被"顺手简化"掉 `NoInfer`，expect-error 位会第一个变红**。

## 五、store 席位：引擎归框架，schema 归注册方

### 框架只拥有一套订阅机制

> **出处**：slot 标准文档 `:64`（逐字）——*"框架**只拥有一套订阅机制**：快照 store 引擎（**zustand vanilla + immer + 可选 localStorage 持久化**）住**运行时包**，产出**裸的可观察源**；ui-renderer 在 outlet 处把它们**绑定成钩子**（按源缓存的 uSES 绑定）。"*

### store 必须写成"工厂函数"（重要纪律）

> **出处**：slot 标准文档 `:64`（逐字）——*"store 里**装什么**是注册方的声明，且**必须写成工厂函数**，使**模块级句柄根本无从存在**（模块级句柄会成为**跨插件重载存活的事实单例**）"*

```ts
// ✅ 出处：slot 标准文档 :64 的代码块（逐字）
export function createChatStore() {
  return defineStore({
    init: () => ({ selection: null as SelectionTarget | null, draft: '' }),
    persist: 'dsh.conversation.chat',
    actions: {
      select:     (d, t: SelectionTarget) => { d.selection = t },
      clearDraft: (d) => { d.draft = '' },
    },
  })
}
```

**为什么必须工厂？** —— 如果是模块级常量：

```ts
// ❌ 危险
export const chatStore = defineStore({...})   // 模块级单例
```

热重载时**新插件实例**会复用**旧模块的单例**——状态"诈尸"。工厂则每次 `create()` 出新实例。

### 一个工厂，三个消费点

> **出处**：slot 标准文档 `:64`（逐字）——*"① `register`——独占 store 直接传工厂；要共享实例，则在 `apply` 里调用一次工厂、把**同一句柄**传给多次 register（**跨插件共享构造性不可能：句柄从不出包**）；② `PropsStore<ReturnType<typeof createChatStore>>` 推导出组件的 store 份额，**零手写成员**；③ 测试自己调用工厂并 `.create()` 出真引擎实例……**生产 outlet 走的正是同一条 `create` 路径，不存在第二套机械**。"*

### 读写接口是"收窄面"

> **出处**：slot 标准文档 `:64`（逐字）——*"**读 = `props.useStore`；写 = 仅 `props.actions.*`**——裸实例（带 `update`/`set`）**永远到不了组件**，声明的 actions 就是**完整且可审计的变更 API**。"*

> **Go 类比**：这就是**"接口收窄"**——组件拿到的是 `Reader` + 少数具名 `Action`，**不是**整个可变 struct。跟**对外暴露 `interface{}` 而非 `*struct`** 是同一条纪律。

**scope 从挂载 entry 推导**：

> **出处**：slot 标准文档 `:64`（逐字）——*"store 的 scope **从挂载 entry 的 scope 推导**（**session slot → 每个会话一个实例**，随会话生灭；**root slot → 每个 entry 一个**）。"*

## 六、inject：注册方通过自己的 ctx 提供业务接口

### inject 工厂的能力边界 = 本插件声明的注入拓扑

> **出处**：slot 标准文档 `:85`（逐字）——*"inject 工厂**只接收其声明所授权的形参**——session slot 获得 `sessionId`，声明了 store 的获得绑定好的 `actions`，否则无参——**取服务一律经 apply 闭包自己的 ctx**，其**能力边界因此就是本插件声明的 `inject` 拓扑**（cordis property proxy 原生生效；**不存在携带更宽 ctx 的装配句柄**）。"*

> **Go 类比**：这就是 **依赖注入 + 最小权限**——工厂签名里**声明的参数就是它能用的全部依赖**，拿不到"全局 ctx 全量门禁卡"。

### 业务面 = 普通数据 + 回调（外加一个保留键 `hooks`）

> **出处**：slot 标准文档 `:85`（逐字）——*"返回值是**普通数据与回调**，至多外加保留键 `hooks` 格：一张**裸 observable source**（getSnapshot+subscribe）表，渲染器**在业务面抵达组件前**把每个 source 绑成 `use<Name>` 选择器钩子……**组件永远收不到裸 source**，业务代码因此仍不包含订阅机制。"*

### 三条"不得"

> **出处**：slot 标准文档 `:85`（逐字）——*"**不得手写钩子，不得生成 ReactNode，也不得传递整个服务对象**——**收窄本身就是价值**：组件能做什么，**恰由工厂返回值的形状圈定**。"*

## 七、数据界线纪律（一张表记住）

这是**全篇最该背下来**的一条：

> **出处**：slot 标准文档 `:89`（逐字）——*"**钩子只许框架造**：`useSession`、`useSessions`、`useWorkspaces`、`useStore`、`renderSlot` **五席**，加上 provide 贡献与 inject `hooks` 格绑出的钩子——全部出自渲染器同一台绑定机械；**业务代码在父子组件之间只传普通数据与回调**……**活数据恰有三条通道**：**父知道的**，作为 owner props 在 renderSlot 现场传入；**只有组件自己知道的**，是本地 state；**需要跨 entry 共享或跨重挂载存活的**，是声明的 store。**派生是对框架钩子数据做纯函数（useMemo），绝不自成一路订阅**。"*

```
活数据的三个合法去处：
  ① 父知道          → owner props（renderSlot 现场传参）
  ② 组件自己知道     → 本地 state
  ③ 要跨 entry/重挂载 → 声明的 store

派生数据（不是"活数据"）：
  → 对框架钩子数据做 useMemo，绝不自成一路订阅
```

> **Go 类比**：这就是**"单一数据源 + 派生即纯函数"**——像 **不要缓存能算出来的东西**（`len(slice)` 不该存个字段）。dsh 把这条纪律写进了架构。

## 八、本篇小结

- **只有一个 API**：`ctx.slots.register(...)`。`children` = **声明 + 授权 + 运行时 spec**（**声明即认领**）。
- **`'root'` 是唯一先验 slot**；渲染器只 `renderSlot('root')` 一次，**无 fallback**，配置错误**装载即炸**。
- **四种 kind**：`single`/`list`/`keyed`/`chain`；`keyed` 是 **owner 点选**，`chain` 是 **entry 自荐**（路由权相反）。
- **props 四份额**（运行时/子渲染/store/业务）**各有唯一真源**，在 `register` 一行上**编译期收口**。
- **store 必须工厂**（防模块级单例诈尸）；**读 `useStore`、写 `actions.*`**，裸实例到不了组件。
- **钩子只许框架造**（5 席）；业务层只传普通数据/回调；**活数据只有三条通道**。

- **下一节**（08.3）看**渲染器怎么写**——slot 的"裸 observable source"是怎么变成 React 组件的 " hooks 的。
