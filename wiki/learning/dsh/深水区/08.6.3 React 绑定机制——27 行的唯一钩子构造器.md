# 08.6.3 React 绑定机制——27 行的"唯一钩子构造器"

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**08.6.1（三层模型）** + **08.6.2（slot 系统）**——本篇是③渲染层的实现细节
> - 核心文件：`packages/client/ui-renderer/src/client/bind.ts`（**全文仅 27 行**）
> - 写法说明：以**读源码 + 讲机制**为主；引号内为源码注释/文档**逐字**

> [!abstract] 本章是什么 / 该记住什么
> **回答的问题**："**dsh 怎么把'没有 React 的数据源'变成'React 组件能订阅的 hooks'？**"
> **答案**：**一个 27 行的函数 `bindSnapshotSelector`**——它把"裸 observable（`getSnapshot`/`subscribe`）"包装成"带 selector 的 uSES 钩子"。
> **读完该记住 6 点**：
> 1. **契约是 `ObservableSnapshot<T>`**：只要满足 `getSnapshot`/`subscribe` 两个方法，**任何对象都是数据源**（Session 对象、store 实例**同构满足**）
> 2. **`bindSnapshotSelector` 是"客户端栈里唯一的钩子构造器"**（源码注释逐字：*"the ONE hook constructor in the client stack"*）
> 3. **绑定发生在 React 侧**——引擎**只产出裸源**（无 selector hook），这是**边界纪律**
> 4. **闭包捕获一次**：`subscribe`/`getSnapshot` 在绑定期被捕获进稳定闭包 → **组件跨渲染不重复订阅**
> 5. **相等性全链一致**：生产端结构共享 → 消费方 `Object.is`/`shallowEqual` 短路 → `React.memo` 浅比较；**深比较全链禁止**
> 6. **uSES 四条约定"按构造成立"**（getSnapshot 恒返缓存引用 / subscribe 是稳定闭包 / 纯 CSR 无 server snapshot / 相等性可配）

## 这一篇在讲什么

08.1 说"③ 渲染层是**唯一**碰 React 的地方"；08.2 说"其他层只产出**裸 observable source**，绝不携带 React 钩子"。

**那么问题来了**：`store` 是 React-free 的，`session-controller` 对象层也是 React-free 的——**它们的数据怎么让 React 组件订阅？**

**答案就在这 27 行里**。本篇把它逐行拆开。

> **Go 类比**：这像 **`http.Handler` 与具体框架的适配层**——核心是"数据源接口"（`ObservableSnapshot`），适配器（`bindSnapshotSelector`）把它接到具体框架（React）。数据源侧**不需要知道 React 存在**，正如 `database/sql` 的 driver **不需要知道调用方是谁**。

## 一、契约：`ObservableSnapshot<T>`（两层都认的"最小接口"）

一切从这个接口开始——**满足它，就是数据源**：

> **出处**：源码 `packages/client/store/src/contract.ts:4-12`（逐字）：

```ts
export interface ObservableSnapshot<T> {
  // ...
  getSnapshot(): T
  /**
   * @returns unsubscribe function.
   */
  subscribe(fn: () => void): () => void
}
```

**两个方法，仅此而已**：
- `getSnapshot()` → 返回**当前快照**（**恒返缓存引用**，见第四节）
- `subscribe(fn)` → 注册变化回调，**返回 unsubscribe**

**谁来满足它？** —— 文档明说**两类对象同构满足**：

> **出处**：`2026-07-19-gui-web-client-architecture.zh.md:78`（逐字）——*"ui-renderer 在绑定处从 React 消费的唯一数据约定合成每个钩子：`ObservableSnapshot<T>`（`getSnapshot`/`subscribe`）——**Session 对象与快照 store 同构满足它**。"*

```
Session 对象（对象层，React-free）  ─┐
                                    ├─► 都满足 ObservableSnapshot<T> ─► bindSnapshotSelector ─► React 钩子
快照 store 实例（状态层，React-free） ─┘
```

> **出处**：`2026-07-19-gui-web-client-architecture.zh.md:51` 也说 Session ——*"`implements ObservableSnapshot<ConversationSnapshot>`，构造时挂 `useSelector = bindSnapshotSelector(this)`，**Session 本身就是 uSES 源**"*。

> **Go 类比**：这就是 **Go 的"隐式接口"**——`Session` 和 `store` **没有共同基类**，但**都"长着" `getSnapshot`/`subscribe` 两个方法**，于是都能当数据源。等价于"`io.Reader` 只有一个 `Read`，但 `*os.File`/`*bytes.Buffer`/`net.Conn` 都满足它"。

## 二、`bindSnapshotSelector`：全栈唯一的钩子构造器

读源码**全文**（27 行）：

> **出处**：`packages/client/ui-renderer/src/client/bind.ts:1-27`（**逐字全录**）：

```ts
/**
 * uSES bridge: turns any bare observable snapshot source into a typed
 * selector hook. Client-side-rendered only, so no server snapshot is wired.
 * This is the ONE hook constructor in the client stack — engines and hosts
 * traffic in bare sources; binding happens on the React side.
 */
import { useSyncExternalStoreWithSelector } from 'use-sync-external-store/shim/with-selector'
import type { HostObservable, SnapshotSelectorHook } from '@deepseek-ai/dsh-client-ui-slots'

export function bindSnapshotSelector<T>(w: HostObservable<T>): SnapshotSelectorHook<T> {
  const subscribe = (fn: () => void) => w.subscribe(fn)
  const getSnapshot = () => w.getSnapshot()
  return function useSelector<S>(sel: (s: T) => S, eq?: (a: S, b: S) => boolean): S {
    return useSyncExternalStoreWithSelector(subscribe, getSnapshot, undefined, sel, eq)
  }
}
```

### 逐行解读

| 行 | 做什么 | 为什么 |
| --- | --- | --- |
| `subscribe = (fn) => w.subscribe(fn)` | **捕获源一次**进闭包 | 让 `subscribe` 引用**永稳**（uSES 要求） |
| `getSnapshot = () => w.getSnapshot()` | 同上 | 重绑 `this`（方法式源的 `this` 会丢） |
| `return function useSelector(sel, eq)` | 返回"**带 selector 的钩子**" | 组件拿到的是个规范 hook |
| `useSyncExternalStoreWithSelector(subscribe, getSnapshot, undefined, sel, eq)` | 真正订阅 | `undefined` = **不传 server snapshot**（纯 CSR） |

### 三个关键点（源码注释逐字）

**① 全栈唯一的钩子构造器**：

> **出处**：`bind.ts:4-5`（逐字注释）——*"This is **the ONE hook constructor in the client stack** — engines and hosts traffic in **bare sources**; **binding happens on the React side**."*

**翻译**：`store` 引擎和各大 host **只搬运"裸源"**；**绑定只在 React 侧发生**。这是 08.1 那条"边界纪律"的**代码实现**。

**② 闭包捕获一次 → 组件永不重复订阅**：

> **出处**：`bind.ts:15-17`（逐字注释）——*"subscribe/getSnapshot are **captured once per source into stable closures** (also **re-binds `this`** for method-based sources), so **components never resubscribe across renders**. Equality defaults to `Object.is`."*

**为什么这很重要？** —— 如果每次渲染都 `w.subscribe(fn)` 建新函数，React 会认为"订阅变了"，**每次渲染都退订重订**。`bind.ts` 用闭包把 `subscribe` 引用**锁死**，从根上杜绝。

**③ 无 server snapshot**：

> **出处**：`bind.ts:2-3`（逐字注释）——*"**Client-side-rendered only, so no server snapshot is wired**."*
> 对应源码 `bind.ts:25` 的第三个参数 `undefined`。

**含义**：dsh Web UI **不做 SSR**（纯客户端渲染），所以 uSES 的"server snapshot"参数传 `undefined`。

## 三、uSES 桥：为什么用 `use-sync-external-store` 而不是手写

`bind.ts:10` 引入的是：

```ts
import { useSyncExternalStoreWithSelector } from 'use-sync-external-store/shim/with-selector'
```

**这不等于 React 自带的 `useSyncExternalStore`**——它是 **`with-selector` 版本**，多两个参数（`selector` + `equalityFn`）：

```
useSyncExternalStore(subscribe, getSnapshot)                  ← 原版：全量快照
useSyncExternalStoreWithSelector(subscribe, getSnapshot,      ← with-selector：可选
                                 undefined, sel, eq)             只订阅"选出来的那部分"
```

**为什么要 `with-selector`？** —— 让组件**只订阅它关心的切片**：

```ts
// 组件只关心 selection 这一段
const selection = props.useStore(s => s.selection)
//            ↑ 只有 selection 变了才重渲染；draft 变了不打扰它
```

> **⚠️ 注意**：selector 返回**派生值**时，`eq` 要配好——否则每次都造新对象 → 引用变 → 重渲染。这正是 08.2 讲 chain `select` 时说的*"选择器只做路由，绝不创建新对象"*的同一条纪律。

## 四、uSES 四条约定"按构造成立"

文档明确说，这套约定是**靠设计保证**的（不是"祈祷调用方遵守"）：

> **出处**：`2026-07-19-gui-web-client-architecture.zh.md:78`（逐字）——*"uSES 约定**四条按构造成立**：**getSnapshot 恒返缓存引用**；**subscribe 是绑定期闭包（引用永稳）**；**纯 CSR 不传 server snapshot**；**相等性缺省 `Object.is`，按调用可选 `shallowEqual`**。"*

逐条对回代码：

| 约定 | 代码保证 |
| --- | --- |
| `getSnapshot` 恒返**缓存引用** | 源侧实现（`store` 引擎/`Session` 都缓存快照——见 08.1 的"引用纪律"） |
| `subscribe` 是**绑定期闭包** | `bind.ts:22` —— `const subscribe = (fn) => w.subscribe(fn)`（**引用永稳**） |
| **纯 CSR** 无 server snapshot | `bind.ts:25` —— 第三参 `undefined` |
| 相等性缺省 **`Object.is`** | `bind.ts:17` 注释 + uSES 默认 + `eq` 可选传入 |

### "相等性协议，全链一致"（最该记住的一条工程纪律）

> **出处**：`2026-07-19-gui-web-client-architecture.zh.md:80`（逐字）——*"**相等性协议，全链一致**：**生产端结构共享**；**消费方以 `Object.is` 或 `shallowEqual` 短路**；**`React.memo` 浅比较**。**深比较全链禁止**。"*

```
生产端（store/session）  →  结构共享（未变的子树保持引用）
消费方（钩子 selector）   →  Object.is / shallowEqual 短路
组件（React.memo）        →  浅比较
─────────────────────────────────────────────
深比较                    →  ❌ 全链禁止
```

> **Go 类比**：这就是**"用指针相等替代深比较"**——像比较两个 `*T` 是否同源（`p == q`）而不是逐字段比。**深比较是性能杀手**，dsh 直接从架构上禁掉。

**为什么"结构共享 + 引用相等"能成立？** —— 因为"**引用纪律**"：

> **出处**：`2026-07-19-gui-web-client-architecture.zh.md:51`（逐字，讲 ConversationSnapshot）——*"**引用纪律**（memo 与 uSES 的前提）：**未变化的子结构和 Node value 保持引用**；**单个业务更新只替换对应 key 的 value**，除非它的顺序或 Location 发生变化。"*

## 五、`createSlotRenderer` 与 `mountApp`：绑定发生在哪

`bindSnapshotSelector` 是**零件**，真正"接线"的地方在 `createSlotRenderer` 与 `mount`：

> **出处**：`packages/client/ui-renderer/README.zh.md:44`（逐字）——*"`createSlotRenderer` 把 slot 注册表连接到 React：**条目列表成为响应式 source**，每个 outlet 经已安装的渲染器渲染。业务插件通过带类型的 slot `hooks` **传递裸 observable source**；渲染器经 **uSES 适配器在 outlet 处完成绑定**。"*

**"绑定发生在 outlet 处"** 是核心：

```
register(..., Component)                 ← 插件只声明组件 + 传"裸源"
        │
        ▼
   slot outlet（渲染器）
        │  在这里做 bindSnapshotSelector(裸源)
        ▼
   Component(props)                       ← 组件拿到的是"钩子"，不是"裸源"
```

> **出处**：源码 `packages/client/ui-renderer/src/client/bindings.tsx:60`（逐字）—— `hook = bindSnapshotSelector(source)`（**真的在这里调**）
> **出处**：源码 `packages/client/ui-renderer/src/client/scoped-slots.tsx:939` —— `export function createSlotRenderer(): SlotRenderer`

### `mount(container)` 的完整职责

> **出处**：`packages/client/ui-renderer/README.zh.md:32`（逐字）——*"`mount(container)` 会**安装 slot 渲染器**、在存在时 **hydrate 现有启动 DOM**、在下一次绘制前把组装后的应用**渲染进容器**，并返回一个**卸载 React 根的 disposer**。"*

**`mount` 做四件事**：

1. `ctx.slots.install(createSlotRenderer())` —— 安装渲染器（**双重安装 throw**）
2. **hydrate** 启动 DOM（如果有 `[data-dsh-boot]`）—— 见下
3. 渲染组装后的应用进容器
4. 返回 **disposer**（卸载 React 根）

### Boot DOM 的"单帧透传"（一个精致的细节）

> **出处**：`packages/client/ui-renderer/README.zh.md:44`（逐字）——*"`mountApp` 会查找启动内核的 `[data-dsh-boot]` 元素：存在时经 **`BootHandoff`（一个保留加载 DOM 的单帧透传）** hydrate，否则创建全新的根节点并同步提交渲染。"*

**为什么要 `BootHandoff`？** —— dsh 启动时先显示**不依赖框架的 loading 页**，等插件全部 ACTIVE 后**一次切换**到真 UI：

> **出处**：`2026-07-23-client-plugin-loading-model.zh.md:69`（逐字）——*"不依赖框架的 loading 页经 `internal/status` 投影真实 fiber 状态。检查完成后，内核调用 `ctx.uiRenderer.mount(container)`，**一次切换到真实 UI**。"*

`BootHandoff` 保证：**加载 DOM 保留到"下一帧绘制前"**——用户**看不到白屏闪烁**。

## 六、一张图总结"数据怎么流到组件"

```
① store 实例 / Session 对象       （React-free，满足 ObservableSnapshot<T>）
        │
        │  裸源：getSnapshot() / subscribe(fn)
        ▼
② inject 的 hooks 格 / provide 通道 （只是"搬运裸源"，不做绑定）
        │
        │  slot props（业务份额）传递裸源
        ▼
③ slot outlet（渲染器内部）
        │
        │  bindSnapshotSelector(source)  ← 唯一钩子构造器
        ▼
④ 组件收到的 props.useXxx(selector)  （带 selector 的 uSES 钩子）
        │
        │  组件只管用，永不重复订阅
        ▼
   React 渲染 / 重渲染（结构共享 + 引用相等 → 精准）
```

> **Go 类比**：像**"驱动注册（裸接口）→ 连接池适配 → 业务拿到 `*sql.DB`"**——业务代码**从不接触底层 socket**，正如组件**从不接触裸源**。

## 七、本篇小结

- **契约是 `ObservableSnapshot<T>`**（`getSnapshot` + `subscribe`）——`Session` 与 `store` **同构满足**，靠的是 **Go 式隐式接口**。
- **`bindSnapshotSelector` 是全栈唯一的钩子构造器**（`bind.ts` 27 行）——**引擎搬运裸源，绑定只在 React 侧**。
- **闭包捕获一次** → 组件跨渲染**不重复订阅**（`subscribe` 引用永稳）。
- **纯 CSR**，不传 server snapshot；**相等性缺省 `Object.is`**，可选 `shallowEqual`。
- **相等性协议全链一致**：生产端结构共享 → 消费方短路 → `React.memo` 浅比较；**深比较全链禁止**。
- **uSES 四条约定"按构造成立"**，不靠调用方自觉。
- **`mount`** 做四件事（装渲染器/hydrate/渲染/返回 disposer）；**`BootHandoff`** 消除白屏闪烁。
