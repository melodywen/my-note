# 09.2 Cordis 骨架——一个 16 行启动器 + 一份配置

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**09.1（四块内核）** + **阶段一（Cordis 内核七讲）**
> - 本篇对象：**想搞懂"dsh 是怎么启动起来"的后端**

> [!abstract] 读完该记住 4 点
> 1. **dsh 的启动器只有 16 行**——`new Context()` → `plugin(Loader)` → `loader.create(include cordis.yml)`
> 2. **配置即插件树**——`cordis.yml` 决定"挂哪些插件"，**代码里不写死任何插件**
> 3. **配置文件条目有 `id` / `name` / `config` / `disabled`** 等元数据
> 4. **mini-dsh 复刻这个骨架**——不发明新东西，**照官方的样子来**

## 一、先看真相：dsh 的启动器长什么样

**整个 dsh 的启动器，就 16 行**（出处：`vendor/cordis/bin.js`，**逐字全文**）：

```js
#!/usr/bin/env node

import { Context } from '@deepseek-ai/cordis'
import { pathToFileURL } from 'node:url'
import Loader from '@deepseek-ai/cordis-plugin-loader'

const ctx = new Context()
ctx.baseUrl = pathToFileURL(process.cwd()).href + '/'

await ctx.plugin(Loader)
await ctx.loader.create({
  name: '@deepseek-ai/cordis-plugin-include',
  config: {
    path: './cordis.yml',
  },
})
```

**逐行读**：

| 行 | 做什么 |
| --- | --- |
| `new Context()` | 创建**根上下文**（所有插件的挂载点） |
| `ctx.baseUrl = ...` | 告诉 Cordis "相对路径以当前目录为基准" |
| `ctx.plugin(Loader)` | 挂载**加载器插件**（Loader） |
| `ctx.loader.create({ name: include, config: { path: './cordis.yml' } })` | 让 Loader 读 `cordis.yml`，**按配置挂载其余所有插件** |

> **出处**：`docs/cordis-tutorial/index.zh.md`「准备工作」（逐字）——*"这个单文件启动器会创建根 `Context`、挂载 Loader 插件，并让它从当前目录加载 `./cordis.yml`。**其余所有内容，包括有哪些插件以及如何配置它们，都来自你稍后将编写的 YAML 文件。**"*

> **Go 类比**：这像**一个只做"读配置 + 起服务"的 `main.go`**：
> ```go
> func main() {
>     cfg := loadConfig("./config.yaml")   // ← 相当于 loader 读 cordis.yml
>     app := newApp(cfg)                    // ← 相当于按配置挂载插件
>     app.Run()
> }
> ```
> **要点**：**`main` 里不写业务**——业务全在配置 + 插件里。**这正是"一切皆插件"的入口体现**。

## 二、配置即插件树

**`cordis.yml` 是一个数组**，每一项是一个"插件条目"。看官方 tutorial 的真实例子（出处：`docs/cordis-tutorial/06-composition-and-hmr.zh.md`，逐字）：

```yaml
- id: logger
  name: '@deepseek-ai/cordis-plugin-logger-console'
- id: timer
  name: '@deepseek-ai/cordis-plugin-timer'
- id: hmr
  name: '@deepseek-ai/cordis-plugin-hmr'
  config:
    root: ['.']
- id: hello
  name: './hello.ts'
```

**每个条目四个常见字段**（出处：同上 + `docs/cordis-primer.zh.md`）：

| 字段 | 含义 | Go 类比 |
| --- | --- | --- |
| `name` | **模块路径**（相对路径 / 包名）——从哪加载插件 | `import "..."` |
| `id` | **稳定标识**——Loader 靠它区分"改这个条目"还是"删了再加" | 配置项的 key |
| `config` | **传给插件的配置**（会按插件的 schema 校验） | 配置结构体 |
| `disabled` | **保留条目但不挂载**（改回来即恢复） | 注释掉 / feature flag |

> **⚠️ 一个重要限制（我造 mini-dsh 时验证过）**：`name` **只接受模块路径**——**不支持 `#具名导出` 语法**。
> 出处：`cordis-plugin-loader` 的 `import(name)` 实现（`vendor/cordis` 同款）——它把 `name` 当**模块说明符**去 `import()`。
> **后果**：一个文件里如果要暴露多个插件，**不能靠 `name: './x.ts#someExport'`**——得**拆成多个文件**，或让一个文件的 `apply` 里 `ctx.plugin(...)` 挂子插件。

**"配置即插件树"的含义**：

```
cordis.yml
├── logger   （控制台日志插件）
├── timer    （定时器插件）
├── hmr      （热重载插件）
└── hello    （你的插件）
```

**没有这行 yml，这些插件一个都不会加载**——**加载什么，完全由配置决定**。

> **Go 类比**：像**依赖注入容器的配置文件**——**容器里有什么，取决于配置，不取决于代码**。

## 三、插件的三种写法（你会在 dsh 里看到）

**Cordis 插件 = 一个"能挂到 ctx 上"的东西**，有几种形态（出处：`docs/cordis-tutorial/01-first-plugin.zh.md` + `02-lifecycle-and-effects.zh.md`）：

### 形态 1：函数式（最常见）

```ts
import type { Context } from '@deepseek-ai/cordis'
export const name = 'hello'
export function apply(ctx: Context): void {
  console.log('hello from my first plugin')
}
```

**读法**：导出 `name`（插件名）+ `apply`（挂载时执行）。

### 形态 2：Service 类（提供服务时）

```ts
// 出处：docs/cordis-tutorial/03-services.zh.md（逐字）
export class GreeterService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'greeter')          // ← 以名称 'greeter' 注册到 ctx
  }
  greet(who: string) { return `Hello, ${who}!` }
}
export function apply(ctx: Context) {
  ctx.plugin(GreeterService)       // ← 挂载这个服务
}
```

### 形态 3：带 `inject` 的消费方

```ts
export const name = 'consumer'
export const inject = ['greeter']   // ← 声明依赖：等 greeter 就绪才启动
export function apply(ctx: Context) {
  console.log(ctx.greeter.greet('world'))
}
```

> **出处**：同文件（逐字）——*"`inject` 列出该插件需要的服务。Cordis 会让插件保持 **PENDING**，直到列出的每项服务都存在……**`cordis.yml` 中的加载顺序无关紧要：决定插件何时启动的是依赖关系，而不是文件顺序。**"*

> **Go 类比**：`inject` = **显式声明依赖**。像你写 `NewServer(db, cache)`——**依赖没就绪就不启动**，而不是"按代码顺序碰运气"。

## 四、mini-dsh 的骨架 = 复刻官方

**mini-dsh 不发明新东西**——**照官方的 16 行来**（出处：`vendor/cordis/bin.js`）。

**唯一的差异**：官方的启动器 import 的是 `vendor/cordis` 里的包；**mini-dsh 在 `dsh-learn` 里**，所以**通过软链复用全局 dsh 的 Cordis 包**（`node_modules/@deepseek-ai/*` → 全局 dsh 的同名包）。

> **⚠️ 实测坑（我踩过）**：
> - `vendor/cordis/lib/` **没有编译好的 JS**（只有 `types/`）——**直接跑会报 `Cannot find module .../vendor/cordis/lib/index.js`**。
> - **可行做法**：用**全局 dsh 安装里的已编译 Cordis**（`~/.nvm/.../dsh/node_modules/@deepseek-ai/cordis/lib/index.js`），在 mini-dsh 里软链过去。
> - 出处：`packages/client/README.zh.md` 等处的插件也用过同样的软链手法。

**mini-dsh 的骨架文件**：

```
mini-dsh/
├── boot.mjs          ← 复刻那 16 行（改用本地软链的 cordis）
├── cordis.yml        ← 插件树：session → tools → echo → mock-llm → loop
└── src/*.ts          ← 五个插件（对应四块内核）
```

**`cordis.yml`（插件树）**：

```yaml
- name: './src/session.ts'    # ④ 会话（先挂，因为别人依赖它）
- name: './src/tools.ts'      # ② 工具服务
- name: './src/echo.ts'       # ② 工具（消费 tools）
- name: './src/mock-llm.ts'   # ③ 假模型
- name: './src/loop.ts'       # ① 循环（消费上面三个）
```

> **注意**：**顺序无关紧要**（Cordis 按依赖启动，不按文件顺序）——上面只是**方便阅读**才按依赖排。

> **出处**：`docs/cordis-tutorial/03-services.zh.md`（逐字）——*"交换 `cordis.yml` 中两行的顺序后重新运行，输出仍然相同。"*
