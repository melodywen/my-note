# 10.1 为什么需要"远程调用"——Host 与 Client 是两个进程

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**08.1（浏览器/服务器边界）** + **10.0（本章地图）**
> - 本篇对象：**后端**（这一篇几乎全是你的主场）

> [!abstract] 读完该记住 4 点
> 1. **Host 和 Client 是两个进程、两台机器**——**不能直接函数调用**
> 2. **跨进程调用 = "把请求序列化 → 通过网络发 → 对面反序列化 → 执行 → 把结果原路返回"**
> 3. dsh 的**分层**：`api/remotes → gateway → connection → webserver`
> 4. **Typert 的价值**：让"跨进程调用"写起来**像本地函数调用一样**

## 一、先划清边界：谁是 Host，谁是 Client

dsh 的 Web 场景，**两个进程**：

```
┌─────────────────────┐                ┌─────────────────────┐
│   Client（浏览器）   │                │   Host（Node 进程）  │
│                     │  ←── 网络 ──►   │                     │
│  显示界面            │                │  跑 agent / 工具     │
│  响应用户点击        │                │  读写文件 / 调模型    │
│  ❌ 不能直接读文件    │                │  ✅ 拥有全部权威状态  │
└─────────────────────┘                └─────────────────────┘
```

> **出处**：`docs/subsystems/web-client.zh.md:9`「分层与所有权」（逐字）——*"**Host 应用**……拥有**权威状态、持久化、mutation 顺序、访问策略与 stream 生产**。"*

**关键**：**Host 是"唯一真相源"（single source of truth）**。Client 只是个"显示器 + 遥控器"。

> **Go 类比**：**这就是你天天写的"服务端 + 客户端"**——服务端拥有数据库（真相），客户端只是调 API 展示。**一模一样**。

---

## 二、为什么不能"直接函数调用"

**浏览器里有段代码，想读一个文件。它能不能直接写：**

```ts
const content = readFile('/path/to/file')   // ❌ 不可能
```

**不能。** 因为：

| 障碍 | 说明 |
| --- | --- |
| **进程隔离** | 浏览器和 Node 是**两个进程**，内存不共享 |
| **可能不同机器** | Host 可能在远程服务器上 |
| **安全** | 浏览器**不可信**——不能让它随便读服务器文件 |
| **语言/运行时不同** | 浏览器 JS 环境 ≠ Node 环境 |

**所以必须"远程调用"**：

```
Client 想读文件：
  ① 把"我要读文件 /path/to/file"序列化成一个消息
  ② 通过网络发出去
  ③ Host 收到 → 反序列化 → 真的读文件
  ④ 把文件内容序列化 → 发回来
  ⑤ Client 收到 → 拿到内容
```

**这一套 = "远程过程调用"（RPC, Remote Procedure Call）**。

> **Go 类比**：**这就是 gRPC 解决的问题**——你不能"直接调远程方法"，只能"序列化参数 → 发 → 对面执行 → 返回"。**dsh 的 Typert 就是它自己的 RPC 方案**。

## 三、dsh 的远程调用分了几层

> **出处**：`docs/api-gateway.zh.md`「边界」（逐字）——*"API 各层按 `remotes → gateway → connection → webserver` 组织。"*

```
remotes      选哪些能力暴露 + 每次调用怎么到达正确的会话
   ↓
gateway      在 Client 与 Host 之间承载调用及其结果（dispatch / 校验 / 取消）
   ↓
connection   物理载体（HTTP POST / WebSocket）、信任边界、请求关联
   ↓
webserver    node:http 服务器（收包的第一站）
```

> **出处**：`packages/api/README.zh.md`（逐字）——*"`remotes` 决定暴露哪些能力、以及每次调用如何到达正确会话的 agent；`gateway` 在 Client 与 Host 之间承载调用及其结果。"*

**逐层看**：

| 层 | 包 | 职责 | 后端类比 |
| --- | --- | --- | --- |
| **remotes** | `api/remotes` | **选**哪些方法对外、路由到正确会话 | API 网关的**路由表** |
| **gateway** | `api/gateway` | **dispatch**：解析参数、调服务、校验返回值、取消 | RPC **框架**（gRPC server） |
| **connection** | `client/connection` | **物理传输**：HTTP/WS、信任校验、请求关联 | **TCP/TLS + 中间件** |
| **webserver** | `host/webserver` | `node:http` 服务器 | `net/http` |

> **出处**：`packages/api/gateway/README.zh.md`（逐字）——*"为 Host 与 Client 两侧的 Cordis 环境提供 Typert RPC endpoint。Host 入口提供 `ctx.typertGateway`，`@deepseek-ai/dsh-api-gateway/client` 则提供 `ctx.remote`；两者使用**同一份生成的 `InvocationDescriptor` 约定**。"*

> **Go 类比**：**`webserver` ≈ `net/http`；`connection` ≈ 你的中间件栈（认证/限流）；`gateway` ≈ 你手写的 handler 分发；`remotes` ≈ 路由注册表**。**分层逻辑跟你的 HTTP 服务完全一致**。

## 四、Typert 的价值：把"远程"写得像"本地"

**没有 Typert**，暴露一个方法要干一堆活（手写序列化、分发、校验……）：

```ts
// 假想的"手写版"
ctx.webserver.route('POST', '/api/goals/create', async (req) => {
  const body = JSON.parse(req.body)
  const agent = agents.get(body.agentId)          // 手动把 id 还原成对象
  validate(body, goalSchema)                       // 手动校验
  const result = goalService.create(agent, body.request)
  return JSON.stringify(result)                    // 手动序列化
})
```

**有了 Typert**，你只写业务方法 + 一个标记：

```ts
// 出处：docs/api-gateway.zh.md（逐字示例）
export class GoalService extends TypertRemoteService {
  constructor(ctx: Context) { super(ctx, 'goals') }

  @Remote('create')
  createForClient(agent: Agent, request: CreateGoalRequest, signal: AbortSignal): CreateGoalResult {
    signal.throwIfAborted()
    return this.create(agent, request)
  }
}
```

**剩下的——序列化、分发、id→对象解析、校验、取消——全自动**。

> **出处**：`docs/api-gateway.zh.md`（逐字）——*"复杂 Host 对象不能直接跨 wire 传输；业务包必须通过 `TypertLookupMap` 声明它与 wire identity 的关联……例如 `Agent` 参数在 Host 签名中名为 `agent`，**生成的 wire 字段为 `agentId`**，Gateway 在调用业务方法前**将 id 解析为 Host 对象**。"*

> **Go 类比**：**就是 protobuf + gRPC**——你写 `.proto`（≈ `@Remote` 标记），工具生成 stub（≈ `ctx.remote.*`）。**但 dsh 更激进：不写 IDL 文件，直接在 TS 方法上打标记**，构建期用 TypeScript 编译器分析签名。

## 五、一个完整的调用旅程（先建立全景）

**一次 `await ctx.remote.goals.create(agentId, {...})`，背后发生了什么**：

```
Client 浏览器
  ① 调 ctx.remote.goals.create(agentId, request)
  ② 生成 descriptor → 序列化 args（agentId + request）→ 编成 HTTP POST
       │
       ▼ 网络（/api）
Host 进程
  ③ connection 解码 carrier + 信任校验（Host/Origin）
  ④ gateway 收到：解析 agentId → 真正解析成 Agent 对象（Lookup）
  ⑤ gateway 调 GoalService.createForClient(agent, request, signal)
  ⑥ 校验返回值 → 序列化结果
       │
       ▼ 网络
Client 浏览器
  ⑦ 解包 → 返回给调用方
```

**记住这条链**——后面 10.2~10.4 就是把每一环拆开讲。

> **Go 类比**：**跟你排查一个 API 请求的路径完全一样**——客户端 → 网关 → 鉴权中间件 → handler → 返回。**只是这里多了一个"id → 对象"的解析步骤（Lookup），因为你传的不是对象而是 id**。

## 自测

1. 为什么 Client 不能直接调 Host 的函数？（→ 两个进程/可能两台机器/安全/不同运行时）
2. dsh 的远程调用分了哪四层？（→ remotes → gateway → connection → webserver）
3. Typert 把什么"自动化"了？（→ 序列化、分发、id→对象解析、校验、取消）
4. Typert 和 gRPC 最大的不同？（→ 不写 IDL/proto，直接在 TS 方法上打标记，构建期分析）
5. `Agent` 参数在 wire 上变成了什么？（→ `agentId`——对象不能过 wire）

**都能答上** → 进 **10.2 Typert 协议**。
