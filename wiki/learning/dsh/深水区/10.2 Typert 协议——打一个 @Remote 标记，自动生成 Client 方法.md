# 10.2 Typert 协议——打一个 @Remote 标记，自动生成 Client 方法

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**10.1（为什么需要远程调用）**
> - 权威文档：`docs/api-gateway.zh.md` + `docs/subsystems/typert.zh.md`
> - 本篇对象：**熟悉 gRPC / OpenAPI 的后端**

> [!abstract] 读完该记住 6 点
> 1. **`@Remote`**：暴露"根 Context 上的 Host 服务方法"
> 2. **`@RemoteScope`**：暴露"某个作用域 Context 上的方法"（如某会话上下文）
> 3. **Lookup**：复杂 Host 对象过不了 wire → **wire 上只传 id**，Gateway 调前解析回对象
> 4. **InvocationDescriptor 不是 wire message**——请求只发 `namespace` + `method` + `args`
> 5. **取消是带外的**——`AbortSignal` 不进 `args`（像 gRPC 的 `ctx`）
> 6. **严格生成**：构建期用 TypeScript 编译器分析签名 → 生成 descriptor + codec

## 一、两种标记：`@Remote` vs `@RemoteScope`

> **出处**：`docs/api-gateway.zh.md`「编程模型」（逐字）——*"`@Remote` 表示调用**根 Host Context** 中注册的 Cordis 服务。……`@RemoteScope(key)` 表示**先通过 `ctx.typert.contexts` 把 identity 解析为一个作用域 Context**，再从该 Context 取得服务并调用方法。"*

| 标记 | 调用目标 | 何时用 |
| --- | --- | --- |
| `@Remote` | **根 Context 上的服务** | 方法需要一个 Host 对象（如 `Agent`）当参数 |
| `@RemoteScope(key)` | **先解析出作用域 Context，再从它取服务** | 方法**依赖作用域组合**，不需要显式传对象（如"当前 agent 的目标"） |

> **Go 类比**：
> - `@Remote` ≈ **`Service.Create(ctx, agent, req)`**——你显式传对象
> - `@RemoteScope` ≈ **从 `ctx` 里直接拿当前会话**（像 `middleware` 已经帮你把 `ctx` 装好了）

## 二、一个完整的 Host 侧例子（官方逐字）

> **出处**：`docs/api-gateway.zh.md`（逐字）：

```ts
import type { Agent } from '@deepseek-ai/dsh-agent'
import { TypertRemoteService, Remote, RemoteScope } from '@deepseek-ai/dsh-typert-protocol'
import type { Context } from '@deepseek-ai/cordis'

export interface CreateGoalRequest { objective: string }
export interface CreateGoalResult { accepted: boolean }

export class GoalService extends TypertRemoteService {
  constructor(ctx: Context) {
    super(ctx, 'goals')                  // ← Cordis 服务 key = 'goals'
  }

  @Remote('create')
  createForClient(
    agent: Agent,
    request: CreateGoalRequest,
    signal: AbortSignal,
  ): CreateGoalResult {
    signal.throwIfAborted()
    return this.create(agent, request)
  }

  @RemoteScope('agent', 'current')
  currentForClient(): CreateGoalResult {
    return { accepted: true }
  }
}
```

**逐条读**：

| 代码 | 含义 |
| --- | --- |
| `extends TypertRemoteService` | 继承基类 → **Cordis 服务 key 与默认 Remote namespace 绑定** |
| `super(ctx, 'goals')` | 服务名 `goals` → Client 端访问路径 `ctx.remote.goals.*` |
| `@Remote('create')` | 暴露为 Client 方法 `create`（**注意：Host 方法叫 `createForClient`，暴露名是 `create`**） |
| `agent: Agent` | **Host 对象参数**——wire 上会是 `agentId`（见第四节） |
| `signal: AbortSignal` | **取消信号**——最后一个参数，**不进 args** |
| `@RemoteScope('agent', 'current')` | 作用域调用：先解析出 agent context，再取 `current` |

**另一种绑定方式**（已有其他基类的服务）：

> **出处**：同上（逐字）——*"已有其他基类的服务可以改为声明 `readonly typertRemote = bindTypertRemote(this, serviceKey)`"*

> **出处**：源码 `packages/typert/protocol/src/index.ts:153`（逐字）——`export abstract class TypertRemoteService<out T = never> extends Service<T>`

## 三、Client 端调用（生成出来的方法）

> **出处**：`docs/api-gateway.zh.md`（逐字）：

```ts
import type {} from '@deepseek-ai/dsh-api-remotes/client'

export const inject = ['remote', 'remote.goals']   // ← 声明依赖这个 namespace

await ctx.remote.goals.create(agentId, { objective: 'ship it' })
await agentCtx.remote.goals.create({ objective: 'ship it' })   // 作用域调用
```

**两个调用点**：

| 调用 | 场景 | 参数 |
| --- | --- | --- |
| `ctx.remote.goals.create(agentId, {...})` | **直接调用**（根 Context） | 要传 `agentId` |
| `agentCtx.remote.goals.create({...})` | **作用域调用** | **不用传 agentId**（已在 context 里） |

> **出处**：同上（逐字）——*"当一个 `@Remote` 方法恰好有一个 lookup 参数、且同名 `TypertContextMap` 使用相同 wire identity 时，**生成的作用域签名会省略该 identity 参数**。"*

**关键设计**（出处：同上，逐字）：

- *"Client 使用**普通对象上的具体函数，不使用 JavaScript Proxy**"* ← 性能/可调试性
- *"每个 namespace 都是注册为 `remote.<namespace>` 的**可追踪 Cordis 子服务**"*
- *"**依赖声明归实际调用方所有**"* ← 谁调用谁声明 `inject`

> **Go 类比**：**生成的 `ctx.remote.goals` ≈ gRPC 生成的 `GoalsClient`**——一堆具体方法，不是魔法代理。

## 四、Lookup：复杂对象过不了 wire（最精髓）

**问题**：`Agent` 是个复杂的 Host 对象（带方法、状态），**不能直接塞进 JSON 发到浏览器**。

**解法**：**wire 上只传 id，Dashboard/Gateway 调前解析回对象**。

> **出处**：`docs/api-gateway.zh.md`（逐字）——*"复杂 Host 对象**不能直接跨 wire 传输**；业务包必须通过 `TypertLookupMap` 声明它与 wire identity 的关联，并在运行时向 `ctx.typert.lookups` 注册默认解析提供方。例如 `Agent` 参数在 Host 签名中名为 `agent`，**生成的 wire 字段为 `agentId`**，Gateway 在调用业务方法前**将 id 解析为 Host 对象**。"*

```
Host 方法签名：  createForClient(agent: Agent, ...)
                          │
                     构建期转换
                          ▼
wire 字段：      { agentId: "sess-123", request: {...} }
                          │
                   Gateway 调用前
                          ▼
真实调用：       createForClient(解析回的 Agent 对象, ...)
```

**Lookup 声明的形状**：

> **出处**：`docs/subsystems/typert.zh.md`「Lookup 与上下文声明」（逐字）：

```ts
interface TypertLookupDefinition {
  readonly key: string              // 声明的 lookup key
  readonly parameter: string        // Host 签名里的参数名（如 'agent'）
  readonly wire: string             // 替换 Host 对象的 wire 字段（如 'agentId'）
  readonly hostTypeSymbol: string   // Host 类型 symbol
  readonly wireTypeSymbol: string   // wire 类型 symbol
}
```

**Lookup 的关键特性**（出处：同上，逐字）：

- *"lookup 的 resolver 卸载后，注册表仍会保留其 wire 声明"* ← **声明是稳定的**，即使解析器没了，也知道"这个参数是 lookup"
- *"Host 组合可以用 `ctx.typert.lookups.configure()` **覆盖某个 lookup key 的解析策略**，而不改变业务包拥有的参数名、wire 字段或规范类型 symbol"* ← **策略可换，签名不变**

> **Go 类比**：**这就是"对象引用序列化"**——你不能把内存里的指针发过去，只能发一个 id，对面拿 id 查表还原。**跟 ORM 的 `foreign key` 一个道理**：数据库里存 `user_id`，不存整个 user 对象。

## 五、InvocationDescriptor：本地反射，不是 wire

**容易误解的点**：

> **出处**：`docs/subsystems/typert.zh.md`「调用 descriptor」（逐字）——*"`InvocationDescriptor` 是**本地反射信息，不是 wire message**。Host 与消费方构建会生成彼此对应的 descriptor；**请求只发送 endpoint 与具名 `args`**。"*

```
descriptor（本地）：  描述"这个方法的参数/类型/编解码器"
         ✗  不发到网上
wire 请求：           { namespace: 'goals', method: 'create', args: { agentId, request } }
         ✓  只有这个发出去
```

**取消是带外的**（出处：同上，逐字）——*"取消通过**带外 carrier signal** 表达：它在业务参数之后注入，**绝不进入 `args`**。"*

> **Go 类比**：**descriptor ≈ 你编译期生成的 `.pb.go` 里的类型信息**（本地）；**wire 请求 ≈ 实际发的 protobuf 字节**。**取消 signal ≈ gRPC 的 `context.Context`**——**带外**（不占你的业务参数）。

## 六、请求长什么样（wire 格式）

> **出处**：`docs/subsystems/typert.zh.md`「Host Gateway」（逐字）：

```ts
interface InvokeRemoteRequest {
  readonly namespace: string                          // 生成的 descriptor 选的 namespace
  readonly method: string                             // 服务方法名
  readonly args: Readonly<Record<string, unknown>>    // 具名 wire 值（必须精确匹配 descriptor）
  readonly signal?: AbortSignal                       // 带外取消，只注入给"支持取消"的方法
}
```

**注意**：`args` 是**具名**的（不是位置参数）——**像 JSON body，不像函数位置参数**。

> **Go 类比**：`args` 像 **HTTP JSON body**（具名字段）；不是 Go 那样的位置参数。

## 七、构建期发生了什么（严格生成流水线）

**Typert 不是运行时魔法**——**是构建期生成的**：

> **出处**：`docs/api-gateway.zh.md`「严格生成流水线」（逐字）——*"Host lib 阶段先运行 `tsc -b tsconfig.host.json`，再运行 `tsdown --env.DSH_BUILD_FACE host`；**Typert generator 由正常 Host Project Reference 图编译**，并在这次 tsdown 中**以 Host aggregate 为唯一 `ts.Program` 种子运行**。"*

**每个贡献业务包生成四个文件**（出处：同上，逐字，表格）：

| 文件 | 给谁 | 内容 |
| --- | --- | --- |
| `typert.host.js` | Host Loader | 运行时反射、严格调用描述符、schema 注册值 |
| `typert.host.d.ts` | Host 类型系统 | Host face 的生成声明 |
| `typert.remote-client.js` | `api-remotes` | 可挂载的 `TypertRemoteContribution`（严格描述符 + codec） |
| `typert.remote-client.d.ts` | Client 类型系统 | `TypertRemoteNamespaceMap` / `TypertRemoteScopeMap` 声明合并 |

**严格分析的约束**（出处：同上，逐字）——*"Remote 必须是**公开、非静态、有具体实现的实例方法**。方法**不能是泛型**；参数必须是**具名且必填的简单标识符**，不能使用解构、默认值、rest 或可选参数。"*

> **⚠️ 记住这条约束**：**`@Remote` 方法不能用解构/默认值/可选参数**——这是"严格生成"的代价。你写的时候会踩到。

> **Go 类比**：**像 protobuf 编译器**——它要能静态分析出每个字段的类型；**你写得太动态（泛型/解构），它就没法生成**。**约束是为了可分析性**。

---

## 八、Typert 为什么这么设计（三个决策）

| 决策 | 好处 | 出处 |
| --- | --- | --- |
| **构建期生成，非运行时反射** | 类型安全、无运行时开销、可编译检查 | 生成流水线 |
| **descriptor 不发到网上** | wire 更小；请求只带 namespace/method/args | 「调用 descriptor」 |
| **Lookup 把对象换成 id** | 复杂对象能跨进程传；策略可换而签名不变 | 「Lookup 与上下文声明」 |

> **Go 类比**：**这正是 gRPC 相比"手写 HTTP+JSON"的优势**——**接口是编译期契约，不是运行时约定**。
