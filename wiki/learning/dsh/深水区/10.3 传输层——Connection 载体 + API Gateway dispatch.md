# 10.3 传输层——Connection（载体）+ API Gateway（dispatch）

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**10.2（Typert 协议）** + **08.1（HTTP/WebSocket 边界）**
> - 权威文档：`docs/api-gateway.zh.md`「运行时调用」 + `packages/client/connection/README.zh.md`
> - 本篇对象：**熟悉 API 网关 / 中间件的后端**

> [!abstract] 读完该记住 6 点
> 1. **职责分离**：**Connection 拥有传输**（HTTP/WS、RPC id、envelope、取消）；**Gateway 只拥有 Remote 数据协议与业务分发**
> 2. **一个 Remote 调用 = `POST /api/<namespace>/<method>`**，payload 只有一个具名 `args` 对象
> 3. **信任检查在 HTTP bridge 之前**（统一在 `/api` 上）
> 4. **Gateway 每次调用都从当前注册表解析**——不缓存业务对象
> 5. **错误码分层**：`gateway/*`（基础设施/边界）+ 业务自有码（如 `session/not-found`）**原样透传**
> 6. **SRC 回退**：源码启动（tsx）时不跑 Typert 编译，用"较弱描述符"开发

## 一、先分清：Connection 和 Gateway 各管什么

**这是全篇最重要的一点**：

> **出处**：`docs/api-gateway.zh.md`「运行时调用」（逐字）——*"**Connection 拥有传输、RPC id、响应 envelope 和请求取消**，**Gateway 只拥有 Remote 数据协议和业务分发**。**替换 Connection carrier 不要求改变 Remote 描述符或 Client 编程接口。**"*

| 层 | 拥有 | 不关心 |
| --- | --- | --- |
| **Connection** | 传输（HTTP POST / WebSocket）、RPC 请求 id、响应 envelope、取消、信任边界 | 业务方法是谁、参数含义 |
| **Gateway** | Remote 数据协议、业务分发、参数/返回值校验、lookup 解析 | **用什么载体传输** |

> **Go 类比**：**这就是"传输层 vs 应用层"的干净切分**——
> - **Connection ≈ `net/http` + 你的认证/限流中间件**（只懂"包"，不懂业务）
> - **Gateway ≈ 你的路由 handler**（懂业务，但不管怎么传的）
>
> **好处**：**换载体（HTTP→WebSocket→IPC）不用改业务**——这正是 Desktop（Electron 用 IPC）能复用同一套 Remote 的原因。

## 二、一次调用的物理路径（wire 级）

> **出处**：`docs/api-gateway.zh.md`「运行时调用」（逐字）——*"Client Remote 调用 `connection.rpc.call('/api', '<namespace>/<method>', { args }, signal)`；**HTTP carrier 对应 `POST /api/<namespace>/<method>`，payload 只包含一个具名 `args` 对象**。"*

```
Client：ctx.remote.goals.create(agentId, { objective: 'ship it' })
   │
   ▼  connection.rpc.call('/api', 'goals/create', { args }, signal)
   │
   ▼  HTTP POST /api/goals/create
      body: { "args": { "agentId": "...", "request": { "objective": "ship it" } } }
   │
   ══════════ 网络 ══════════
   │
   ▼  webserver（node:http）收到
   ▼  Connection：统一信任检查（Host/Origin）
   ▼  共享 FetchHandler 分发
   ▼  Gateway 认领这个两段式 endpoint（goals/create 有严格描述符）
   ▼  Gateway：校验 args 字段集 → codec 校验 → lookup 解析 agentId→Agent → 调服务 → 校验返回值
   │
   ▼  响应 envelope 回传
```

**逐段对齐 10.1 的"调用旅程"**——现在你知道每一环落在哪个包了。

## 三、路由与认领规则（谁处理哪个请求）

> **出处**：`docs/api-gateway.zh.md`「运行时调用」（逐字）——*"Typert Gateway 只**认领存在严格描述符或活跃 SRC marker 的两段式 endpoint**；**功能自有的精确 Fetch 路由处理非 JSON 响应，其他请求返回 404**。"*

| 请求 | 谁处理 |
| --- | --- |
| `POST /api/<ns>/<method>`（**有两段式 endpoint**） | **Gateway**（认领） |
| 功能自有的精确 Fetch 路由（如文件下载） | 注册那个路由的功能包 |
| 其他 | **404** |

> **出处**：`docs/api-gateway.zh.md`「边界」（逐字）——*"需要**流式或浏览器原生响应**的功能注册**精确的 Connection Fetch 路由**，而不定义 Remote 方法。"*

**记住**：**Remote 只处理"一个请求、一个结果"的一元方法调用**（出处：同上「边界」：*"Remote 只处理有单个请求与单个结果的一元方法调用"*）。**流式（会话事件）走另一条路**。

> **Go 类比**：**一元 RPC（unary）vs 流式（streaming）**——**你的 gRPC 也分这两种**。dsh 的 Remote 只管 unary；streaming 另走 `$events`（见第五节）。

## 四、Gateway 的调用纪律（不缓存、严格校验）

> **出处**：`docs/api-gateway.zh.md`「运行时调用」（逐字）——*"Gateway **每次调用都从当前注册表解析描述符和实时服务，不缓存业务对象**。它要求 `args` 的字段集合与描述符**完全一致**，先用 codec 校验 wire 值，再通过注册的 lookup 或 Context 提供方**解析对象或接收者**，最后调用 binding 指向的服务方法并**校验返回值**。"*

**调用五步**（出处：同上）：

```
① 校验 args 字段集 == descriptor（多一个/少一个都失败）
② codec 校验 wire 值（类型对不对）
③ lookup/Context 解析对象（agentId → Agent）
④ 调 binding 指向的服务方法
⑤ 校验返回值
```

**失败时机**（出处：同上）——*"缺少提供方、identity 未命中、binding 不一致、参数缺失或多余、schema 失败和方法不存在都会**在进入业务代码前**或**离开业务代码后**失败。"*

> **Go 类比**：**这就是你在 handler 里做的参数校验 + 反序列化**——**只是 Gateway 帮你做了，且是"编译期生成的严格版本"**。

## 五、错误码分层（后端会很熟）

> **出处**：`docs/subsystems/typert.zh.md`「Host Gateway」（逐字）——*"基础设施与边界失败由 `TypertGatewayError` 承载，其 `gateway/*` 码就是普通的 `RemoteError` 码，因此 **RPC 适配器会把每个经结构识别的 `RemoteError` 连同其 code 与 details 原样放行，只把无法识别的异常归并为 `gateway/internal`**。"*

**两类错误**：

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| **基础设施/边界** | `gateway/lookup-not-found`、`gateway/arguments-invalid`、`gateway/signature-invalid` | Gateway 产生，`gateway/*` 码 |
| **业务自有** | `session/not-found`、`session/agent-busy` | 业务抛，**原样透传** |

> **出处**：`docs/api-gateway.zh.md`（逐字）——*"恢复失败与 ownership fence 抛出携带自有码的 `RemoteError`（`session/not-found` 或 `session/agent-busy`），**Gateway 原样编码上 wire**；只有**未归类的 throw 才折成 `gateway/internal`**。"*

**`gateway/*` 码全表**（出处：`docs/subsystems/typert.zh.md`，逐字，共 17 个）：

```
gateway/ambiguous-endpoint    gateway/lookup-failed
gateway/arguments-invalid     gateway/lookup-not-found
gateway/binding-invalid       gateway/lookup-unavailable
gateway/context-failed        gateway/method-unavailable
gateway/context-not-found     gateway/provider-mismatch
gateway/context-unavailable   gateway/result-invalid
gateway/definition-unavailable gateway/service-unavailable
gateway/input-invalid         gateway/signature-invalid
gateway/invocation-unavailable
```

> **Go 类比**：**这就是"框架错误 vs 业务错误"的区分**——**框架错误（路由没找到/参数不对）**归框架；**业务错误（会话不存在）**原样返回。**跟你设计 error code 的思路一样**。

## 六、Lookup 的运行时：Session Controller 负责 agent/session

> **出处**：`docs/api-gateway.zh.md`「运行时调用」（逐字）——*"**Session Controller 负责 `agent` 与 `session` 的标准 resolver 语义**：**复用 live Agent，自动恢复普通冷会话，对并发恢复去重，并拒绝由 subagent routing 拥有的 identity**；`session` lookup 返回该 Agent 的 Session。"*

**"冷恢复"是什么意思**：一个 agent 会话可能**不在内存里**（进程重启了），但历史还在磁盘。**当你调用一个需要该 agent 的方法时，resolver 自动把它"恢复"到内存**。

> **出处**：同上「边界」（逐字）——*"lookup 策略**按 key 配置**，因此所有 `agent` 或 `session` 参数**共享冷恢复行为**。"*

> **Go 类比**：**这就是"懒加载 + 缓存"**——对象不在内存就**按需加载**；且**"共享冷恢复"= 同一类参数用同一套恢复策略**（不用逐个方法配）。

## 七、事件流：另一条路（`$events`）

**Remote 只管 unary**。**流式事件（agent 边跑边推）走 `$events`**：

> **出处**：`docs/subsystems/web-client.zh.md`「Remote 通信」（逐字）——*"内部 `$events` **logical stream** 是 Connection **generation source**。它的 opening `ready` frame 携带用于路径显示的 Host home，并在 Host listener 已挂载、任何 controller 开始 baseline read 之前建立 generation。`ctx.remote.$on()` 把 allowlist 内的普通 event 交付给 root Client Context，并把 scoped waterfall event 交付给已解析的 Session Context。"*

| 通道 | 用途 | 传输 |
| --- | --- | --- |
| **Remote（unary）** | 一次性调用（创建目标、取消） | `POST /api/<ns>/<method>` |
| **`$events`（stream）** | 持续事件（agent 状态、消息流） | **WebSocket**（`/api/remote.mux`） |

> **出处**：`packages/client/connection/README.zh.md:11`（逐字）——*"浏览器通过 **HTTP POST** 执行 Remote 一元调用；**API Gateway 自己拥有 `/api/remote.mux` WebSocket 及其逻辑流**。"*

> **Go 类比**：**unary RPC vs server-streaming RPC**——**一个走短连接 POST，一个走长连接**（回扣 08.1 讲的 HTTP/WebSocket）。

---

## 八、SRC 回退：源码启动时的"弱描述符"

**开发时**，Host 用 `tsx` 直接从源码跑（**不编译**）——那 Typert 怎么工作？

> **出处**：`docs/api-gateway.zh.md`「SRC 开发回退」（逐字）——*"Host 通过 `node --import tsx/esm` 从源码启动时**不会执行 Typert 编译插件**。标准 decorator 初始化器仍会把方法名和调用模式记录到 Service 原型上的**带版本描述符**中……**Gateway 因而可以在不启动 `ts.Program` 的情况下构造一个较弱的临时描述符**。"*

**SRC 回退的能力**（出处：同上，逐字）：

- ✅ 从运行中函数解析简单参数名
- ✅ 用 lookup 的 `parameter`（如 `agent`/`session`）做 id→对象
- ✅ `@RemoteScope` 用已注册的 Context provider
- ❌ **不读 TypeScript 类型**
- ❌ **不生成 Zod schema**
- ❌ **不支持解构/默认值/rest/可选参数**

**关键**（出处：同上）——*"**Client 不会从运行中的 Host 发现 decorator**，Client Remote 也**拒绝挂载缺少严格 codec 的 SRC 描述符**。"*

> **Go 类比**：**像"开发模式用反射、生产模式用代码生成"**——**开发图快（反射），生产图严（生成）**。**dsh 明确区分了两者**。

---

## 九、卸载与热重载（一个精细点）

> **出处**：`docs/api-gateway.zh.md`「运行时调用」（逐字）——*"Client 卸载一个贡献时会**一起移除描述符和具体方法，中止其进行中的调用**，并使外部仍持有的陈旧方法句柄**拒绝继续调用**。Host 上已经注册过的严格 endpoint 被撤回后**也不会降级到 SRC 推断**，以免热卸载悄然降低校验强度。"*

**两个安全点**：

1. **卸载 → 中止在途调用 + 旧句柄拒绝调用**（不会"调了个寂寞"）
2. **严格 endpoint 撤回后不降级到 SRC**（不会"校验强度偷偷变弱"）

> **Go 类比**：**这就是"优雅关闭 + 防止陈旧引用"**——**关服务时中止在途请求，旧客户端句柄报错，而不是静默降级**。

## 自测

1. Connection 和 Gateway 的职责怎么分？（→ Connection 传输/envelope/取消；Gateway 数据协议/业务分发）
2. 一个 Remote 调用对应什么 HTTP 请求？（→ `POST /api/<namespace>/<method>`，body 是 `{args}`）
3. 业务错误（如 `session/not-found`）会怎样？（→ 原样透传；只有未归类异常折成 `gateway/internal`）
4. `$events` 和 Remote 的区别？（→ 流式事件（WebSocket）vs 一元调用（POST））
5. SRC 回退是什么？（→ 源码启动时的弱描述符，不读类型、不生成 schema）
6. 卸载一个贡献时会发生什么？（→ 移除方法 + 中止在途调用 + 旧句柄拒绝调用）

**都能答上** → 进 **10.4 Web Client 的六层分层**。
