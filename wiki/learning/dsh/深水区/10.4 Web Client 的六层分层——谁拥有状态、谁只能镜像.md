# 10.4 Web Client 的六层分层——谁拥有状态、谁只能镜像

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**10.2 / 10.3（Typert + 传输）** + **08.6.1（三层架构，可选）**
> - 权威文档：`docs/subsystems/web-client.zh.md`「分层与所有权」
> - 本篇对象：**熟悉 CQRS / 状态镜像的后端**

> [!abstract] 读完该记住 5 点
> 1. **六层**：Host 状态 → 传输 → **Client model** → UI adapter → Conversation → Slots/React
> 2. **依赖方向单向**：`Host 状态 → Remote 传输 → Client model → UI adapter → ... → React`
> 3. **Host 拥有权威状态**；Client model **只是"与 React 无关的镜像"**
> 4. **用户操作走 callback 反向**（进入 Client service 或 Remote namespace）
> 5. **UI 组件绝不接收 `ctx` / transport 对象 / 其他插件的实现**（边界纪律）

## 一、六层全表（官方逐字）

> **出处**：`docs/subsystems/web-client.zh.md:9`「分层与所有权」（逐字）：

| 层 | Owner | 职责 |
| --- | --- | --- |
| **Host 应用** | 业务 service 与 `packages/api/*-controller` Host entry | **拥有权威状态、持久化、mutation 顺序、访问策略与 stream 生产** |
| **传输与 API assembly** | `client/connection`、`api/gateway`、`api/remotes` | 建立 Client generation，公开生成的 `ctx.remote` method 与 stream，转发选定事件，承载取消和结果 |
| **Client model** | `api/session-controller/client`、`api/workspace-controller/client` | 维护**不依赖 React 的 Host 状态镜像**，处理 stream/unary 竞态，拥有对象 identity 与订阅，公开收窄的 command service |
| **UI adapter** | `client/ui-session`、`client/ui-workspace` | 把 model observable 转换为 root 或 Session scope 的标准 **Slot source**，**不接管业务状态所有权** |
| **Conversation 数据** | `client/ui-conversation`、`ui-chat`、`ui-trajectory` | 把标准 event 与紧凑的 Assistant 历史批次**组装成相互独立的 target snapshot** |
| **组合与渲染** | `client/ui-slots`、`ui-renderer`、`ui-layout`、各 UI 功能包 | 声明扩展位置、推导组件 props、把 observable 绑定成 React hook、挂载最终组件树 |

**依赖方向**（出处：同上，逐字）——*"依赖方向是 **Host 状态 → Remote 传输 → Client model → UI adapter → Conversation 或 presentation → Slots → React**。用户操作通过 **callback 反向**进入注入的 Client service 或生成的 Remote namespace。"*

```
┌──────────── Host 进程 ────────────┐
│ Host 状态（权威）                  │
└──────────────┬────────────────────┘
               │  Remote（10.2/10.3）
┌──────────────▼──── Client 进程 ────┐
│ 传输与 API assembly                │
│   ↓                                │
│ Client model（镜像，无 React）      │   ← "读模型"
│   ↓                                │
│ UI adapter（转成 Slot source）      │
│   ↓                                │
│ Conversation 数据（组装 snapshot）  │
│   ↓                                │
│ Slots / React（渲染）              │
└────────────────────────────────────┘
               ↑
用户操作 ── callback 反向 ──► Client service / Remote namespace
```

> **Go 类比**：**这就是标准的 CQRS / 读写分离**——
> - **Host = 写模型（权威、有序、持久化）**
> - **Client model = 读模型（镜像、可订阅、不拥有真相）**
> - **用户操作 = command，反向回到写侧**
>
> **你用过 CQRS 的话，这层关系一眼就懂。**

## 二、为什么 Client 不直接渲染 Host 数据？（中间为什么要 Client model）

**直觉做法**：Host 推啥，UI 就显示啥。

**dsh 不是**——中间隔了 **Client model**（无 React 的镜像层）。**三个理由**：

| 理由 | 说明 |
| --- | --- |
| **处理竞态** | stream（事件流）和 unary（一次性调用）可能乱序到达，model 负责**排序/去重** |
| **维持对象 identity** | 同一个会话/工作区，**引用要稳定**（否则 React 疯狂重渲染） |
| **隔离 React** | 业务状态逻辑**不依赖 React**，可测试、可复用 |

> **出处**：同上（逐字）——*"Client 侧基于相同的生成 wire type 维护 **identity 稳定、与 React 无关的 model**，并公开 observable snapshot 与 command。UI 包消费这些 Client service，**不在 component store 中复制 transport state**。"*

> **Go 类比**：**Client model ≈ 你服务端的"本地缓存 + 一致性处理"**——**你不让数据库直连视图，中间隔一层"领域服务"**。**同一套分层动机。**

## 三、UI adapter：把 model 转成"Slot source"

> **出处**：`docs/subsystems/web-client.zh.md:9`（逐字）——UI adapter 的职责是*"把 model observable **转换为 root 或 Session scope 的标准 Slot source**，**不接管业务状态所有权**。"*

**`ui-session` / `ui-workspace` 干的事**：把"Client model 的 observable"**翻译成"slot 系统认识的 source"**。

> **回扣 08.6.2 / 08.6.3**：slot 系统的"裸 observable source"（`getSnapshot`/`subscribe`）→ 渲染器绑成 React hook。**UI adapter 就是"model → 那个裸 source"的转换器**。

```ts
// 概念示意
Client model (observable)
   │  ui-session 做适配
   ▼
Slot source（{ getSnapshot, subscribe }）
   │  ui-renderer 绑定
   ▼
组件里的 hooks（useSession / useStore）
```

> **Go 类比**：**适配器模式**——**把 A 接口转成 B 接口**（你的 `sql.Scanner` / `driver.Valuer` 就是这味道）。

## 四、一条铁律：UI 组件"什么都不能碰"

> **出处**：`docs/subsystems/web-client.zh.md:9`（逐字）——*"Presentation component **绝不接收 Cordis `ctx`、transport object 或其他功能插件的实现**。"*

**UI 组件只能拿到**：

- ✅ 类型化的 **props**（从 slot 系统推导）
- ✅ 绑好的 **hooks**（`useSession` / `useStore` 等）
- ✅ 普通数据与回调

**UI 组件不能拿到**：

- ❌ Cordis `ctx`
- ❌ transport 对象（connection）
- ❌ 别的插件的内部实现

> **Go 类比**：**这就是"依赖收窄"**——**handler 不拿 `*sql.DB`，只拿收窄的 interface**。**回扣 08.2 的 inject 收窄纪律。**

## 五、启动链（从 HTML 到 React）

> **出处**：`docs/subsystems/web-client.zh.md`「浏览器启动」（逐字）——*"Host 把组合后的 `WebBootGraph` 写入 `window.__DSH_BOOT__`……Web boot kernel 创建模块系统、预取 `immediately` entry、挂载 vendored Cordis Loader，再创建图中的每个 entry。Cordis service injection 决定激活顺序……完整 roster 到达 settled 状态后，`ui-renderer` hydrate 不依赖框架的 boot DOM，并调用**唯一一次 context 级 `renderSlot('root')`**。"*

```
① Host 写 window.__DSH_BOOT__（插件名册）
② boot kernel 建模块系统 + 挂 Loader + 创建每个 entry
③ 等所有 entry ACTIVE
④ ui-renderer hydrate boot DOM + renderSlot('root') 一次
⑤ React 接管
```

> **回扣 08.6.1**：这就是"三层架构"的**启动时序**——**Cordis 插件树先起，React 后挂**。

## 六、重连：generation 的概念

> **出处**：`docs/subsystems/web-client.zh.md`「Remote 通信」（逐字）——*"内部 `$events` logical stream 是 Connection **generation source**。"*
> **出处**：`packages/client/connection/README.zh.md`「Connection generation」（逐字）——*"`ConnectionController` 仅在收到该 **ready 项**后**发布 generation** 并调用 `onConnected`，因此 **baseline 不会跑在增量 listener 前面**。"*

**generation = "一次连接的世代"**：

```
连接建立 → 收到 ready → 发布 generation ① → 正常收发
    ↓ 连接断了
重连 → 收到 ready → 发布 generation ② → 各控制器 resync（重新拉基线）
```

**关键**（出处：同上）——*"重连即重建：`onConnected` → **列表刷新 + 各已打开会话 resync**。"*

**重试策略**（出处：同上，逐字）——*"在 500ms、1s、2s、4s、8s 与 10s 上限内采用 **50%–100% 抖动**重试。"*

> **Go 类比**：**这就是"断线重连 + 重新同步"**——**连接有"世代"概念，重连后必须重新拉一遍基线**（因为你可能漏了断线期间的事件）。**跟 etcd/client-go 的 watch 重连逻辑一个思路。**

## 七、把六层串成一个具体场景

**场景**：用户在 Web UI 里点了"取消当前对话"。

```
① 用户点按钮（React 组件，Slots 层）
        │  onClick → 调 props 里的回调
        ▼
② 回调进入 Client service（Client model 层，ui-session 提供）
        │  收窄的 command
        ▼
③ 调 ctx.remote....cancel(...)（传输层，生成的 Remote 方法）
        │  POST /api/.../cancel
        ══════════ 网络 ══════════
        ▼
④ Gateway → Host 服务 → 真正取消（Host 层，权威状态变更）
        │  产生 session/event
        ▼
⑤ $events WebSocket 推回 Client（传输层）
        ▼
⑥ Client model 更新镜像（处理竞态）
        ▼
⑦ UI adapter → Slot source 变化
        ▼
⑧ React 重渲染（用户看到"已取消"）
```

**这条链把 10.2/10.3 和 08 章全串起来了**。

> **Go 类比**：**命令（write）走一条路，事件（read）走另一条路**——**CQRS 的经典双通道**。
