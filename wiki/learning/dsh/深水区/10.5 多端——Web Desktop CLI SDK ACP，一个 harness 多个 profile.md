# 10.5 多端——Web / Desktop / CLI / SDK / ACP，一个 harness + 多个 profile

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**10.4（Web Client 六层）** + **09.2（配置即插件树）**
> - 权威文档：`apps/cli/README.zh.md`、`apps/desktop/README.zh.md`、各 bundle README
> - 本篇对象：**后端**（"同一套代码支撑多个端"是你熟悉的话题）

> [!abstract] 读完该记住 5 点
> 1. **"多端"不是多套代码**——是"**同一个 harness + 不同 profile**"
> 2. **`dsh` 是唯一受支持的启动器**；**SDK / ACP 都是 profile**，不是独立命令
> 3. **各端靠 bundle 区分**：`web-app` / `sdk-app` / `sdk-minimal` / `acp-app` / `headless`
> 4. **Desktop = Electron 壳包 Web UI**——不开端口，走 IPC（复用同一套 Remote）
> 5. **`base` bundle 是共享核心**——各端在它之上叠加（回扣 09.2 的 patch 层叠）

## 一、核心命题：多端 = 一个 harness + 多个 profile

> **出处**：`apps/cli/README.zh.md`（逐字）——*"`dsh` 是**唯一受支持的 Node 应用启动器**；profile 由多个插件组合包 patch 层按顺序叠加而成，其上再应用用户自己的覆盖配置。**SDK 与 ACP（Agent Client Protocol）都是 profile，而不是独立的公开可执行命令。**"*

**这句话是整篇的钥匙**：**不存在"dsh-web"、"dsh-sdk"、"dsh-desktop" 三个程序**——**只有一个 `dsh`**，**换 profile 就是换端**。

```
                    ┌──────────────┐
                    │     dsh      │  ← 唯一启动器
                    └──────┬───────┘
        ┌──────────┬───────┼───────┬──────────┐
        ▼          ▼       ▼       ▼          ▼
     web-app   sdk-app  sdk-minimal acp-app  headless
     (浏览器)   (SDK)    (极简SDK)   (IDE)    (一次性任务)
        └──────────┴───────┴───────┴──────────┘
                          ▼
                    base（共享核心）
```

> **Go 类比**：**这就是"一个二进制 + 多种运行模式"**——像 `busybox`（一个程序，软链成 `ls`/`cp` 就变不同工具），或你编译时用 build tag 切功能。**dsh 用 profile（配置）而不是编译来切。**

## 二、五个端逐个看（都有出处）

| 端 | 启动方式 | bundle | 说明（出处：各 bundle README 逐字） |
| --- | --- | --- | --- |
| **Web** | `dsh web` | `web-app` | *"dsh 的**浏览器 GUI**：交互式聊天、模型与设置管理、会话历史"* |
| **CLI/headless** | `dsh --profile headless` | `headless` | *"一次任务模式：从命令行运行单个任务并打印最终答案，供脚本化或自动化"* |
| **SDK** | `dsh --profile sdk` | `sdk-app` | *"面向启动 **JSON-RPC harness 运行时**的用户……SDK stdio 应用 profile"* |
| **SDK-minimal** | `dsh --profile sdk-minimal` | `sdk-minimal` | *"不含共享 base bundle 的**极简跨平台 coding agent**……默认提供一个 shell 工具"*（回扣 09 章） |
| **ACP** | `dsh --profile acp` | `acp-app` | *"**纯自动化 ACP（Agent Client Protocol）** stdio 应用 profile"* |
| **Desktop** | 装 App | —（Electron 壳） | 见第三节 |

> **出处**：`packages/bundle/` 目录（`base` / `web-app` / `sdk-app` / `sdk-minimal` / `acp-app` / `headless`）

**`base` 是共享核心**：

> **出处**：`packages/bundle/base/README.zh.md`（逐字）——*"共享的 dsh 核心：为每个 `dsh --profile` 表层提供**模型访问、工具、持久会话与安全默认值**，供用户组合或定制 profile。"*

**回扣 09.1**：还记得 `sdk-minimal` **刻意不继承 `base`** 吗？（它是"不含共享 base bundle 的独立 SDK profile"）——**这正是"profile 可以完全自定义"的极端例子**。

> **Go 类比**：**`base` ≈ 你的"基础镜像"（Docker `FROM golang:base`）**；**各端 ≈ 在基础镜像上 `RUN` 不同步骤**。**`sdk-minimal` ≈ `FROM scratch`**（不要基础镜像）。

## 三、Desktop：Electron 壳包 Web UI

> **出处**：`apps/desktop/README.zh.md`（逐字）——*"桌面应用是**包裹 dsh Web UI 的 Electron 壳**。它**不打开监听端口**：内置的上游 Node.js 子进程启动已安装的 dsh 项目，**带版本的分帧字节管道**在没有外层 Base64 信封的情况下承载 Fetch 请求与流式响应，**Node IPC 承载生命周期控制**，`dsh-app://` 则提供与后端版本匹配的客户端资源。"*

**关键洞察**：Desktop **不是新 UI**——**是同一个 Web UI，换了个"载体"**：

| 方面 | Web | Desktop |
| --- | --- | --- |
| UI | 同一套 React | **同一套** |
| Remote 协议 | 同一套 Typert | **同一套** |
| 载体 | HTTP POST + WebSocket（`/api`） | **IPC（分帧字节管道）** |
| 监听端口 | 有（3080） | **无**（不开端口） |

**为什么能这样？** —— **回扣 10.3**：

> **出处**：`docs/api-gateway.zh.md`「运行时调用」（逐字）——*"**替换 Connection carrier 不要求改变 Remote 描述符或 Client 编程接口。**"*

**"换载体不用改业务"**——Desktop 就是这个设计的**实证**。

> **Go 类比**：**这就是"依赖倒置"的威力**——**传输可替换**（HTTP→IPC），业务代码不动。**像 `io.Writer`：写文件、写网络、写内存，调用方不变。**

## 四、SDK：把 harness 当"库"用

> **出处**：`packages/sdk/server/README.zh.md`（逐字）——*"`dsh-sdk-jsonrpc-server` 通过 **stdio 服务 SDK 协议格式**，使**进程外客户端能够驱动 harness agent**：它为每个 `sessionId` 打开一个会话、把用户提示词排入队列，并把每个会话事件与 agent 状态转换**流式发回客户端**。"*

**SDK 的样子**：

```
你的程序（Python / Node）
   │  spawn dsh --profile sdk
   ▼
dsh 进程（stdio）
   │  JSON-RPC 帧（stdin/stdout）
   ▼
你发 prompt → dsh 跑 agent → 事件流回你
```

**约束**（出处：同上，逐字）——*"**Stdout 只承载 JSON-RPC 帧，因此部署不得组合 stdout logger**。"* ← **重要坑：stdout 是协议通道，别往里打日志**。

> **Go 类比**：**这就是"把程序当子进程驱动"**——像 `git` 被 IDE 通过 stdio 调用，或 **LSP（Language Server Protocol）**。**你写工具时常用的手法。**

## 五、ACP：给编辑器/IDE 用的协议

> **出处**：`packages/acp/acp/README.zh.md`（逐字）——*"`dsh-acp` 让**受信程序通过标准 [ACP](https://agentclientprotocol.com) 自动操作持久 DeepSeek Harness agent**：创建或恢复会话、选择模型与推理强度、挂载 MCP 服务器、提交或取消工作、接收语义更新，并独立关闭会话。"*

**ACP = Agent Client Protocol**（一个公开标准）——**让编辑器（如 Zed 之类）能驱动 agent**。

**定位**（出处：同上，逐字）——*"**进程外 subagent、测试运行器与脚本化控制器**适合选择它；它**刻意不提供 DSH 专用呈现数据与交互式 UI 功能**。"*

**ACP 的能力边界**（出处：同上）——*"持久化支持跨进程重启**列出、恢复与关闭**会话，但**不支持删除、fork、transcript 回放与附加目录**。"*

> **Go 类比**：**ACP ≈ LSP 的"agent 版"**——**一个标准协议，让外部工具（编辑器）能"标准化地"驱动你的 agent**。**dsh 实现了这个协议，所以能被标准客户端驱动。**

## 六、一张总表：多端怎么共享、怎么分化

| | Web | Desktop | SDK | ACP | headless |
| --- | --- | --- | --- | --- | --- |
| **是 profile 吗** | ✅ | 壳（包 Web） | ✅ | ✅ | ✅ |
| **载体** | HTTP/WS | IPC | stdio JSON-RPC | stdio ACP | 进程内 |
| **UI** | React | 同一套 React | 无 | 无 | 无 |
| **共享核心** | base | base | base | base | base |
| **典型用途** | 人用 | 人用（桌面） | 程序嵌入 | IDE 集成 | 脚本/CI |

**共享的**：harness 内核（09 章四块）+ Remote 协议（10.2）+ 业务服务。
**分化的**：**载体 + UI + profile 配置**。

> **Go 类比**：**这就是"核心逻辑复用、接入方式分化"**——**同一套领域逻辑，gRPC / REST / CLI / 库 四种接入**。**你做过这种"多渠道接入"就有共鸣。**

## 七、为什么这个设计好（回到"一切皆插件"）

**多端能这么干净，靠的是前面学的三件事**：

| 支撑 | 来自 |
| --- | --- |
| **一切皆插件**（换 profile = 换插件树） | 09.2 |
| **Remote 载体可替换**（业务不感知传输） | 10.3 |
| **UI 与业务解耦**（六层分层） | 10.4 |

**三者合起来** → **"多端 = 换配置，不换代码"**。

> **Go 类比总纲**：**这就是"内核 + 适配器"架构**——**内核稳定（harness），适配器可换（web/desktop/sdk/acp）**。**你在网关/协议栈里常用的架构模式。**

## 自测

1. "多端"是多套代码吗？（→ 不是，一个 harness + 多个 profile）
2. SDK / ACP 是独立命令吗？（→ 不是，都是 profile）
3. `base` bundle 是什么？（→ 共享核心，各端在其上叠加）
4. Desktop 为什么能复用 Web UI？（→ 换载体不改业务——Connection carrier 可替换）
5. SDK 的 stdout 能打日志吗？（→ 不能，stdout 只承载 JSON-RPC 帧）
6. ACP 是给谁用的？（→ 编辑器/IDE 等受信程序，走标准协议）

**都能答上** → **05 章结束**。回 `00 学习顺序` 继续别的块。
