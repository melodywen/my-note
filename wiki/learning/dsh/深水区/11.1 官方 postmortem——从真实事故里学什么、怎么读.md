# 11.1 官方 postmortem——从真实事故里学什么、怎么读

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**11.0（本章地图）**
> - 权威材料：`docs/postmortem/`（4 篇）+ `docs/postmortem/README.zh.md`
> - 本篇对象：**想学会"从失败里提炼流程级教训"的工程师**

> [!abstract] 读完该记住 5 点
> 1. **postmortem ≠ bug fix**——它记的是"**为什么我们的流程放过了它**"
> 2. **三个收录条件**：隐蔽 / 系统性 / 重新发现的代价高
> 3. **结构固定**：执行摘要 → 概述 → 时间线 → 根因 → 防护措施 → 教训
> 4. **每篇都要有"新增的防护措施"**——不只是"改了那一行"
> 5. **读 postmortem 的价值**：学"**系统性逃逸的模式**"，不是学"某个函数怎么修"

## 一、postmortem 到底记什么

> **出处**：`docs/postmortem/README.zh.md`（逐字）——*"事故复盘记录的是：一个 bug 出现在了**不该出现的地方**（真实用户、已合并的 PR、已发布的版本），值得关注的是**为什么我们的流程放过了它**，而**不仅仅是那一行修复**。"*

**对比一下就懂了**：

| | 普通 bug fix | postmortem |
| --- | --- | --- |
| 关注 | **这一行怎么修** | **为什么流程没拦住** |
| 产出 | 一个 commit | 一篇文档 + **新增的防护措施** |
| 价值 | 修好了 | **同类 bug 下次会自己报错** |

> **出处**：同上（逐字）——*"它是一份**回顾性的失败记录**：什么坏了、机制是什么、**为什么每道安全网都没拦住**、以及为此**新增了哪些具体防护措施**，以确保同类 bug 下次出现时会明确报错。"*

> **Go 类比**：**这就像"线上事故复盘"（postmortem/incident review）**——你不是只修 BUG，而是问"**为什么监控没报警、为什么测试没覆盖、为什么评审没发现**"。**跟 SRE 的 postmortem 文化一模一样。**

---

## 二、什么时候才值得写（三个条件）

> **出处**：同上（逐字）——*"当一个 bug 满足以下条件时，请撰写事故复盘：**隐蔽**（机制不显而易见，即使是细心的工程师也得费力重新推导）、**系统性**（逃逸的原因是测试、工具、约定的缺口，而非一次性的笔误）、**重新发现的代价高**（它消耗了真实的调试时间，且下次还会如此）。"*

**三个条件**：

| 条件 | 含义 |
| --- | --- |
| **隐蔽** | 机制不显然，重新推导费劲 |
| **系统性** | 原因是**测试/工具/约定的缺口**，不是笔误 |
| **代价高** | 花了真实调试时间，且**下次还会** |

> **⚠️ 注意**：**"一次性笔误"不配写 postmortem**——**只有"系统性漏洞"才配**。这是纪律。

---

## 三、固定结构（读的时候看这几节）

> **出处**：同上（逐字）——*"每篇事故复盘以一段**执行摘要**开头……然后才是后续的详细「**概述、时间线、根因、防护措施**」各节。"*

```
① 执行摘要（30 秒读完）——什么坏了、根因、为什么逃逸、教训
② 概述      ——背景、设计意图
③ 时间线    ——什么时候暴露、怎么发现
④ 根因      ——机制到底是什么（技术细节）
⑤ 已添加的防护措施 ——具体加了什么测试/规则/门禁
⑥ 教训      ——可长期沿用的
```

**读的重点**：**④根因 + ⑤防护措施**——**根因让你懂机制，防护措施让你学"怎么防同类"。**

## 四、四篇官方 postmortem（我们逐个看）

> **出处**：`docs/postmortem/README.zh.md` 的目录表（逐字）

| # | 标题 |
| --- | --- |
| 0001 | ACP 服务器在连接时崩溃：`export default` 丢失了插件的 `inject` |
| 0002 | 文件系统快照工具被一个字面量 `!!js` 对象永久禁用 |
| 0003 | Web agent 验证了替代服务器，而非承载其会话的 GUI |
| 0004 | Landlock 部分强制执行通知导致子进程失败被误归类 |

**这四篇各代表一种"逃逸模式"**（我概括，出处为各篇摘要）：

| # | 逃逸模式 | 一句话根因（出处：各篇「摘要」逐字） |
| --- | --- | --- |
| **0001** | **测试走的路 ≠ 生产走的路** | *"两个集成错误在单元测试全覆盖的情况下仍然导致 ACP 崩溃……**手动挂载的测试绕过了这两条路径**"* |
| **0002** | **你以为会求值的地方，其实没求值** | *"Cordis **仅在插件 `config` 内部**对 JavaScript 表达式求值……原始的表达式对象为 truthy，因此文件系统栈**始终处于禁用状态**"* |
| **0003** | **验收了错的对象** | *"它**把验收交还给用户**，随后……**仍把裸 Vite 返回的 HTTP 200 当作成功**……原页面其实已经加载了重建产物，它却去验收**另一个端口**上的替代服务器"* |
| **0004** | **一次判定吞掉了另一类错误** | *"harness 把共享的 `landlock-run:` 前缀与任意非零子进程退出组合起来，判定为 launcher 失败，因此 **ripgrep 在没有匹配项时以 1 退出等普通结果会呈现为 `SANDBOX_UNAVAILABLE`**"* |

> **读这四篇的正确姿势**：**别记"某个函数怎么修"**，**记"这种逃逸模式"**——
> - 0001 → **测试路径要覆盖真实路径**（别用"手动挂载"绕过）
> - 0002 → **配置项的求值规则要写清、要验证**
> - 0003 → **验收要针对"对的实例"**（别验收了替代服务器）
> - 0004 → **错误分类别太宽**（一次宽判定会吞掉无关错误）

> **Go 类比**：**这些模式你在后端都见过**——
> - 0001 ≈ "**mock 测试过了，真实集成挂了**"
> - 0002 ≈ "**配置写了但没生效**"（经典！）
> - 0003 ≈ "**健康检查查错了实例**"
> - 0004 ≈ "**错误码太粗，把正常情况也判成失败**"

## 五、深入一篇：0002（"配置没生效"的经典案例）

> **出处**：`docs/postmortem/0002-js-expression-disabled-filesystem-tools.zh.md`（逐字）

**摘要**（逐字）——*"ACP 示例试图通过 `disabled: !!js ...` 有条件地启用文件系统插件，但 **Cordis 仅在插件 `config` 内部对 JavaScript 表达式求值**。原始的表达式对象为 **truthy**，因此文件系统栈**始终处于禁用状态**。"*

**根因**（逐字，这是技术精华）——*"实现时假设 `!!js` 适用于**整个 Loader 配置项**。实际**只有 `entry.options.config` 使用它**：`Entry._resolveConfig()` 对该字段进行插值，而 **`Entry.disabled` 直接测试 `entry.options.disabled`，不经过插值**。YAML 标签在语法上合法，因此**加载过程不产生任何诊断信息**。"*

**翻译成人话**：

```yaml
# 开发者以为这么写能"有条件启用"
- name: 'filesystem'
  disabled: !!js process.env.FULL_ACCESS !== '1'   # ← 以为这里会求值
```

**实际**：`!!js` **只在 `config:` 里面求值**——写在 `disabled:` 位置上，它**不会求值**，变成了一个"恒为真的对象" → **永远禁用**。

**更糟的是"为什么没被发现"**（逐字）——*"快照套件通过了，因为结构化会话日志和 stdout 渲染出的通用失败工具卡片均与刷新后的 fixture 匹配；**它证明的是回归的确定性回放，而非文件系统行为的正确性**。"*

> **⚠️ 这是最值得学的一句**：**"快照测试通过"不等于"行为正确"**——**快照只证明"输出和上次一样"，不证明"输出是对的"**。

**教训**（逐字）——*"语法上被接受的配置值不一定在该位置被求值；应**记录并验证具体对哪些字段进行插值**。……**快照刷新是 fixture 的生产过程，不是正确性审查**。"*

## 六、从 postmortem 里该学到的"通用模式"

我把四篇提炼成**四条可迁移的教训**：

| 模式 | 教训 | 你会用在哪 |
| --- | --- | --- |
| **测试路径 ≠ 生产路径** | 测试要覆盖真实装配，别用"手动挂载"绕过 | 你的集成测试 |
| **配置"写了"≠"生效了"** | 求值规则要明确、要验证 | 你的配置系统 |
| **验收要针对对的实例** | 确认你验收的就是"正在服务"的那个 | 你的健康检查/部署验证 |
| **错误分类别太宽** | 宽签名会吞掉无关错误 | 你的错误码设计 |

> **Go 类比总纲**：**这就是"复盘文化"的价值**——**单个 bug 会被修复遗忘，但"逃逸模式"会反复出现**。**读一遍这四篇，你就有了"防同类"的直觉。**

## 自测
