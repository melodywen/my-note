# 11.2 贡献者的真实路径——为什么官方不收 PR，还能怎么参与

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**11.1（postmortem）**
> - 权威材料：`CONTRIBUTING.zh.md` + `docs/development.zh.md` + AGENTS.md 社区清单
> - 本篇对象：**想参与 dsh 生态的人**

> [!abstract] 读完该记住 5 点
> 1. **官方目前【不接受外部 PR】**——但这不是"不欢迎你"
> 2. **贡献的主战场是"社区插件"**：写插件 + 加 `dsh-plugin` topic
> 3. **官方仓库的定位**：*"一种理念、一份官方示例、一处灵感来源"*——**不要求社区跟随**
> 4. **参与方式很多**：Discussions 报 bug / 写插件 / 写博客 / 回答问题
> 5. **真要做源码贡献**，得先过 `development.zh.md` 那套（双 tsconfig / CI 门禁 / 双语配对）

## 一、一个反直觉的事实：官方不收 PR

> **出处**：`CONTRIBUTING.zh.md`（逐字）——*"DeepSeek Harness 仍处于早期阶段，并在积极开发中。**很抱歉，我们目前无法接受外部 PR（Pull Request）。**"*

**第一反应可能是"那还怎么贡献？"** —— 但**下一句就解释了**：

> **出处**：同上（逐字）——*"不过，**贡献代码远非帮助本仓库建设的唯一途径**。你还可以通过许多其他方式参与进来。"*

**为什么不收 PR？** —— 因为**项目早期 + 团队小**，外部 PR 会带来**评审/维护负担**。**这是个务实的决定**，不是"关门"。

> **Go 类比**：**很多早期项目都这样**——比如一些公司内部框架、或者早期的小团队项目，**宁可你自己 fork/写扩展，也不接 PR**（因为维护 PR 的成本 > 收益）。**dsh 用的是"插件生态"替代"直接改源码"。**

---

## 二、贡献的真正形态：插件生态

> **出处**：`CONTRIBUTING.zh.md`（逐字）——*"**创建令你感兴趣的插件**，并分享给其他人：**为你的 GitHub 项目添加 `dsh-plugin` 话题**，让其他人更容易找到你的插件。撰写有关 DeepSeek Harness 的博客文章和操作指南。回答问题并帮助其他社区成员。"*

**贡献的四条路**（出处：同上）：

| 方式       | 具体做什么                                  |
| -------- | -------------------------------------- |
| **写插件**  | 给 GitHub 项目加 `dsh-plugin` topic，让别人能找到 |
| **写文章**  | 博客 / 操作指南                              |
| **回答问题** | 帮社区成员                                  |
| **报问题**  | GitHub Discussions 报告 bug、投票           |

> **出度**：同上（逐字）——*"在 GitHub Discussions 中发现并报告问题或 bug……为你希望引起团队关注的讨论投票。"*

> **回扣 03 章**：**你学过的"插件 = package + bundle + patch + profile"**——**就是你贡献的载体**。**这才是 dsh 生态的"入口"。**

---

## 三、官方仓库的定位（很重要的一段）

> **出处**：`CONTRIBUTING.zh.md`（逐字，这段值得逐字读）：

> *"DeepSeek Harness 的设计支持**深度定制**。我们**并不认为官方仓库中的包天然就比社区开发的包更重要**。你可以将本仓库看作**一种理念、一份官方示例以及一处灵感来源**，而**不是我们要求社区遵循的方向**。"*

**这段话的份量**：

- ✅ **官方包 ≠ 更重要**——社区包可以是标杆（AGENTS.md 里就提到 `dsh-compaction` 是"社区标杆必体验"）
- ✅ **官方仓库 = 理念 + 示例 + 灵感**，不是"唯一方向"
- ✅ **"已经看到社区中涌现出令人期待的项目，也希望生态系统继续沿着自己的方向发展"**（出处：同上）

> **Go 类比**：**这像 Go 官方对"第三方包"的态度**——官方提供**标准库（理念+示例）**，但**生态靠社区繁荣**（Gin、Echo…**不比标准库差**）。**dsh 明确拥抱这个模式。**

**AGENTS.md 里就有社区标杆的例子**（出处：`dsh-learn/AGENTS.md:86`）——*"`dsh-compaction`（**社区标杆必体验**）"*。

## 六、给你的"参与路线"建议

**按成本从低到高**：

```
① 先用 —— 装 dsh、跑通、体验社区插件（写笔记）
      ↓
② 写插件 —— 把你遇到的问题做成一个小插件，发 GitHub + 加 dsh-plugin topic
      ↓
③ 写文章 —— 把"我怎么用 dsh 解决了 X"写成博客/指南
      ↓
④ 参与讨论 —— GitHub Discussions 报 bug、投票
      ↓
⑤ （许可后）改源码 —— 走 development.md 那套（双 tsconfig / CI 门禁 / 双语）
```

> **回扣你已学的**：**②③ 你其实已经在做了**——`dsh-learn` 里的 codebuddy-llm 插件、深水区这一整套笔记，**就是"插件 + 文章"的实践**。

> **Go 类比**：**这跟你在 Go 生态里的成长路径一样**——**先用 → 写自己的库 → 写文章 → 参与社区 → （够格了）给官方提 PR**。
