## 一、它到底让模型能干什么

> **出处**：`packages/extensions/tool-cordis/README.zh.md`（逐字）——*"`dsh-tool-cordis` 让模型**检查实时 Cordis 运行时，并创建、运行、停止、更新或移除包含 host 代码、浏览器代码或两者的【临时动态包】**。包版本**不可变**，因此包失败后，模型可以**添加新版本并更新当前运行的版本**。定义**只存在于进程内存中，DSH 重启即消失**；本包**不写仓库文件、不安装依赖，也不改 `cordis.yml`**。它还会**把这套工作流教给模型**。"*

**一句话**：**Agent 在运行时，自己写一个插件 → 挂上去 → 跑 → 不行就改（加新版本）→ 再跑。**

> **回扣 02 章**：02 章标题就是"让 Agent 运行时自己写插件"——**11.3 是它的"官方完整实现 + 工具清单"**。

## 二、7 个工具（模型的手）

> **出处**：`packages/extensions/tool-cordis/src/index.ts`（逐字，工具名与描述）

| 工具 | 干什么 | 读写 |
| --- | --- | --- |
| **`cordis_inspect_list`** | 列出 Host 知道的所有 Inspect Provider | 只读 |
| **`cordis_inspect_query`** | 跑一个 Provider 声明的只读查询 | 只读 |
| **`cordis_inspect_self`** | 检查**当前 Session 拥有的动态对象** | 只读 |
| **`cordis_define`** | **定义一个不可变 Cordis 包**（新插件用 `kind:"new"`） | 写 |
| **`cordis_run`** | **激活某个包**（`mode:"run"` 首次激活） | 写 |
| **`cordis_stop`** | **停掉某插件当前运行**（取消未完成的审批/激活请求） | 写 |
| **`cordis_undefine`** | **永久移除**当前 Session 拥有的动态插件 | 写 |

**结构很清晰**：

```
看（3 个）：inspect_list / inspect_query / inspect_self
写（4 个）：define → run → stop → undefine
```

> **注意 `cordis_stop`**（出处：源码 `:334` 逐字）——*"Stop the current Run of a dynamic Plugin **and cancel unfinished approval or activation requests**."* ← **挂载插件要"审批"**（安全闸门）。

> **Go 类比**：**这就像给 agent 一套"热部署"工具**——`define` 像写代码，`run` 像 `go run`，`stop` 像停服务，`undefine` 像清理。**只是"代码"是模型现写的。**

## 三、"包版本不可变"——为什么要这样设计

> **出处**：`tool-cordis/README.zh.md`（逐字）——*"包版本**不可变**，因此包失败后，模型可以**添加新版本并更新当前运行的版本**。"*

**含义**：

```
❌ 不能：改一个正在跑的包（那会破坏"正在跑的版本"的一致性）
✅ 只能：define 一个新版本 v2 → run v2（取代 v1）
```

**为什么**（回扣 Cordis 纪律）：
- 正在运行的插件**必须有一个稳定的身份**
- 要更新 → **产生新版本**（像容器镜像 `:v1` / `:v2`，**不改 `:v1`**）

> **Go 类比**：**这就是"不可变基础设施 / 版本化制品"**——**部署新版本，而不是原地改**。**跟容器镜像 tag、或数据库 migration 的思路一致。**

---

## 四、"内存里、重启即失"——为什么刻意不持久化

> **出处**：同上（逐字）——*"定义**只存在于进程内存中，DSH 重启即消失**；本包**不写仓库文件、不安装依赖，也不改 `cordis.yml`**。"*

**这是刻意的安全/纪律设计**：

| 不做 | 为什么 |
| --- | --- |
| 不写仓库文件 | **不污染你的代码库** |
| 不安装依赖 | **不改变环境** |
| 不改 `cordis.yml` | **不持久化 agent 的改动**（重启回到已知状态） |

**含义**：**Agent 的"自进化"是"会话内的临时实验"**——**重启就回到"干净状态"**。**要真正留下，得人（你）来决定**（把验证过的插件正式写进仓库）。

> **Go 类比**：**像"容器里的临时改动"**——`docker run` 里改的东西，`docker rm` 就没了；**要持久，得改 `Dockerfile`（人来改）**。**这是一条安全底线。**

## 五、"把工作流教给模型"——工具即提示词

> **出处**：同上（逐字）——*"它还会**把这套工作流教给模型**。"*

**这点很 dsh**：**工具不只是"能力"，还带"怎么用"的指引**（回扣 07.1「agent 的 prompt 写哪」）。

**含义**：**模型不用"猜"这 7 个工具怎么配合**——**工具的描述/指引里就写了"先 inspect → 再 define → 再 run → 失败就加新版本"**。

> **回扣 07.1**：这就是 dsh "**提示词归属**"的一个体现——**能力（工具）和它的用法说明（prompt）应该在一起**，而不是散落。

## 六、它和 `cordis-host-runner` 的分工

> **出处**：同上（逐字）——*"请与 `@deepseek-ai/dsh-cordis-host-runner` 一同组合，后者**提供沙箱与运行往返**。"*

**两个包的分工**：

| 包 | 职责 |
| --- | --- |
| `dsh-tool-cordis` | **工具**（模型调用面：inspect/define/run/…） |
| `dsh-cordis-host-runner` | **运行时**（沙箱 + 运行往返） |

> **回扣 02.1**：02.1 讲的就是"`cordis-host-runner`——动态插件的运行时与沙箱"——**11.3 是它的"模型工具面"**。

> **Go 类比**：**这就是"API 层 vs 执行层"分离**——`tool-cordis` 是给模型用的 API，`host-runner` 是真正执行（且隔离）的引擎。**你在后端也这么分层。**

## 七、为什么这就叫"自进化"

**把上面的拼起来**：

```
① 模型 inspect（看当前运行时有什么）
      ↓
② 模型 define 一个插件（写代码）
      ↓
③ 模型 run（挂载）
      ↓
④ 观察结果 → 失败 / 不满意
      ↓
⑤ 模型 define 新版本 → run 新版本（取代旧的）
      ↓
⑥ 重复 ④⑤ → 逐步逼近目标
```

**这个闭环 = "Agent 自己扩展自己的能力"**。

**关键纪律**：
- **版本不可变**（改 = 加新版本）→ **可追溯、不破坏运行中的**
- **内存里、重启即失** → **不乱改环境**（人为准）
- **要审批**（`cordis_stop` 提到 "cancel unfinished approval"）→ **有安全闸门**

> **Go 类比**：**这像一个"会自己写代码部署的 CI/CD"**——**但每步都隔离、可回滚、需审批**。**架构上就是把"人改代码→部署"换成"模型写插件→挂载"。**
