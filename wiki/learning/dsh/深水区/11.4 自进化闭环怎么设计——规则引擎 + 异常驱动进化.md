# 11.4 自进化闭环怎么设计——规则引擎 + 异常驱动进化

> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`
> - 前置：**11.3（dsh-tool-cordis）** + **02（dynamic-cordis）** + **06（goal）**
> - 依据：`dsh-learn/AGENTS.md:103`（原始目标定义）
> - 本篇对象：**想设计"会自我进化的 Agent 系统"的人**

> [!abstract] 读完该记住 5 点
> 1. **自进化闭环 = 规则引擎 + 异常驱动进化**
> 2. **规则引擎的四要求**：规则**可生成、可评测、可确认、可持久化**
> 3. **异常驱动进化**：从"**异常**"里学，长出/修正规则（如"防火墙 Agent"）
> 4. **闭环是关键**：**观察 → 生成规则 → 评测 → 人确认 → 持久化 → 再观察**
> 5. **`dsh-tool-cordis`（11.3）是"执行器"**——**规则引擎是"大脑"，它负责"动手"**

## 一、回到原始目标（AGENTS.md 逐字）

> **出处**：`dsh-learn/AGENTS.md:103`（逐字）——*"Agent 自进化闭环：**规则引擎（规则可生成、可评测、可确认、可持久化）**、**异常驱动进化（如防火墙 Agent）**；官方样板 `dsh-tool-cordis`「运行时 Cordis 工具」——Agent 可在运行中挂载/卸载**模型自己写的插件**。"*

**拆开看**，这个目标有**三个部件**：

```
① 规则引擎      —— 管规则的生命周期（生成/评测/确认/持久化）
② 异常驱动进化   —— 从"异常"里学习（触发进化的信号）
③ dsh-tool-cordis —— 执行器（真去挂/卸插件）← 11.3 学的
```

**本篇的任务**：把 **①②** 讲清楚，**并说明它和 ③ 怎么配合**。

---

## 二、规则引擎：一条规则的"生命周期"

**"规则"是什么**？—— 一个 **"如果 X，那就 Y"** 的判断（如"如果某 IP 一分钟内请求 > 1000 次，就拉黑 5 分钟"）。

**AGENTS.md 给了规则的四个阶段**（逐字："可生成、可评测、可确认、可持久化"）：

```
① 可生成   —— 规则由谁产生？（模型根据观察/异常生成）
② 可评测   —— 生成后怎么知道"好不好"？（跑评测 / 打分）
③ 可确认   —— 谁来"拍板"？（人来确认——安全闸门）
④ 可持久化 —— 确认后怎么"留住"？（写进存储，下次还在）
```

> **出处**：同上。**这四个"可"字，就是规则引擎该有的四个能力。**

**注意顺序**：**生成 → 评测 → 确认 → 持久化**。
**关键在"确认"**——**规则不是"生成即生效"**，**得人点头**（这是安全底线，回扣 11.3 的"审批"）。

> **Go 类比**：**这就像"配置变更的 CI/CD 流水线"**——
> - 生成 ≈ 有人提了个配置变更
> - 评测 ≈ CI 跑测试（这个变更会不会搞坏）
> - 确认 ≈ 人工 code review / 审批
> - 持久化 ≈ merge + 落盘
>
> **"规则"就是"会自动执行的配置"**——**所以要有 CI，要有审批。**

## 三、异常驱动进化：从"异常"里学

**"异常驱动"是什么意思**？—— **进化的触发信号，来自"异常"**（出现了意料之外的情况）。

> **出处**：同上（逐字）——"**异常驱动进化（如防火墙 Agent）**"

**"防火墙 Agent" 是个好例子**：

```
正常运行时：防火墙按现有规则放行/拦截
   ↓
出现异常：某个新攻击模式没被现有规则拦住（漏了）
   ↓
异常驱动：Agent 观察到"漏了"，生成一条新规则
   ↓
规则引擎：评测（挡住攻击？误伤正常流量？）→ 人确认 → 持久化
   ↓
下次：同类攻击被拦（进化完成）
```

**核心思想**：**系统从"自己的失败/异常"里，长出新的规则**。

> **Go 类比**：**这像"可观测性驱动的自适应限流"**——**平时用静态限流阈值；一旦发现异常流量（漏了），就动态调整规则**。**dsh 把它做成了"Agent 主动生成规则"的闭环。**

## 四、把闭环串起来（最重要的图）

**自进化闭环 = 一个不断转的圈**：

```
        ┌───────────────────────────────────────┐
        │                                       │
        ▼                                       │
   ① 观察 / 遇到异常                            │
   （现有规则没覆盖 / 出错了）                    │
        │                                       │
        ▼                                       │
   ② 生成规则（模型提出一个"如果X则Y"）           │
        │                                       │
        ▼                                       │
   ③ 评测（跑测试 / 打分 / 回放历史）             │
        │                                       │
        ├─ 不过 → 回到 ②（改进规则）              │
        ▼                                       │
   ④ 人确认（安全闸门）                          │
        │                                       │
        ▼                                       │
   ⑤ 持久化（写进存储）                          │
        │                                       │
        └─────────────► 回到 ①（继续观察）───────┘
```

**圈里的每个"件"对应什么**：

| 环 | 对应 |
| --- | --- |
| ① 观察 / 异常 | **session 日志 / 事件**（回扣 09.3 的"日志是上下文来源"） |
| ② 生成规则 | **模型**（回扣 09.1 的 llm） |
| ③ 评测 | **另一个 agent / 测试**（回扣 04 的 subagent——"评测者"） |
| ④ 确认 | **人**（工具审批） |
| ⑤ 持久化 | **storage**（回扣阶段三的存储） |
| **执行** | **`dsh-tool-cordis`（11.3）——真去挂/卸插件** |

> **回扣**：**这个闭环用到了你几乎学过的所有东西**——日志、模型、subagent、存储、dynamic-cordis。**这就是为什么它放在最后一块。**

## 五、`dsh-tool-cordis` 在这个闭环里的位置

**别混淆两个东西**：

| | 规则引擎 | dsh-tool-cordis |
| --- | --- | --- |
| 是什么 | **大脑**（管规则：生成/评测/确认/持久化） | **手**（执行：定义/运行/停止/移除插件） |
| 谁提供 | **你要设计/搭建** | **官方现成**（11.3） |
| 关系 | 规则引擎**决定"该做什么"** | cordis-tool **负责"动手挂载"** |

**一个具体例子**：

```
防火墙 Agent 发现"某攻击没拦住"（异常）
   ↓
规则引擎生成规则："如果 payload 含 X，则拦截"（②生成）
   ↓
评测：跑历史流量回放，确认不误伤（③）
   ↓
人确认（④）
   ↓
【用 dsh-tool-cordis】define 一个"拦截 X"的插件 → run（⑤+执行）
   ↓
持久化这条规则（写进规则存储）
```

**`dsh-tool-cordis` 是"执行层"**——**规则引擎是"决策层"**。**两者配合，才叫"闭环"。**

> **Go 类比**：**规则引擎 ≈ 你的"策略中心"（决定规则）**；**dsh-tool-cordis ≈ "配置下发器"（把规则变成运行中的插件）**。**决策与执行分离——你在后端常用的模式。**

## 六、设计这样一个系统，要注意什么（五条）

基于前面的材料，给你**五条设计要点**：

| 要点 | 原因 | 回扣 |
| --- | --- | --- |
| **① 一定要有"人确认"闸门** | 自生成的规则可能危险（误伤/被利用） | 11.2 的安全底线、11.3 的审批 |
| **② 规则要"可评测"** | 没有评测，你不知道规则对不对 | 11.1 的 0002 教训（快照≠正确） |
| **③ 执行要隔离/沙箱** | Agent 写的插件可能出错 | 11.3 的 `cordis-host-runner` 沙箱 |
| **④ 要有"回滚"** | 规则生效后发现问题，得能撤 | 11.3 的"版本不可变"（加新版本取代） |
| **⑤ 规则要"可解释"** | 出问题得知道"哪条规则干的" | 11.1 的 0002 教训（要能诊断） |

> **⚠️ 最重要的一条是 ①**：**自进化系统最大的风险是"失控"**——**所以每个"进化"都要有确认点和回滚点**。

> **Go 类比**：**这跟你做"自动化运维"的纪律一样**——**自动可以，但要有审批、要有回滚、要有审计**。**"自动化"不等于"无人化"。**

```
规则引擎（大脑）  +  dsh-tool-cordis（手）  +  人确认（闸门）
```
