## 一、知识库的物理形态

- **每个知识库 = 一个 Obsidian vault**（一个目录）
- **建库校验**：若目标路径下已存在 vault → **报错拒绝**（防重复绑定）
- **插件边界（明确收窄）**：本插件**只做**「Git 仓库 → 知识库文档」这一条链路，其他能力一概不做

> **出处**：学习者口述（本会话）。

## 二、三类内容（知识库的内部结构）

| 类别             | 性质               | 内容                                                                                                                                                                   | 生命周期                                          |
| -------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| **① 史官**（变更历史） | **append-only**  | 以「**事件**」为单位，**一篇一事**：几月几号干了什么；事件 ↔ commit **多对多**（一个分支干多件事 → 拆多篇；多个 commit 合成一件事 → 一篇）。**每篇明确记录：日期、作者（谁提交的）、commit ids（一个或多个）、变更性质（新增能力 or 修改既有能力）**（2026-09-27 补全） | 只增不改（修订策略待讨论，见第五节 B）                          |
| **① 史官**（变更历史） | **人可增可改** | 以「**事件**」为单位，**一篇一事**：几月几号干了什么；事件 ↔ commit **多对多**（一个分支干多件事 → 拆多篇；多个 commit 合成一件事 → 一篇）。**每篇明确记录：日期、作者（谁提交的）、commit ids（一个或多个）、变更性质（新增能力 or 修改既有能力）**（2026-09-27 补全） | 增：Agent 产新稿、人审阅归档；改：**人工修改**（B/C 决议——佐证冲突人工裁决后改，术语替换清单确认后应用） |
| **② 快照**（当前能力） | **人可增可改** | 只记录当前这一刻 Master 具备的能力/功能点 | 增/改：随史实追平滚动更新（D2 按域增量）；⛔ **硬约束：史实未追平，快照不允许生成、不允许更新** |

**数据源优先级**（生成与检索共用同一序）：

| 优先级 | 来源 | 角色 |
|---|---|---|
| **P1** | **代码仓库**（Master 当前现状 + 史实） | **永远第一优先级** |
| **P2** | 方案文档、TAPD 需求文档 | 辅助解释代码 |
| **P3** | 群聊、会议纪要 | 旁证、零散线索 |

> **出处**：学习者口述（本会话）——"代码永远是第一优先级，其次方案文档、TAPD，第三是群聊、会议纪要。搜索的时候也按这个优先级。"
> **2026-09-27 范围裁定**：P2/P3 旁证为**被动存储**——"用户提起让存才存，没提就留白"，插件**不做主动抓取**（原「经 MCP 抓取 TAPD/内部 Wiki」的设想作废）。
> ⚠️ 注：TAPD / 内部 Wiki 仅作为「可能被存入的旁证类别」记录在此；**接入细节（网关/凭证/API）如后续展开，属内部资料，应放 `dsh-learn/doc/`，不进本知识库**（遵守 AGENTS.md）。

## 三、质量要求（每篇文档的验收标准）

1. **人类可读**——每篇文档一定是人为可读的
2. **完整**——每篇文章是一个完整的事
3. **有依据**——每篇有对应出处（commits / 文档 / 会议）
4. **术语一致性（术语表机制）**——生成中翻译不准、人为修正过的词（例：某术语曾被随意译作 zero card），**记录成术语表**；后续生成遇到同一词，必须沿用人为修正后的译名

> **出处**：学习者口述（本会话）。

## 四、审阅闭环（生成节奏控制）

```
Agent 导入 → 检测是否已更新到最新（游标）
   └─ 未最新 → 逐篇生成史实（每批最多 5 篇）
        └─ 满 5 篇 → 停下 → 徽章提醒（"已生成 5 篇待审"）
             └─ 人工逐篇审阅
                  ├─ 审阅 OK → 归档存入
                  └─ 有问题 → 不允许归档（打回）
史实全部追平 → 才允许生成快照（当前 Master 能力）
   └─ 新项目同样：先史实、后快照
```

> **出处**：学习者口述（本会话）——"最多同时生成 5 篇……必须人点进来，小徽章提醒，每篇必须审阅，OK 才归档""史实没记完，当前快照这篇文章不要出来，只有赶到最新 Master 才写快照"。

## 五、洞与决议（2026-09-27 学习者裁决，C–F 全部议定）

| # | 问题 | 决议 |
|---|---|---|
| **A** | **历史体量 vs 审阅节奏** | ✅ **全量精读，不分档**。依据：①审阅**越归档越快**（术语表、模板、上下文累积，负载递减）；②审阅标准是「看大概意思」；③不赶时间 |
| **B** | **append-only vs 晚到证据** | ✅ **冲突 → 面板弹窗 → 人工裁决修改**。P2/P3 永远只是佐证，代码 P1 永远是真源。优先级：**P1 代码 / P2 方案文档 + TAPD / P3 群聊、会议纪要、会议笔录** |
| **C** | **术语变更的回溯** | ✅ **C3 替换建议清单**（2026-09-27 拍板）：术语表更新 → 扫描存量 → 生成待替换清单（哪篇哪段用了旧译名）→ 人工确认后应用 + 文末留修订记录。**绝不静默改历史**，每一处改动经过人的眼睛。快车道：清单支持「全部应用」，语义判定交 Agent，人兜底 |
| **D** | **快照的更新策略** | ✅ **D2 按仓库分篇 + 增量更新**（2026-09-27 拍板）：硬约束重申——**史实未追平，快照不允许开始、不允许更新；史实推进到最新 master，才更新快照**。快照锚定「截至 commit X」（X = 已追平点，写进 frontmatter `as-of`）。vault 按仓库→代码层级分目录（史实 / 快照 / 方案与 TAPD / 会议群聊），每层级可按具体模块细分子目录、可嵌套多层、分别迭代（提案见第六节） |
| **E** | **事件拆分权** | ✅ **E3 批次计划前置确认**（2026-09-27 拍板，按 AI 提案）：生成前先出**批次计划**（本批每篇的标题 + 各自依据的 commits），人确认/调整后再生成。结构决策前置（先 review 接口设计，再写实现），内容打回率下降 |
| **F** | **游标怎么存** | ✅ **总表（大纲）+ 文章级溯源**（2026-09-27 拍板）：每篇史实文章明确记录**谁提交的、哪个分支、哪个/哪几个 commit id、时间点**（frontmatter）；vault 最外层有一张**总表（大纲）**：每篇文章对应哪些 commits、已推进到哪里。实现上（AI 补充）：总表即游标的人读版——cursor 从已归档文章推导、可重建；快路径用 master hash 取增量，hash 失效（rebase/force push）时用 patch-id 内容指纹兜底找回等价点 |

> **决议出处**：学习者 2026-09-27 口述（本会话）。语音歧义解读（已确认）：「快招」=快照、「卡密达」=commit（学习者 2026-09-27 确认）、「TIBD/TBD」=TAPD。

## 六、vault 目录结构（多仓库版）

> 依据：D 决议「vault 按仓库→代码层级分目录，可多级子目录、分别迭代」+ 仓库在上层、代码层级在仓库下——仓库是物理隔离单位，代码层级是仓库内的代码分层。详见 [[11 物理隔离与磁盘布局——三级目录与共享clone#10-史实/ 的目录层级]]。

```text
<vault>/                              ← 项目级（一个项目可绑 N 个 git 仓库）
├── 00-总表/
│   ├── 仓库登记簿.md                 ← 绑定表：一行一仓库 (repo URL, subpath, branch, 启用状态)
│   ├── 进度总表.md                   ← 项目级汇总：每仓库一行（追平状态 / 落后 N commits / 待审 N 篇）
│   └── 术语表.md                    ← C 决议的术语登记处（旧译名 → 新译名 + 出处）
├── 10-史实/（append-only，一篇一事）
│   └── @<repoA>/                     ← 第一级：仓库
│       ├── _追踪.md                  ← per-repo 明细游标（本仓库追到哪、已归档文章清单）
│       ├── <主领域>/                 ← 第二级：主领域（代码层级）
│       │   ├── <事件>.md            ← frontmatter: 日期/作者/分支/commits/patch-ids/变更性质(新增|修改)
│       │   └── <子领域>/             ← 第三级：子领域（需要拆时才建）
│       │       └── <事件>.md
│       └── <主领域>/
│           └── <事件>.md
├── 20-快照/（随史实追平滚动更新）
│   └── @<repoA>/                     ← 第一级：仓库
│       └── 当前能力.md               ← frontmatter: as-of: {repoA: c1x}
├── 30-方案与TAPD/（P2 旁证，项目级；被动存储：用户让存才存，留白是常态）
└── 40-会议与群聊/（P3 旁证，项目级；被动存储，同上）
```

要点：
- **总-分两层游标**：`00-总表/进度总表.md` 只做**项目级汇总**（每仓库一行）；**明细游标 `_追踪.md` 放各仓库的 `@<repo>/` 地盘内**，上下文聚簇。`_` 前缀置顶排序，与事件文档区分
- **仓库登记簿不分子目录**：静态绑定清单，一行一仓库，天然按行组织
- **溯源消歧**：目录上下文（`@repoA/`）即仓库作用域，frontmatter 的 commits 在此消歧；**跨文件引用（总表、快照依据）一律写 `repoA:abc1234`**
- **跨仓库联动事件**：按仓库**分开写**（每篇溯源单仓库，游标推进干净），篇间 wiki-link 互链
- **超大 diff 的拆分**：一个 commit id 可被**多篇文章共享**（「一篇一事」细化到「一事的 diff 也可分片」）——不砍内容、不强行综合，边读边写、分段落笔
- **检索红利（scope filter）**：「做方案只读某仓库」= 路径前缀过滤（`10-史实/@repoA/**`），N 个仓库互不干扰
- **审阅闭环**：agent 直接写归档路径 10-史实/，审阅通过后确认归档（文件不搬运，只更新 meta 状态）
- **编号前缀**（00/10/20/…）：排序稳定 + 留间隔，后续插目录不用重排

## 七、激活与运行时（2026-09-27 议定）

### 运行形态：Host 后台 job + 固定生成配置（非独立 Agent 形态）

**裁定**：追史工人**不做**成用户可见/可对话的独立 Agent（Preset）。理由：用户永远不该「跟史官聊天」，只该点按钮看结果——能力封装在插件内比暴露 Agent 形态更稳。

**稳定性靠三样版本化资产钉死**（随插件发布，用户不可改）：

| 资产 | 作用 | 防什么 |
|---|---|---|
| ① 提示词模板（固定） | 角色、文章骨架、引用规则、few-shot 范文 | 结构漂移 |
| ② 输出 schema（强制） | frontmatter 字段 + 章节结构 | 格式不合格的草稿**进不了待审列表**，自动打回 |
| ③ 模型与参数（锁定） | 生成模型 + temperature 固定于插件配置 | 同批内风格抖动 |

**三层稳定性承诺**（诚实边界）：格式层（schema 校验，稳）、结构层（模板+few-shot，稳）、内容层（模型固有噪声，靠人工审阅兜底——审阅闭环正是为此设计）。
**插件升级纪律**：换生成模型或调提示词必须同步版本号，「文章风格变化」永远可追溯到具体插件版本。

### 上下文纪律：按「单篇」装箱，不按「整库」装箱

单篇生成上下文只装：该事件的 commit diff + 该仓库最近若干篇已归档史实 + 术语表。**跨批上下文靠已归档文章传递**（「越归档越快」飞轮的技术本质），主会话不被污染。几千 commit 也不会爆炸。

### 激活流程（完整生命周期）

```
用户点「开始/继续追史」（面板按钮）或对话指令
→ Host 起 job（持久化，Web UI 关闭可继续）
→ 读总表游标 → git fetch → 算增量
→ E3 批次计划（标题+commits+变更性质）→ 人确认
→ 逐篇生成（每篇独立小上下文）→ 写归档路径 10-史实/
→ 满 5 篇 → 停 → 徽章提醒
→ 人工逐篇审阅（批准/打回）
→ 审阅通过 → 确认归档（更新 _追踪.md + 进度总表）
→ 循环至追平 → 触发快照更新（同样走审阅）
```

### 稳定提示词的机制落点（2026-09-27 核实后补全，完整版迁至 [[03 运行时机制——skill载体、job执行与Git集成]]）

**三层组合**（出处：`docs/subsystems/skills.zh.md`，master `0d1f50007f`）：

| 层 | 实体 | 职责 |
|---|---|---|
| **载体** | **skill**（bundled，随插件包分发；`modelInvocable: false, userInvocable: false`） | 提示词模板 + few-shot 范文资源，版本化随插件发布——「稳定提示词」的物理宿主 |
| **执行者** | **Host 后台 job** | 管批次/游标/断点；`ctx.skills.get()` 读 skill 正文，装配上下文（diff + 近期史实 + 术语表），发起生成 |
| **容器**（可选） | subagent 或直接 LLM 调用 | 单篇生成的一次性沙箱，跑完回收，**不持有人格** |

关键依据：skill 的调用策略三元组——`{modelInvocable: false, userInvocable: false}` 的 skill「只能由受信的 `ctx.skills.get()` 调用方获取」（skills.zh.md：*"两个字段均设为 false 后，这个 skill 只能由受信的 ctx.skills.get() 调用方获取"*）——模型看不见、用户看不见、不会乱触发。

**不选 Preset（独立 Agent）的理由**：Preset 是用户可切换、可对话的形态，人格会被会话上下文污染；追史工人不该被对话。
**不选裸 subagent 的理由**：subagent 委派时 prompt 由委派方现拼，没有模板锚就没有稳定性；subagent 只作执行容器。

**语义边界**：普通 skill（modelInvocable: true）触发权在模型；本插件反转为**代码驱动**——生成时机由 job 的游标/批次逻辑决定（确定性逻辑），模型在普通会话里看不见此 skill，永不乱触发。
