## 一、用法二是什么：三个独立的知识库（2026-09-27 归并版）

| 库            | 内容单元性质                  | 采集方式 | 分篇             |
| ------------ | ----------------------- | --------------- | -------------- |
| **方法论与架构**   | 原则 + 代码证据：判断/为什么/怎么拆分 | **主动提交**（口述→起草→审） | [[05 我的方法论与架构]] |
| **我的编码习惯**   | 特征清单：习惯 + 证据（累积归纳）     | **双通道**（唯一）：主动声明 + 被动发现（job 扫存量 + 会话观察增量） | [[06 我的编码习惯]]  |
| **API 调用案例** | 卡片：片段 + SDK/版本 + 场景 + 坑 | **主动提交**        | [[07 API调用案例]] |

**归并理由（学习者 2026-09-27）**：不拆太碎——好代码的「好在哪」本质是一条方法论，片段只是**证据**；「新项目怎么架构、目录怎么拆分」与「这段代码为什么好」是同一类知识（设计判断力）。方法论是主键，代码是外键。

**采集哲学（2026-09-27 统一裁定）**：**编码习惯（2b）是唯一双通道**（主动声明 + 被动发现：job 扫存量 + 会话观察增量），**其余全部纯主动提交**——被动观察只发生在「可从 Git diff 直接观察」的内容上（机器看得见的）；一切涉及判断、品味、思想的内容，判断权全在人，Agent 只做记录员/起草员。**无论哪条通道，落正式区前都过同一道人工审阅闸**。

**与用法一的本质差异**：用法一的文章是「**事件叙事**」（重溯源、编年）；用法二的条目是「**卡片/原则**」（重检索、重复用）。两类内容性质不同，schema 分开设计，但共享基础设施。

**边界规则（2b 与 05）**：能从 diff 观察到的归 2b（编码习惯）；需要解释「为什么」的归 05（方法论）。如「永远先写测试」若只是行为 → 2b；若含「因为」的理由 → 05。

## 二、共享基础设施（插件工程红利）

三个个人库 + 项目史官库**共用同一套底层**，插件只做一次：

| 共享物 | 说明 |
|---|---|
| vault 物理结构约定 | `00-总表/`、`10-内容/`、`50-草稿区/` 编号前缀体系 |
| 审阅闭环 | 草稿 → 徽章 → 人审 → 归档（同 02 第四节） |
| 术语表机制 | 同 02（C 决议） |
| skill 载体 + job 运行时 | 同 03（隐藏 skill 做提示词锚；扫描归纳类任务走 job） |
| 检索层（未来 09） | 统一入口，跨库检索 |

**个人库的差异面**：不绑 Git 仓库、无追史游标、无快照区、无项目能力域 taxonomy（分类轴是语言/类别/SDK 名/方法论域，不是项目能力域）。

## 三、采集机制总览（细节在分篇）

|           | 触发              | 运行时                       |
| --------- | --------------- | ------------------------- |
| 方法论与架构   | 用户口述方法论 / 指定好代码片段（作 evidence）→ Agent 起草 | 会话内工具调用（显式提交工具）           |
| 2b 编码习惯   | **主动**：用户显式声明习惯  **被动**：① 用户点「归纳」→ job 扫 Git 历史 ② 会话中发生提交时静默观察 | **job**（与追史 job 同构，复用 03）+ 会话内观察 |
| API 案例 | 用户主动说「存」       | 会话内工具调用（显式提交工具）           |
