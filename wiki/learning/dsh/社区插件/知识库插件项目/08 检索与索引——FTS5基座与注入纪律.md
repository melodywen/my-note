# 08 检索与索引——FTS5 基座与注入纪律

> [!info] 文档状态

## 一、选型决议：SQLite FTS5 基座（2026-09-27 确认）

| 层 | 决议 | 依据 |
|---|---|---|
| **V1 基座** | SQLite FTS5 + trigram 分词 + BM25 排序 | 零外部服务（进程内嵌入式，`better-sqlite3`/`node:sqlite` 默认含 FTS5）；单文件部署 |
| **V2 可选** | 叠加本地 embedding（sqlite-vec / 本地模型）+ RRF 融合 | 等「语义搜不到」痛点真出现再上 |
| **永不丢的底** | 源（vault markdown）与索引（.db）分离；索引可全量重建 | 00 篇「源与索引分离」原则 |

**为什么不是纯 grep**（调研修正记录）：grep 的致命伤是 **Agent 消费时的 token 数量级差距**——[agentmemory 评测](https://blog.gitcode.com/c3f94a4db6cbebfce9980adc86825438.html)：grep 全量 19,462 tokens/查 vs 检索式 1,571（省 92%）；Recall@10 55.8% vs 55.9%（几乎持平）。另 [BM25 给编程智能体降 30% token 的实测](https://pasqualepillitteri.it/zh/news/10753/bm25-jiang-di-biancheng-zhinengtoken)：7,536 文件仓库 token -29.2%、执行时间 -34.2%、成功率不变。

**社区形态印证**：[handrew/knowledge-base-mcp](https://lobehub.com/fr/mcp/handrew-knowledge-base-mcp)（FTS5+向量混合）、[khg420/knowledge-mcp](https://lobehub.com/es/mcp/khg420-knowledge-mcp)（Go，BM25 + CJK bigram，段落 chunk）、[QMD](https://pypi.org/project/qmd/0.1.0/)（BM25+向量+重排，路径级 context 元数据）——成熟项目几乎全是「FTS5/BM25 基座 + 向量可选」。纯 grep 只有最简 MCP 包装（[ripgrep-mcp](https://github.com/mcollina/mcp-ripgrep)）。

## 二、FTS5 机制（黑盒拆解）

### 存储侧：倒排索引

写入时 tokenize → `map[token] → [docID:位置...]`。查询「退款」= 一次倒排表查找，O(1) 定位文档集，不扫全文。

### 查询侧：BM25 排序

`score ≈ TF饱和 × IDF × 文档长度归一`——稀有词权重高、高频词边际递减、短文档信息密度高。

### 中文分词：trigram（已确认）

- 默认 `unicode61` 中文基本废（整句一个 token）
- **trigram**：3 字滑窗，子串可搜、零词典依赖、SQLite 内置——「退款流程」可被「流程」命中
- 未来可换 jieba 外置分词（索引重建即切换，成本仅重建时间）

## 三、索引 schema 设计（V1）

```sql
CREATE VIRTUAL TABLE knowledge_base_docs USING fts5(
  title,          -- 文件名/标题（加权高）
  path,           -- 相对 vault 的路径（scope filter 用）
  frontmatter,    -- frontmatter 原文（溯源字段可搜：commits/repo/as-of）
  body,           -- 正文
  tokenize='trigram'
);

-- 查询示例：标题命中权重 ×10
SELECT path, snippet(body, 0, '「', '」', '…', 12)
FROM knowledge_base_docs
WHERE knowledge_base_docs MATCH @query
ORDER BY bm25(knowledge_base_docs, 10.0, 1.0, 2.0, 1.0)
LIMIT @k;
```

**索引列权重**（已确认）：title(10) > frontmatter(2) > path/body(1)——搜「存储选型」优先命中方法论篇的标题；搜 `repoA:abc1234` 走 frontmatter 列精确溯源。

### 索引同步时机（架构红利）

**审阅闭环即索引刷新点**：正式区只能经「归档动作」改变 → 归档/修订/删除文章时同步 upsert/delete 索引行。不存在「索引悄悄失效」——源的改变必经我们的代码路径。

### 术语表作为查询扩展器（已确认）

查询流水线：`用户查询 → 查术语表（记忆→memory 等人审映射）→ 展开查询词 → FTS5`。人审过的同义词映射补词法检索的语义缺口——V1 的「穷人的语义检索」。

## 四、检索工具面（scope 单工具族，已确认）

| 工具 | 签名（示意） | 说明 |
|---|---|---|
| `knowledge_base_search` | `(scope, query, limit?)` | scope 枚举：库 id（项目库/方法论/习惯/API 案例/all）；返回**摘要行**：标题+路径+snippet 预览 |
| `knowledge_base_read` | `(path)` | 按需读全文（两级火箭第二级） |

**两级火箭注入纪律**（已确认）：

1. **第一级**：`knowledge_base_search` 只回摘要行（标题+路径+snippet 窗口）——token 有界
2. **第二级**：Agent 按需 `knowledge_base_read` 具体文章
3. **单次注入上限**：一次任务上下文中 knowledge_base_read 的篇数/token 上限（默认 N 篇，可配）
4. **例外**：编码习惯库**全量注入**（它天生是 AGENTS.md 型内容，短小、全相关）

## 五、能力边界（诚实声明）

| 场景 | FTS5 表现 |
|---|---|
| 「存储选型」（标题命中） | ✅ 主场 |
| `"物理隔离"`（短语） | ✅ |
| `repoA:abc1234`（frontmatter 溯源） | ✅ |
| `退款 NEAR/5 灰度`（邻近） | ✅ |
| 「怎么让项目变快」→ 想命中「性能优化」 | ❌ 语义缺口——术语表部分缓解，彻底解决待 V2 向量 |
| 拼错容错（refnud） | ❌（spellfix1 可加，暂不） |

## 六、磁盘布局（与 11 篇联动）

```
vault（源）                          索引（派生物）
~/kb/<库名>/...                      <插件 storage>/index/<库名>.db
                                    （11 篇定具体 storage domain）
```

索引不进 vault（Obsidian 打开不看到杂文件）；删 .db 从 markdown 全量重建，源无损。
