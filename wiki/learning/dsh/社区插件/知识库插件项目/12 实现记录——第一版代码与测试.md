## 四之四、HTTP API 通道 405 → 200（2026-09-28 修复 ✅，两连根因）

面板「新建知识库」一直空转：浏览器半侧 `fetch('/knowledge-base/api/listLibraries')` 得到 405（webServer 全局 fallback 对非 GET 一律 405，即路由从未注册）。用「最小替身 probe + 逐段 stderr 探针」定位出**两个独立 bug**：

| # | Bug | 根因（源码级） | 修复 |
|---|---|---|---|
| 1 | `apply(ctx, undefined)` → `config.root` TypeError | `vendor/cordis/src/fiber.ts:52` `resolveConfig`：`if (!runtime.Config) return config`——插件**不导出 Config schema 时，patch 行没写 config 就是裸 `undefined` 传给 apply**。之前把 schema 写成了 `loadConfigSchema()` 动态函数（为了单测可独立跑），loader 看不到 | 导出**静态** `export const Config = z.object({...})`（schemastery 顶层静态 import；单测兼容：peer 依赖在 profile 里天然满足）。better-sidebar 同款（`export { Config, apply, inject, name }`） |
| 2 | `ctx.knowledgeBase = service` 抛 `cannot set property without provide` | `vendor/cordis/src/reflect.ts:178`——Context 是 Proxy，**插件 fiber 内给未 provide 的属性赋值直接抛**。异常被 apply 自己的 `.catch(err => ctx.logger.error)` 吞进 logger（dsh web 的 logger 不落 stdout，启动日志完全静默） | 改 `ctx.provide('knowledgeBase', service)`——这是 cordis 的正式服务声明 API（web-app 的 `ctx.provide(WEB_RUNTIME_SERVICE, runtime)` 同款） |

**为什么这么难查**：两个 bug 叠加产生「幽灵挂起」假象——bug 1 修掉前，apply 里 `create enter → after os` 打印后链路死掉（`config.root` 炸），错误进 logger 不落盘，看起来像 `mkdir` 挂起（还 sample 了进程栈，主线程事件循环其实完全健康）。bug 2 同样静默。**方法论教训：dsh 插件里所有 async 链的 catch 必须先 `process.stderr.write` 兜底**，logger 在 web 进程不可见。

**修复后的验证矩阵（2026-09-28，真实 `dsh web` :3860-:3863 全实测）**：

**坑 3（本次实测抓出）**：行级 `inject: [webServer, webRuntime, tools]` 在 headless profile（无 webServer/webRuntime）让 fiber 永远 PENDING，**整个插件树 boot 失败**：

```
Error: dsh: plugin tree failed to load: dsh: 1 entry did not activate
@melodycchen/dsh-knowledge-base: pending (waiting for services: webServer, webRuntime)
```

修复：行级 inject 只声明**所有宿主都提供**的服务（tools）；webServer/webRuntime 改回 `apply()` 内 `ctx.inject()` 软依赖——非 web 宿主上回调自然不触发、路由不注册、无副作用。**教训：行级 inject = 硬依赖门闩（fiber 在服务就位前不激活，宿主没有就永远 pending），只放通用服务；宿主特有服务一律软依赖。**

## 四之六、vault 同步远端改必选 + 多库共享远端（2026-09-28 ✅，学习者设计演进）

**起因**：学习者看面板截图指出「Git 远端为什么是可选的？文档里是必选，而且多个知识库可以用同一个 git，写到不同的目录下，都能进行 Git 提交」。核对文档：R5「绑定 Git 仓库 URL」、R6「同 URL 不同路径 = 不同知识库」、11 §0「建库时绑定它自己的 Git 远端」——第一版实现把远端软化成可选且**未申报**（流程疏漏，本节补记）。

**设计演进（学习者 2026-09-28 口述，AI 落地）**：11 §0 原设计「一库一远端」演进为「**多库可共享同一远端仓库，各写各的子路径（vaultPath），都能 commit/push**」。

**落地方案（共享工作树模型）**：

- 本地布局：`<root>/remotes/<远端指纹>/` = 每个远端一个**工作 clone**（init + remote add，网络延迟到首次 fetch/push）；库内容 = clone 内 `<vaultPath>/00-总表/…` 目录树（vaultPath '' = 仓库根）
- commit/push 跑在整个 clone 上（git 原生处理多目录变更），commit message 带 `[库名]` 归因
- R4 隔离重审：内容层面各库各子目录互不干扰（scope 边界 assertInsideVault 照旧生效）；同一 clone 的 .git 共享是存储实现细节，不破坏内容隔离；Obsidian 直接打开 clone 目录能看到全部库（更方便）
- 新布局下磁盘结构：`vaults/` 弃用（保留目录兼容旧数据不迁移），`remotes/` 为内容真身
- registry 损坏重建改为扫描 `remotes/<fp>/**/00-总表/_库.json`（限定深度 3，跳过 .git）

**校验**（createLibrary 服务端强制）：vaultRemote 必填（URL 过白名单）；同远端同 vaultPath 冲突检测（报错提示换路径）；vaultPath 规范化 + 越界拒绝（绝对路径 / `..`）。

**踩坑**：第一版尝试用 git sparse-checkout 做「本地库目录 ↔ 远端子路径」映射——和本地工作树语义打架（`git add` 拒绝 sparse cone 外文件），放弃回退。教训：**git 的提交路径永远相对仓库根，要在远端子目录看到内容，本地工作树就必须有同样的目录结构**；「本地平铺 + push 时映射路径」在 git 里不存在（subtree push 除外，复杂度不值）。

**白名单补充**：vault-internal 集新增 `config`（写 sparse 时用的，现保留）与 `fetch`；git.test.ts 全过（tracked repos 侧白名单未动）。

**验证**：34/34 全过（含 e2e 11 步：建库→submit→adopt→共享 clone git log 有 adoption commit）；真实服务端到端：同远端建两库（methodology / coding-habits 两个子目录）→ 同路径冲突拒绝 ✅ → 缺远端拒绝 ✅ → 删光库后 clone 随之清理 ✅。
