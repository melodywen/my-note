# 13 调试实录——UI 样式三层失效的排查与修复

> [!info] 文档状态
> - 状态：**已完成**（2026-09-28）
> - 前置：[[12 实现记录——第一版代码与测试]] 四之八（UI 按官方 web-styling 规范重做）
> - 代码位置：`dsh-learn/plugins/knowledge-base/build-client.mjs`、`src/panel.module.css`

> 2026-09-28。一次「样式完全失效」的排查，挖出了三个互相独立、又互相掩盖的 bug。
> 记录价值不在结论（结论就三行），而在**排查路径**——哪一步走对了、哪一步绕了远路。

## 一、现象与误导

用户截图拍桌：面板全是裸文本堆叠，零样式。第一反应是「CSS 没注入」——错。
真实情况是三层各自坏了一层，坏法还不一样：

| 层 | 应然 | 实然 | 检查手段 |
|---|---|---|---|
| ① 样式表注入 | `<style data-plugin-css>` 挂进 head | ✅ 正常（107 个 style 标签里有我们那个） | `document.querySelectorAll("style")` 找内容含 `.lib-card` 的 |
| ② className 挂载 | `h1.className === "title"` | ❌ 空字符串 | `document.querySelector("h1").className` |
| ③ 选择器匹配 | `.libIcon` 命中 `.lib-icon` 规则 | ❌ camel vs kebab 不匹配 | 遍历 `document.styleSheets` 找规则再 `el.matches(sel)` |

**教训：排查分层的意义**。若一开始就同时改「CSS 导出」和「类名大小写」，两个 fix 混在一次 build 里，中间态没法归因。

## 二、Bug ①：esbuild `__toESM` 互操作吞掉导出

**源码**（build-client.mjs 的 CSS 模块插件）：

```js
module.exports = { classes: __classes, inject: __inject }
```

**打包后**（dist/client.js）：

```js
var import_panel = __toESM(require_panel(), 1)
import_panel.default.inject()          // ✅ 有——inject 是顶层属性
import_panel.default.tabBar            // ❌ undefined——藏在 .classes 下面
```

`__toESM(mod, 1)` 的互操作规则：若模块没有 `__esModule` 标记，就把整个 `module.exports` 挂成 `.default`。于是 `import css from './panel.module.css'` 里的 `css` **就是 exports 对象本身**——`css.inject()` 能用（顶层属性），但 `css.tabBar` 拿不到（真实位置在 `css.classes.tabBar`）。React 拿到 `className={undefined}`，渲染出空 class。

**修复**：导出对象本身做成转发 Proxy——任何属性名都直接返回类名：

```js
const __exports = new Proxy({}, {
  get: (_, name) => {
    if (name === 'inject') return __inject
    if (name === 'classes') return __classes
    if (name === 'default') return __exports   // __toESM 再包一层也安全
    if (name === '__esModule') return undefined
    return typeof name === 'string' ? name : undefined
  },
})
module.exports = __exports
```

三条访问路径全兼容：`css.tabBar`（源码风格）、`css.classes.tabBar`（官方管线契约）、`css.default.tabBar`（互操作再包装）。

**通用教训**：写 bundler 插件 = 接受它的互操作语义。esbuild 的 CJS↔ESM 转换不是透明传递，`.default` 指向会变。导出「可自省的 Proxy」比导出「固定形状的对象」抗包装。

## 三、Bug ②：kebab/camelCase 类名映射两侧不一致

修完 ① 后 className 正常了（`h1.className === "title"`），但 `.libIcon` 元素 `display` 仍是 `inline`——规则 `.lib-icon { display: flex }` 存在于样式表，就是不命中。

原因：原 build 脚本有 `__kebab` 转换（`libIcon` → `lib-icon`），重写时删掉了（改恒等映射），但 **panel.module.css 里的类名还是 kebab-case**。TSX 引用 `css.libIcon` → class `libIcon`，选择器 `.lib-icon`，永远匹配不上。

**修复**：CSS 全部类名统一 camelCase，与 TSX 引用和恒等映射严格一致：

```bash
sed -i '' -e 's/\.page-inner/.pageInner/g' -e 's/\.lib-card/.libCard/g' … src/panel.module.css
```

**通用教训**：CSS Modules 的类名映射策略必须**两侧严格一致**——要么全 camel（TSX 惯例 + 恒等映射，最简），要么全 kebab（CSS 惯例 + kebab 转换）。混用必炸。选恒等映射的额外好处：样式表里的选择器和 class 属性肉眼可对照，调试成本最低。

## 四、排查工具链（本次实测有效的命令）

```js
// ① 样式表注入了吗？（找内容而不是找标签，避免同名干扰）
[...document.querySelectorAll('style')].some(s => s.textContent.includes('.lib-card'))

// ② className 挂上了吗？
document.querySelector('h1').className            // 期望 "title"

// ③ 规则在样式表里吗？元素匹配吗？（两者分开查）
for (const sheet of document.styleSheets) {
  for (const rule of sheet.cssRules) {
    if (rule.selectorText?.includes('lib-icon')) console.log(rule.cssText)
  }
}
el.matches('.lib-icon')                            // false = 大小写不匹配

// ④ 计算样式兜底（最终真相）
getComputedStyle(el).display                       // "inline" = 规则没命中
```

**教训**：`getComputedStyle` 不会骗人，截图看图会。模型描述截图时可能「脑补」样式存在——以 DOM/计算样式为准。

## 五、另一个教训：构建通过 ≠ 运行时正确

整个期间 `npm run build` 全绿、`npm test` 34/34 全过——测试覆盖的是 host 侧（草稿流、搜索、git 安全），client 侧的 CSS 导出契约**零测试覆盖**。Bug ①② 都活过了 CI。

对构建管线改动的最小验证闭环：

```
build → 真实宿主加载 → eval 检查关键 DOM 属性（className / computed style）→ 截图
```

这四步一步都不能省。build 绿只说明「能打包」，不说明「打包出来的东西在宿主的模块系统里行为正确」。
