# 16 审阅队列管控——逐篇生成与审阅

> 本文记录审阅队列的行为：逐篇生成、逐篇审阅、打回改重写、采纳加顺序锁定。

---

## 一、问题背景

### 1.1 队列无上限堆积

- `planBatch` 每轮取 5 个 commit，但 `autoContinue` 默认开——采纳一篇就自动追下一轮 5 篇
- 队列里很快就堆了 11 篇待审，审不过来

### 1.2 打回 = 永久丢失

- 原设计的 `reject` 把草稿标记为 `rejected`（删除线显示），但游标 `lastChased` 已经前进
- 被打回的 commit 不会被重新追史——等于这个 commit 的史实永久缺失
- 用户其实要的是"重新生成"，不是"永久丢弃"

### 1.3 agent 草稿不进审阅队列

- `chaseOneCommit` 让 agent 直接写 .md 到归档路径 10-史实/<域>/@<repo>/
- `DraftStore.list()` 只读 `.meta.json` sidecar
- agent 写的草稿没有 meta → 不出现在审阅队列里

---

## 二、修正方案

### 2.1 逐篇生成、逐篇审阅

生成一篇就停下来，进入审阅队列。审阅通过后才能开始下一篇。队列自然不超过一篇，不需要五篇上限。

### 2.2 打回 → 重写

| 打回（reject） | 重写（rewrite） |
|---|---|
| 删除 body，meta 标记 `rejected` | 删除 body + meta，干净清除 |
| 游标不动，commit 永久跳过 | 游标不动，commit 重新进入待追 |
| 留在底部"已打回"区 | 无留痕 |
| 不重新生成 | 立即开新会话追同一个 commit |

重写流程：
1. 删除旧草稿的 .md + .meta.json
2. 立即调用 `chaseOneCommit` 追同一个 commit
3. 新草稿进待审队列

### 2.3 顺序采纳

每个仓库各自排序，不能跳过：

```
repoA: M1(待审) → M2(待审) → M3(待审)
必须先采纳 M1，才能采纳 M2，再采纳 M3

repoB: N1(待审) → N2(待审)
repoB 和 repoA 独立，各自排序
```

- M3 的 adopt 按钮在 M1、M2 未采纳前 disabled
- M1 采纳完后 → 自动生成 M2

### 2.4 游标与审阅分离

游标（`lastChased`）记录"追到哪了"，和"审到哪了"是两回事。

```
事情链:  M1 → M2 → M3 → M4 → M5 → (M6 待生成)

追史跑到 M5（游标指向 M5）✓
审阅只到 M1（M2-M5 都待审）

对 M2 点"重写":
  - 游标不动，还是 M5
  - M2 草稿删除，重新追 M2 生成新草稿
  - M3/M4/M5 不受影响

M5 采纳完 → M6 开始生成
```

## 三、实现要点

### 3.1 数据模型

`DraftEntry` 字段：
- `commitHash?: string` — 该草稿追的 commit hash
- `repoName?: string` — 所属仓库名

`DraftStatus`: `'pending' | 'adopted'`

### 3.2 DraftStore

| 方法 | 说明 |
|------|------|
| `rewriteDraft()` | 删 body + meta，返回 commitHash |
| `save()` | 签名加 `extra?: { commitHash?; repoName? }` |
| `reconcileOrphans()` | 扫描 `10-史实/` 为无 meta 的 .md 创建 meta |

### 3.3 chaseOneCommit 后置处理

agent 完成后调用 `reconcileOrphans`，为 agent 直接写的 .md 创建 meta.json：
- commitHash 从 .md frontmatter 的 commit 字段提取
- repoName 从 binding.name 传入

### 3.4 顺序采纳检查

`adoptDraft` 前检查：
1. 从 DraftEntry 拿到 commitHash 和 repoName
2. 查 ledger（workspace/repos 的 working clone）中此 hash 之前的所有 node
3. 对每个前置 node，检查是否有已采纳草稿（formal file 存在）
4. 有未采纳的前置 node → 拒绝，提示"请先采纳 <date> <title>"

## 四、设计决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 生成模式 | 逐篇生成审一篇 | 串行保证上下文准确，第一篇偏了后面全偏 |
| 重写触发时机 | 立即开新会话 | 删一加一，净增 0 |
| 顺序采纳范围 | 每仓库各自排序 | 不同仓库的 commit 无时间先后关系 |
| 游标是否回拨 | 不回拨 | 追史进度和审阅进度分离，重写只影响待审状态 |
