# 17 连贯性测试——全按钮产品视角验证与文档勘误

> 本文记录如何对知识库插件做端到端连贯性测试：站在产品视角，覆盖面板上每一个用户可操作的按钮，验证全链路数据前后一致、所有交互有反馈、整个体验连贯友好。
> 过程中发现设计文档与代码的 6 处不一致，已全部处理（见第五节）。

---

## 一、为什么要做连贯性测试

现有 56 个单元测试覆盖的是**单个模块的正确性**——DraftStore 的 CRUD、git.ts 的白名单、history.ts 的批次规划。但用户面对的是一个完整产品：打开面板 → 看到库列表 → 点进某个库 → 追史 → 审阅草稿 → 采纳归档 → 搜索验证。这条链路上任何一个按钮失灵、任何一处数据不一致，产品体验就断了。

单元测试的盲区：

| 盲区 | 说明 |
|------|------|
| 按钮可用性 | 每个按钮在什么状态下可点、什么状态下灰显，前后是否一致 |
| 数据一致性 | 面板显示的数字（pending/adopted/behind）和磁盘实际文件数量是否对得上 |
| 操作链路连贯 | 追史 → 草稿落盘 → 审阅 → 归档 → 搜索可检索，每一步的输出是下一步的输入 |
| 状态转换 | 空库 → 追史中 → 待审 → 部分采纳 → 追平，每个状态下面板显示是否合理 |
| 错误反馈 | 顺序采纳拦截、5 篇上限冻结、重写触发，用户能否看到清晰的提示 |
| 跨模块对账 | 游标推进数 = 草稿数 + 归档数，时间线 chased 数和实际文件数对齐 |

这些只有连贯跑一遍才能暴露。

## 二、产品视角：全按钮覆盖矩阵

面板上的每一个用户操作，对应一个 API 端点。测试要覆盖全部 20 个操作，验证每个按钮在对应状态下可用、返回正确数据、且和其他按钮的数据一致。

### 库管理（4 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 查看库列表 | `listLibraries` | 打开面板 | 返回非空数组，每个库有 id/name/kind |
| 新建知识库 | `createLibrary` | 填表创建 | 创建成功后 listLibraries 多一条；磁盘上出现对应目录结构 |
| 删除知识库 | `deleteLibrary` | 点删除 | 删除后 listLibraries 少一条；磁盘上库内容、索引、workspace 全部清除 |
| 编辑库配置 | `updateLibrary` | 改名/改仓库/改模型 | 改完后 listLibraries 返回新值；追史用新配置 |

### 搜索与浏览（4 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 搜索 | `search` | 输入关键词 | 空库搜索返回空；采纳后搜索能找到归档文章；中文分词正确 |
| 阅读文章 | `read` | 点击文件 | 返回完整 markdown 内容；不存在的路径报错 |
| 浏览内容 | `browse` | 查看术语表/目录 | 返回对应区域的结构化数据 |
| 展开文件树 | `browseTree` | 浏览库目录 | 树结构正确；隐藏目录（.git/workspace）不出现 |

### 审阅队列（4 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 查看草稿列表 | `listDrafts` | 打开审阅面板 | 空库返回空；追史后返回草稿数组，每个有 id/targetPath/body/status/commitHash/repoName |
| 采纳草稿 | `adoptDraft` | 点采纳 | 草稿消失，归档文件出现，search 可检索，chaseStatus.adoptedDrafts +1 |
| 重写草稿 | `rewriteDraft` | 点重写 | 旧草稿删除，新追史会话启动，新草稿进队列，数量不变（删一加一） |
| 修改后采纳 | `reworkDraft` | 编辑内容后采纳 | 归档的是修改后的内容，不是原始草稿 |

### 手动添加与术语（2 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 手动提交文章 | `submitDraft` | 填写内容提交 | 草稿出现在 listDrafts 中，可以走采纳流程 |
| 添加术语对 | `addTerm` | 填写术语映射 | 添加后 search 时自动展开查询 |

### 模型与追史（6 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 查看可用模型 | `listModels` | 打开模型选择 | 返回模型列表，供 createLibrary/updateLibrary 使用 |
| 立即追史 | `startChase` | 点追史按钮 | 返回 plan；游标设为 pending；5 篇上限时拒绝并提示 |
| 查看追史状态 | `chaseStatus` | 查看状态卡片 | behindCount/pendingDrafts/adoptedDrafts 与磁盘实际一致 |
| 查看时间线 | `chaseTimeline` | 打开时间线 | 每个 commit 的 chased 标记与实际草稿/归档对齐 |
| 预览提示词 | `chasePrompt` | 查看提示词 | 返回 skill 内容 + 用户提示词模板 + 下一个待追 commit 的材料 |
| 刷新仓库 HEAD | `refreshRepo` | 手动刷新 | lastSeenHead 更新；如果有新 commit，behindCount 增加 |

## 三、测试设计：完整产品链路

### 阶段一：建库（库管理 4 按钮）

**操作**：`listLibraries`（空）→ `createLibrary` → `listLibraries`（1 条）→ `updateLibrary` → `listLibraries`（新值）

**校验点**：
- 空库时 listLibraries 返回 `[]`
- 创建后返回值包含正确的 id/name/kind/vaultRemote/vaultPath/repos
- 磁盘上 `<指纹>/knowledge-base/<vaultPath>/` 出现 00-总表/10-史实/50-草稿区/ 目录结构
- updateLibrary 改名后 listLibraries 返回新名字
- updateLibrary 加仓库后 listLibraries 的 repos 数组变长

### 阶段二：空库状态验证（追史状态 + 浏览）

**操作**：`chaseStatus` → `listDrafts`（空）→ `search`（空）→ `browseTree`

**校验点**：
- chaseStatus: behindCount = 总 commit 数，pendingDrafts = 0，chasedDrafts = 0，adoptedDrafts = 0，running = false
- listDrafts 返回 `[]`
- search 返回空数组
- browseTree 返回目录树，.git/workspace 不出现

### 阶段三：追史启动（立即追史 + 状态 + 时间线）

**操作**：`startChase` → `chaseStatus`（running）→ `chaseTimeline`

**校验点**：
- startChase 返回 plan，items 按时间正序（最老在前）
- chaseStatus: running = true，sessionId = 'pending'，batchTotal = plan.items.length
- chaseTimeline: 前 N 个 commit 标记为 chased = true（有草稿的）

### 阶段四：草稿落盘 + 自愈收编（草稿列表 + 时间线对账）

**操作**：追史完成后 `listDrafts` → `chaseTimeline` → 磁盘验证

**校验点**：
- listDrafts 数量 = plan.items.length
- 每个草稿有 commitHash 和 repoName（从 frontmatter 提取）
- chaseTimeline 中对应 hash 的 chased = true, draftId 非空
- 磁盘 50-草稿区/ 下 .md 文件数 = listDrafts 数量
- chaseStatus.pendingDrafts = listDrafts 中 pending 状态的数量

### 阶段五：审阅归档（采纳 + 搜索 + 状态对账）

**操作**：`adoptDraft`（第一篇）→ `listDrafts`（-1）→ `search`（能找到）→ `chaseStatus`（adoptedDrafts +1）→ `read`（读归档文件）

**校验点**：
- 50-草稿区/ 中该草稿的 .md 和 .meta.json 删除
- 10-史实/<域>/@<repo>/ 下出现归档文件，内容正确
- search 能用关键词找到归档文章
- chaseStatus.adoptedDrafts = 1，pendingDrafts -1
- read 返回归档文件的完整内容

### 阶段六：顺序采纳拦截

**操作**：跳过 M1 直接 `adoptDraft`(M2)

**校验点**：
- 返回错误"顺序采纳：请先采纳之前的 commit"
- 草稿不动，listDrafts 数量不变

### 阶段七：修改后采纳

**操作**：`reworkDraft`（编辑内容）→ `adoptDraft`

**校验点**：
- 归档文件内容是修改后的版本，不是原始草稿
- search 能找到修改后的内容

### 阶段八：重写

**操作**：`rewriteDraft` → 观察新追史 → `listDrafts`

**校验点**：
- 旧草稿的 .md + .meta.json 删除
- 新追史会话启动
- 新草稿落盘后 listDrafts 数量不变（删一加一）

### 阶段九：auto-continue + 5 篇上限

**操作**：采纳到 pending < 5 → 观察自动启动 → 造到 pending >= 5 → `startChase`

**校验点**：
- autoContinue=true 且 pending < 5 时自动启动下一轮
- autoContinue=true 且 pending >= 5 时日志出现 `skipped, N pending >= 5`
- 手动 startChase 在 pending >= 5 时报错"待审草稿已达 5 篇上限"

### 阶段十：手动添加 + 术语

**操作**：`submitDraft` → `listDrafts` → `addTerm` → `search`（用术语）

**校验点**：
- submitDraft 后草稿出现在 listDrafts
- 可以走正常 adopt 流程
- addTerm 后 search 用 surface term 能匹配到 canonical term 的内容

### 阶段十一：刷新 + 追平

**操作**：`refreshRepo` → `chaseStatus`（behindCount = 0）→ `chasePrompt`（无待追）

**校验点**：
- refreshRepo 返回最新 HEAD
- 追平后 chaseStatus: behindCount = 0
- startChase 报错"已追平，无待追 commit"
- chasePrompt: sampleMaterial 为空

### 阶段十二：删除库（清理验证）

**操作**：`deleteLibrary` → `listLibraries`（空）→ 磁盘验证

**校验点**：
- listLibraries 返回空
- 磁盘上库内容、索引、workspace 全部清除

```bash
# 阶段一

  -d '{"name":"测试库","kind":"project-history","vaultRemote":"...","repos":[...]}'

curl -s -X POST "$BASE/startChase" -H "Content-Type: application/json" \
  -d '{"library":"test-lib","repo":"source-repo"}'

  -d '{"draftId":"...","library":"test-lib"}'
```

```typescript
// 不创建真 agent，直接写 .md 到 50-草稿区（模拟 agent 行为）
async function mockAgent(draftDir: string, draftName: string, commitHash: string) {

}
```

测试验证的是**产品连贯性**（全按钮可用、数据前后一致、状态转换合理），而非 LLM 生成质量。
