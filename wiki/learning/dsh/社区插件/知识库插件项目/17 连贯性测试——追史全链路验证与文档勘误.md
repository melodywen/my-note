# 17 连贯性测试——全按钮产品视角验证

> 本文记录如何对知识库插件做端到端连贯性测试：站在产品视角，覆盖面板上每一个用户可操作的按钮，验证全链路数据前后一致、提示词拼接正确、目录结构完整、所有交互有反馈、整个体验连贯友好。
> 过程中发现设计文档与代码的 6 处不一致，已全部处理（见第五节）。

---

## 一、为什么要做连贯性测试

现有单元测试覆盖的是**单个模块的正确性**——DraftStore 的 CRUD、git.ts 的白名单、history.ts 的逐篇规划。但用户面对的是一个完整产品：打开面板 → 看到库列表 → 点进某个库 → 追史 → 审阅草稿 → 采纳归档 → 搜索验证。这条链路上任何一个按钮失灵、任何一处数据不一致，产品体验就断了。

单元测试的盲区：

| 盲区 | 说明 |
|------|------|
| 按钮可用性 | 每个按钮在什么状态下可点、什么状态下灰显，前后是否一致 |
| 数据一致性 | 面板显示的数字（pending/adopted/behind）和磁盘实际文件数量是否对得上 |
| 操作链路连贯 | 追史 → 草稿落盘 → 审阅 → 归档 → 搜索可检索，每一步的输出是下一步的输入 |
| 状态转换 | 空库 → 追史中 → 待审 → 部分采纳 → 追平，每个状态下面板显示是否合理 |
| 错误反馈 | 顺序采纳拦截、pending 上限冻结、重写触发，用户能否看到清晰的提示 |
| 跨模块对账 | 游标推进数 = 草稿数 + 归档数，时间线 chased 数和实际文件数对齐 |
| 提示词拼接 | 系统提示词（skill）+ 用户提示词（任务信息）是否完整传给 agent |
| 目录结构 | 追史后磁盘上的 00-总表/10-史实/20-快照 是否完整 |
| 搜索层级 | 史实搜索和快照搜索是否分开，结果是否正确分层 |

这些只有连贯跑一遍才能暴露。

## 二、产品视角：全按钮覆盖矩阵

面板上的每一个用户操作，对应一个 API 端点。测试要覆盖全部 21 个操作（含快照生成），验证每个按钮在对应状态下可用、返回正确数据、且和其他按钮的数据一致。

### 库管理（4 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 查看库列表 | `listLibraries` | 打开面板 | 返回非空数组，每个库有 id/name/kind |
| 新建知识库 | `createLibrary` | 填表创建 | 创建成功后 listLibraries 多一条；磁盘上出现对应目录结构 |
| 删除知识库 | `deleteLibrary` | 点删除 | 删除后 listLibraries 少一条；磁盘上库内容、索引、workspace 全部清除 |
| 编辑库配置 | `updateLibrary` | 改名/改仓库/改模型 | 改完后 listLibraries 返回新值；追史用新配置 |

### 搜索与浏览（4 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 搜索 | `search` | 输入关键词 + 选层级 | 空库返回空；采纳后史实搜索能找到；指定 layer=snapshot 只搜快照 |
| 阅读文章 | `read` | 点击文件 | 返回完整 markdown 内容；不存在的路径报错 |
| 浏览内容 | `browse` | 查看术语表/目录 | 返回对应区域的结构化数据 |
| 展开文件树 | `browseTree` | 浏览库目录 | 树结构正确；隐藏目录（.git/workspace）不出现 |

### 审阅队列（4 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 查看草稿列表 | `listDrafts` | 打开审阅面板 | 空库返回空；追史后返回草稿数组，每个有 id/targetPath/body/status/commitHash/repoName |
| 采纳草稿 | `adoptDraft` | 点采纳 | 草稿消失，归档文件出现，search 可检索，adoptedDrafts +1 |
| 重写草稿 | `rewriteDraft` | 点重写 | 旧草稿删除，新追史会话启动 |
| 修改后采纳 | `reworkDraft` | 编辑内容后采纳 | 归档的是修改后的内容，不是原始草稿 |

### 手动添加与术语（2 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 手动提交文章 | `submitDraft` | 填写内容提交 | 草稿出现在 listDrafts 中，可以走采纳流程 |
| 添加术语对 | `addTerm` | 填写术语映射 | 添加后 search 时自动展开查询 |

### 模型与追史（6 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 查看可用模型 | `listModels` | 打开模型选择 | 返回模型列表 |
| 立即追史 | `startChase` | 点追史按钮 | 返回 plan 单篇；pending ≥ 1 时拒绝 |
| 查看追史状态 | `chaseStatus` | 查看状态卡片 | behindCount/pendingDrafts/adoptedDrafts 与磁盘实际一致 |
| 查看时间线 | `chaseTimeline` | 打开时间线 | 每个 commit 的 chased 标记与实际草稿/归档对齐 |
| 预览提示词 | `chasePrompt` | 查看提示词 | 返回 skill 内容 + 用户提示词模板 + 下一个待追 commit 的材料 |
| 刷新仓库 HEAD | `refreshRepo` | 手动刷新 | lastSeenHead 更新 |

### 快照（1 个按钮）

| 按钮 | API 方法 | 用户动作 | 测试要点 |
|------|----------|---------|---------|
| 生成快照 | `generateSnapshot` | 点生成快照 | 快照文件出现在 20-快照/；frontmatter 有 commit hash；三向校验返回 issues |

## 三、测试设计：完整产品链路

### 阶段一：建库（库管理 4 按钮）

**操作**：`listLibraries`（空）→ `createLibrary` → `listLibraries`（1 条）→ `updateLibrary` → `listLibraries`（新值）

**校验点**：
- 空库时 listLibraries 返回 `[]`
- 创建后返回值包含正确的 id/name/kind/vaultRemote/vaultPath/repos
- 磁盘上 `<指纹>/knowledge-base/<vaultPath>/` 出现 00-总表/10-史实/20-快照 目录结构
- updateLibrary 改名后 listLibraries 返回新名字

### 阶段二：空库状态验证（追史状态 + 浏览）

**操作**：`chaseStatus` → `listDrafts`（空）→ `search`（空）→ `browseTree`

**校验点**：
- chaseStatus: pendingDrafts = 0，chasedDrafts = 0，adoptedDrafts = 0，running = false
- listDrafts 返回 `[]`
- search 返回空数组
- browseTree 返回目录树，.git/workspace 不出现

### 阶段三：追史启动（立即追史 + 状态 + 提示词验证）

**操作**：`startChase` → `chaseStatus`（running）→ `chasePrompt`（提示词内容）

**校验点**：
- startChase 返回 plan，items.length = 1（逐篇），最老 commit 在前
- chaseStatus: running = true，sessionId = 'pending'
- chasePrompt 返回的 systemPrompt 包含产品语言规范（非空）
- chasePrompt 返回的 userTemplate 包含 commit hash、工作空间路径、草稿文件名
- chasePrompt 返回的 sampleMaterial 非空（有待追 commit 的材料）
- `workspaceRegistry.create` 被调用（创建 `知识库-<库名>` 工作空间）
- `workspace.attachSession` 被调用（会话归入正确工作空间分组，不落「未分组」）

### 阶段四：草稿落盘 + 自愈收编（草稿列表 + 目录验证 + 时间线对账）

**操作**：追史完成后 `listDrafts` → `chaseTimeline` → 磁盘验证

**校验点**：
- listDrafts 数量 = 1（逐篇生成一篇草稿）
- 每个草稿有 commitHash 和 repoName
- chaseTimeline 中对应 hash 的 chased = true, draftId 非空
- 磁盘 10-史实/ 下 .md + .meta.json 文件数 = listDrafts 数量
- chaseStatus.pendingDrafts = listDrafts 中 pending 状态的数量
- 目录结构完整：00-总表/ \_库.json 存在；10-史实/ 下有 @repo 目录；@repo/ 下有 .md

### 阶段五：审阅归档（采纳 + 搜索 + 状态对账 + read）

**操作**：`adoptDraft`（第一篇）→ `listDrafts`（-1）→ `search`（能找到）→ `chaseStatus`（adoptedDrafts +1）→ `read`（读归档文件）

**校验点**：
- 10-史实/ 中该草稿的 .meta.json 状态改为 adopted
- 10-史实/\<域>/@\<repo>/ 下出现归档文件，内容正确
- search 能用关键词找到归档文章
- chaseStatus.adoptedDrafts = 1，pendingDrafts -1
- read 返回归档文件的完整内容

### 阶段六：顺序采纳拦截

**操作**：跳过 M1 直接 `adoptDraft`(M2)

**校验点**：
- 返回错误"顺序采纳：请先采纳之前的 commit"
- 草稿不动，listDrafts 数量不变

### 阶段七：修改后采纳

**操作**：`reworkDraft`（编辑内容）→ `adoptDraft`

**校验点**：
- 归档文件内容是修改后的版本，不是原始草稿
- search 能找到修改后的内容

### 阶段八：重写

**操作**：`rewriteDraft` → 观察新追史 → `listDrafts`

**校验点**：
- 旧草稿的 .md + .meta.json 删除
- 新追史会话启动

### 阶段九：pending 上限冻结

**操作**：有 pending 草稿时 `startChase`

**校验点**：
- 手动 startChase 在 pending ≥ 1 时报错"待审草稿已达上限"
- autoContinue=true 且 pending ≥ 1 时日志出现 `skipped, N pending >= 1`

### 阶段十：手动添加 + 术语

**操作**：`submitDraft` → `listDrafts` → `addTerm` → `search`（用术语）

**校验点**：
- submitDraft 后草稿出现在 listDrafts
- 可以走正常 adopt 流程
- addTerm 后 search 用 surface term 能匹配到 canonical term 的内容

### 阶段十一：刷新 + 追平 + 快照

**操作**：`refreshRepo` → `chaseStatus`（behindCount = 0）→ `chasePrompt`（无待追）→ `generateSnapshot`

**校验点**：
- refreshRepo 返回最新 HEAD
- 追平后 chaseStatus: behindCount = 0
- startChase 报错"已追平，无待追 commit"
- chasePrompt: sampleMaterial 为空
- 快照文件出现在 20-快照/\<repo>/当前能力.md
- 快照 frontmatter 有 commit hash 和 generatedAt
- 快照包含已有史实文章列表

### 阶段十二：搜索层级验证

**操作**：`search`（layer=history）→ `search`（layer=snapshot）

**校验点**：
- 史实搜索只返回 10-史实/ 下的文档
- 快照搜索只返回 20-快照/ 下的文档
- 不指定 layer 时搜全部

### 阶段十三：删除库（清理验证）

**操作**：`deleteLibrary` → `listLibraries`（空）→ 磁盘验证

**校验点**：
- listLibraries 返回空
- 磁盘上库内容、索引、workspace 全部清除

用 `curl` 直接打 HTTP API，每步断言返回值。日志在 `/tmp/dsh-kb.log`。

```bash

# 阶段一

  -d '{"name":"测试库","kind":"project-history","vaultRemote":"...","repos":[...]}'
```

### 4.4 提示词验证

追史 agent 收到的提示词分两层：

**系统提示词**（来自 skill 文件，管"怎么写"）：
- 非空，包含产品语言规范
- 包含穿插块标识符格式（`→ [commit]` / `← [commit]`）
- 包含外链锚点格式（`↗ [commit · file]`）
- 包含自检清单

**用户提示词**（每次拼接，管"写什么"）：
- 包含 commit hash
- 包含工作空间路径（workspace 目录 + knowledge-base 软链 + 被跟踪仓库路径）
- 包含草稿文件名
- 包含任务步骤（checkout → 读代码 → 读 diff → 读已有史实 → 生成 → 写归档路径）

验证方式：调用 `chasePrompt` API，断言返回值的 `systemPrompt` 和 `userTemplate` 包含上述要素。
