# 19 快照生成——当前能力画像与三向校验

> 史实追完后，最后一篇文档是快照——基于当前 master 代码生成的当前能力完整画像。
> 类似 Docker image 跟 Docker container 的关系：史实是一层一层叠的 image，快照是最终运行的 container。

---

## 一、快照是什么

史实文档记录的是演进脉络——什么时候加了什么、删了什么。快照文档记录的是"此刻这个项目能做什么"——不关心历史，只看当前 master 代码。

读者不同：
- 史实：想了解"为什么这样设计、踩过什么坑"的人
- 快照：做方案、做选型的人，只需要知道"现在能做什么"

---

## 二、三向交叉校验

快照生成时做三向校验，三份文档互相验证：

| 来源 | 作用 |
|------|------|
| 当前 master 代码 | 事实来源——当前能做什么 |
| 史实文档 | 演进来源——什么时候加的、什么时候删的 |
| 快照文档 | 当前画像——完整的能力清单

校验规则：

- 快照说有这个功能 → 代码里确实有
- 史实说加过这个功能 → 快照里有（没被删）
- 代码里有新功能 → 史实提到过
- 三者不一致 → 暴露问题，修正后重新生成

---

## 三、生成流程

1. 切到当前 master，读全部代码，理解当前完整架构
2. 读所有史实文档，理解每个场景的演进脉络
3. 双向比对——史实说有但代码没了标记移除，代码有但史实没提过标记补充
4. 生成当前能力文档——每个场景的完整流程，基于 master 代码
5. 全量校验——每个外链指向的文件在 master 上确实存在且逻辑匹配
6. 快照文档走审阅，git diff

## 五、快照与史实的关系

- **史实是 image layers**：每一层是一个时间点的功能增量，叠加起来构成完整演进
- **快照是 container**：最终运行态，只反映当前 master，不关心中间过程
- 快照搜索到关键词 → 返回当前完整流程
- 想了解为什么这样设计 → 跳转到史实看演进脉络
- 三向交叉验证保证三者一致

---

## 六、迭代

快照迭代不是从零重写，是以旧快照为底子，只改动有变化的部分。

**生成流程**：

1. 对比旧快照的 commit id 和当前 master 的 commit id，知道中间迭代了多少个版本
2. 读中间这些 commit 的史实文档，知道动了哪些功能点
3. 以旧快照为底子，只改动涉及的功能点
4. 如果发现之前快照有错也一并修正
5. 全量校验——外链指向的文件在 master 上确实存在
6. 走审阅，只看 diff

**原则**：

- 动了哪个功能点就改哪个功能点，没动的不动
- 不要一个字都不复用全部重写
- 改动点要清晰，审阅时能看到具体改了什么
- 快照也走审阅，git diff
