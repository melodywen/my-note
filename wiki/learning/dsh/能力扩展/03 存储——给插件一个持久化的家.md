> [!info] 版本锚点
> - 源码：`~/ai-work/dsh/deepseek-harness/`（master `0d1f50007f`）；全局包 `dsh 0.1.5-rc.1`

> - 写法说明：本系列采用**完整重讲式**；本篇由本人从源码 + 实测组织，**每段标出处**

## 这一篇在讲什么

前面你写的插件都是**无状态**的——重启就忘。**存储子系统**给插件一个**持久化的家**：把数据写进介质（文件 / SQLite），重启后读回。

官方定位：

> **出处**：`docs/subsystems/storage.zh.md:5`（逐字）——*"存储子系统持久保存一切不属于会话事件日志的数据（会话日志有自己的 seam——见 persistence.md）。"*

**本篇核心**：理解 storage 的**四层结构**（hub / backend / domain / table），并动手写一个**带存储的插件**。

> ⚠️ **和 07 篇的分工**：**会话日志（`SessionEvent`）有自己的 seam——`persistence`**（不是本篇）。本篇的 storage 管**"日志之外"的数据**（如：你的插件自己的状态、缓存、配置）。

### ⭐ storage 到底存什么？（先讲清，别懵）

**"日志之外的数据"太抽象**。具体说：

**storage 存的是"插件想持久化、又不是对话记录"的结构化数据。** 三类典型用途（都有真实案例）：

| 用途 | 真实案例 | 存的内容 |
|---|---|---|
| **元数据 / 索引** | `workspace`（工作区插件） | 工作区路径、**它属于哪些会话**、创建时间 |
| **缓存 / 派生数据** | `session-projection-cache` | 会话投影的**检查点**（能重算，但存下来省事） |
| **插件自己的状态** | 你写的 `storage-demo` | 插件想**跨重启记住**的东西（如笔记、计数、偏好） |

> **出处**：源码 `packages/workspace/workspace/src/spec.ts`（工作区领域）；`packages/session/session-projection-cache/src/spec.ts`（投影缓存领域）

**它不存什么**（划清边界）：

| 不存 | 存哪 |
|---|---|
| **对话记录**（你说的话、模型回复） | **`persistence`**（另一条 seam，落成 JSONL 日志） |
| 用户设置 | `settings.yaml` |
| 凭据 / API key | `.credentials.yaml` |

> **Go 类比**：**storage ≈ 给你的插件一个"内嵌 KV 数据库"**（像 BoltDB / Badger）——你定义表结构，它负责落盘。存什么**取决于你写什么插件**：记录对话用 `persistence`；记自己的一亩三分地用 **本篇 storage**。

### ⭐ 用什么介质存？（这是你要选的）

storage 把"介质"抽象成 **Provider（后端）**——**你不用改代码就能换介质**：

| 后端                       | 介质                           | 特点            | 何时选                            |
| ------------------------ | ---------------------------- | ------------- | ------------------------------ |
| **`dsh-storage-json`**   | 一棵**文件树**（每 unit 一个 JSON 文件） | 人类可读、易调试      | **演示 / 数据量小 / 想手动看** ← 本篇案例用这个 |
| **`dsh-storage-sqlite`** | 一个 **SQLite 数据库文件**          | 每行一份文档、适合频繁更新 | **频繁写 / 数据量大**                 |

> **出处**：`storage.zh.md:47`——*"json 后端以原子方式为每个 unit 整文件重新发布一份人类可读文件；sqlite 后端在单个数据库中每行存储一份文档，用于频繁更新的数据。"*

**你怎么选？** —— 由 **Consumer 自己的配置**（领域层的**路由表**）决定，**不是全局选**：

```yaml
# storage-domain 插件的配置（示意）
backend: json          # 默认路由（必填）
routes:                # 按领域名逐个覆盖
  my-plugin-data: sqlite
```

> **出处**：`storage.zh.md:130`——*"路由是领域插件的配置，绝不属于枢纽：`backend` 指定必填的默认路由，`routes` 按领域名逐个覆盖。"*

**Go 类比**：像 `database/sql` ——**你选 driver（json/sqlite），但代码用同一套 API**；换 driver 不改业务代码。

### ✅ dsh 默认就给你一套存储（你通常啥都不用配）

**关键认知**：**你不需要自己搭存储**——`dsh-base` bundle（所有 profile 的公共底层）**默认已经挂了**一套：

```yaml
# packages/bundle/base/cordis.patch.yml:141-154（逐字）
# Durable KV storage: the storage hub, the json backend, and the ...
- id: storage
  name: '@deepseek-ai/dsh-storage'
- id: storage-json
  name: '@deepseek-ai/dsh-storage-json'
  config:
    root: !!js dshHomePath('storages')     # ← 默认存到 ~/.dsh/storages/
- id: storage-domain
  name: '@deepseek-ai/dsh-storage-domain'
```

> **出处**：源码 `packages/bundle/base/cordis.patch.yml:145-154`

**所以默认情况**：
- **后端 = `json`**（不是 sqlite——**sqlite 要你自己加**）
- **位置 = `~/.dsh/storages/`**（`dshHomePath('storages')`，每个领域一个子目录）
- **hub + domain 组件都在**

**这意味着**：你写个插件用 storage → **默认就能跑**（它自己会写进 `~/.dsh/storages/<域名>/`），**你一行配置都不用写**。**只有想换介质（sqlite）或换位置时，才需要配置。**

> **Go 类比**：像框架默认给你一个本地数据目录（`~/.your-app/data/`）——**开箱即用**；想换 Postgres 才动配置。dsh 的结构一模一样。

> **出处**：本人核对（2026-09-16，`dsh-base` bundle `:141-154`）；`dsh-storage-sqlite` 未在 base 中默认挂载

## 一、storage 是能力 seam——08 篇三角色的第三次应用

**回扣 08 篇**：你在 `bash`（`dsh-shell`）、LLM（`dsh-llm`）上见过三角色。**storage 是第三次**——但**变形了**：

> **出处**：`storage.zh.md:5`（逐字）——*"按能力 seam 拆分：**枢纽（hub）与 Service Definition**（`dsh-storage`，`ctx.storage`）、**Service Provider**（注册为 `json` 的 `dsh-storage-json` 与注册为 `sqlite` 的 `dsh-storage-sqlite`），以及 **Consumer 数据形式**（`dsh-storage-domain`，`ctx.storageDomain`…）"*

| 角色 | storage 里 | 与 08 篇的差异 |
|---|---|---|
| **Definition** | `dsh-storage`（`ctx.storage`） | 是**"枢纽 hub"**——**自己不做 IO**，只管注册/挂载 |
| **Provider** | `dsh-storage-json` / `dsh-storage-sqlite` | 两个**后端**（介质），可替换 |
| **Consumer** | `dsh-storage-domain`（`ctx.storageDomain`） | **类型化领域 API**——"后端约定的唯一 Consumer" |

> **关键洞察**（文档原话）：*"枢纽自身不做任何 IO：后端拥有介质，数据形式拥有语义，产品包绝不直接触碰后端。"*（`storage.zh.md:5`）
>
> **出处**：源码 `packages/storage/storage/src/index.ts:2`（逐字）——*"The hub itself performs no IO — backends own media"*
**与 08 篇的对照**：
- 08 篇：Definition（`dsh-shell`）**拥有执行语义**（抽象类带 resolve/run）
- 本篇：Definition（`dsh-storage`）**只有注册表**（连 IO 都没有）——**更"薄"**

## 二、四层结构（比 bash/LLM 多一层）

```
ctx.storage（hub，Definition）           ← 注册表，无 IO
   ├── backend.register('json', backend)     ← Provider 注册
   └── mount('domain', facility)             ← 数据形式挂载
        ↓
ctx.storageDomain（DomainFacility，Consumer 门面）  ← 类型化 API
   └── open(spec) → Domain                   ← 打开一个"领域"
        └── domain.table('x') → KvTable       ← 读写的最终把手
```

**"领域（Domain）"是核心概念**：用 `defineDomain(spec)` 声明（含 **zod schema**），`ctx.storageDomain.open(spec)` 打开。

> **Go 类比**：
> - `ctx.storage` ≈ `database/sql` 的**驱动注册表**（`sql.Register`）
> - `backend` ≈ **驱动实现**（mysql / sqlite driver）
> - `defineDomain(spec)` ≈ **表结构的 schema 声明**
> - `domain.table(k)` ≈ 拿到一张**类型化的表句柄**

## 三、Definition：`ctx.storage`（枢纽）

> **出处**：源码 `packages/storage/storage/src/index.ts:47`

```ts
export class Storage extends Service {           // index.ts:47
  readonly backend: BackendRegistry              // 名称 → 后端 的表
  mount(form, facility): () => void              // 挂载数据形式（effect，返回 disposer）
  form(form): ...                                // 解析已挂载的形式
}
```

- **它不管 IO**——只维护"后端表"和"数据形式表"
- **多后端并存**：哪个后端服务哪个消费方，由**消费方自己的配置**决定（领域层的路由），不是 hub 全局选择

### 后端注册

> **出处**：源码 `packages/storage/storage/src/registry.ts`

```ts
ctx.storage.backend.register('json', backend)    // 注册名为 json 的后端
```

**返回 disposer**（effect）——**注销不关闭后端**（由拥有它的插件自己关）。

> **出处**：`registry.ts:18-25`（逐字）——*"Registration is an effect: the returned disposer removes the name. **Disposal does NOT close the backend** — the owning plugin closes it after unregistering."*

## 四、Provider：后端（`json` / `sqlite`）

后端约定：

> **出处**：`storage.zh.md:34`（`StorageBackend`）

```ts
interface StorageBackend {
  readonly kv?: KvFacet        // KV 操作组（唯一已交付的组）
  close(): Promise<void>        // 释放介质
}
```

- **一个后端 = 一个介质**（一棵文件树的根 / 一个 db 文件）
- `KvFacet.open(descriptor)` → `KvUnit`（`loadAll`/`putRecord`/`deleteRecord`/`setGlobal`/`close`）

**两个已交付后端**：

| 后端 | 介质 | 特点 | 出处 |
|---|---|---|---|
| `dsh-storage-json` | 一棵文件树 | 人类可读，整文件原子发布 | `storage.zh.md:47` |
| `dsh-storage-sqlite` | 一个 db 文件 | 每行一份文档，适合频繁更新 | 同上 |

**Provider 的注册写法**（真实源码）：

> **出处**：`packages/storage/storage-json/src/index.ts:110-117`

```ts
export function apply(ctx: Context, config: Config) {
  const backend = new JsonStorageBackend(config.root)
  ctx.effect(() => {
    const unregister = ctx.storage.backend.register('json', backend)
    return async () => { unregister(); await backend.close() }   // 注销 + 关闭
  })
  ctx.provide(storageBackendServiceKey('json'), backend)          // 生命周期服务键
}
```

> **注意**：`ctx.effect` 的 disposer 里**先 unregister 再 close**——**和文档说的"由拥有者关闭"一致**。

## 五、Consumer：怎么写（**这才是你要用的**）

### 声明领域：`defineDomain(spec)`

> **出处**：`storage.zh.md:55`（`DomainSpec`）+ `session-projection-cache/src/spec.ts`（真实案例）

```ts
import { defineDomain, domainTable } from '@deepseek-ai/dsh-storage-domain'
import { z } from 'zod'

const myDomainSpec = defineDomain({
  name: 'my-plugin-data',       // 须匹配 UNIT_NAME_RE
  version: 1,
  layout: 'single',             // 默认；per-record 为每条记录单独一份文档
  tables: {
    items: domainTable(z.object({          // 一张表，value schema 用 zod
      id: z.string(),
      note: z.string(),
    })),
  },
})
```

**`spec` 是领域的单一来源**——身份、版本、布局、记录 schema。

### 打开 + 读写

> **出处**：`session-projection-cache/src/index.ts:93,106-108`（真实 Consumer）

```ts
export const inject = ['storageDomain', ...]

async apply(ctx: Context) {
  const domain = await ctx.storageDomain.open(myDomainSpec)     // 打开
  ctx.effect(() => () => domain.close(), 'myPlugin.domainClose') // 卸载自动关
  const table = domain.table('items')                            // 拿表句柄

  await table.put('k1', { id: 'k1', note: 'hello' })             // 写（异步，落盘后 resolve）
  const v = table.get('k1')                                      // 读（同步，走内存权威态）
}
```

**关键性质**（都必须记住）：

| 性质 | 说明 | 出处 |
|---|---|---|
| **读同步、写异步** | `get` 同步（内存权威态）；`put`/`delete` 异步（落盘后 resolve） | `storage.zh.md:126` |
| **写前持久化** | 先落盘 → 更新内存 → 发 `domain/changed`；后端拒则内存不动 | 同上 |
| **返回的是存储对象本身**（非副本） | 必须 `put`/`update` **整体替换**，**别就地改** | 同上 |
| **单写者** | 同一领域名同时只能 open 一次（`already-open`） | `storage.zh.md:130` |
| **卸载自动关** | 没手动关，facility 卸载时兜底 | 同上 |

> [!warning] ⚠️ "返回的是引用"这条最容易踩
> `table.get(k)` 返回的**就是存储内部的对象**，不是副本。你**就地改它（`v.note = 'x'`）不会触发持久化**——必须 `put(k, newValue)` 整体替换。（出处：`storage.zh.md:126`）
>
> **Go 类比**：像 `map` 里取出的指针——你改了它，map 不知道，得 `m[k] = newVal` 才"提交"。

### 变更事件：`domain/changed`

> **出处**：`storage.zh.md:132` + `events.ts`

每次持久写入后发一个事件（**严格在落盘确认之后**）：

```ts
type DomainChanged =
  | { operation: 'put'; domain: string; table: string; key: string; value: unknown }
  | { operation: 'deleted'; domain: string; table: string; key: string }
```

- `put` 携带**新快照**（不带旧值）；`deleted` 是墓碑
- **仅限进程内**（跨进程推送是已记录的限制）
- **是通知，不是事务参与者**：发出时提交点已过

> **Go 类比**：像 `fsnotify` 的文件变更通知——**事后通知**，不是"改之前问你"。

## 六、动手案例：写一个带存储的插件（**补阶段二欠账**）

> **规则（AGENTS.md）**：动手环节"你动手"。本节代码待**动手阶段**补齐并实测。

**目标**：写一个**最小带存储插件**——`defineDomain` 一张表 → `put` 一条 → **重启后 `get` 读回**（证明持久化）。

**计划**（`dsh-learn/example/stage-03/plugins/storage-demo/`）：

```
storage-demo/
├── storage-demo.ts          ← 插件：defineDomain + put/get + 监听 domain/changed
├── storage-demo.patch.yml   ← 挂载层
└── package.json
```

**核心代码（草案）**：

```ts
import { defineDomain, domainTable } from '@deepseek-ai/dsh-storage-domain'
import { z } from 'zod'

const spec = defineDomain({
  name: 'storage-demo-data', version: 1, layout: 'single',
  tables: { notes: domainTable(z.object({ text: z.string() })) },
})

export const name = 'storage-demo'
export const inject = ['storageDomain']

export async function apply(ctx) {
  const domain = await ctx.storageDomain.open(spec)
  ctx.effect(() => () => domain.close(), 'storageDemo.close')
  const notes = domain.table('notes')

  // 启动时读回（验证持久化）
  console.log('[storage-demo] 已有记录:', [...notes.entries()])

  // 写一条
  await notes.put(String(Date.now()), { text: 'hello' })

  // 监听变更
  ctx.on('domain/changed', (e) => console.log('[storage-demo] changed:', e))
}
```

**验证步骤**：
1. 挂上插件启动 → 看它写入了记录（`domain/changed` 打印）
2. **重启** → 看启动日志 `[storage-demo] 已有记录: [...]` **包含上次写的**（= 持久化成功）
3. ⚠️ **必须真启动验证**（09 篇教训：dump 通过 ≠ 能启动）

| 概念 | 一句话 | Go 类比 | 出处 |

| `dsh-storage-{json,sqlite}` | 两个可替换后端 | mysql/sqlite driver | `storage.zh.md:47` |
| `defineDomain(spec)` | 声明领域（zod schema） | 表结构声明 | `storage.zh.md:55` |
| `ctx.storageDomain.open` | 打开领域 → `Domain` | `sql.Open` | `session-projection-cache:106` |
| `domain.table(k)` | 拿类型化表句柄 | 表句柄 | 同上 |
| **读同步 / 写异步** | `get` 同步；`put` 落盘后 resolve | — | `storage.zh.md:126` |
| **返回引用非副本** | 别就地改，要 `put` 整体替换 | map 里的指针 | `storage.zh.md:126` |
| `domain/changed` | 持久写后的事件通知 | `fsnotify` | `storage.zh.md:132` |

## 踩坑预防

- **⚠️ `get` 返回的是存储对象本身（引用）**：就地改不持久化，必须 `put`/`update` 整体替换。（出处：`storage.zh.md:126`）
- **⚠️ 同一领域名只能 open 一次**：重复 open 抛 `already-open`。（出处：`storage.zh.md:130`）
- **⚠️ 领域要手动 `close`**（用 `ctx.effect` 兜底）：否则 facility 卸载时才兜底关。（出处：`storage.zh.md:130`）
- **⚠️ `register` 的 disposer 不关后端**：后端由拥有它的插件自己 `close`。（出处：`registry.ts:18-25`）
- **⚠️ storage 管"日志之外"的数据**：会话日志有自己的 seam（`persistence`），别混。（出处：`storage.zh.md:5`）
